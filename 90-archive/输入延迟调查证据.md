# 输入/帧率延迟调查全记录（2026-09-08，含收尾定案）

> **历史横幅（2026-09-09）**：文中"音频 ~100-200ms 未解"**已被 OHAudio 迁移解决**（OpenAL 默认后端切 OHAudio + FAST 通路，实测系统路由延迟 ≈25ms）；现状见 [`../40-adaptation/ohaudio-backend.md`](../40-adaptation/ohaudio-backend.md)。本文其余（输入/帧率）结论仍有效。
>
> 主题：MC 操作"不跟手"（转视角、背包 hover、物品拖动）+ 音频延迟。
> **总览入口**：`鼠标输入方案总览.md`（试过什么 / 当前方案 / 死路 / 量化对比）；本文是逐条证据全文。
> 结论先行：菜单/背包 hover 已修复（窗口级 filter 直通，真实改善）；
> 转视角 & 帧率 60 上限为 OS 仲裁/平台限制（本 SDK 2in1 无解，已定案）；
> 音频 ~100-200ms 为后端一直存在（另题）。

## 一、测量事实（探针证据）
| 环节 | 频率/延迟 | 手段 |
|---|---|---|
| 窗口层原始鼠标事件 | **150-500 Hz**（FILTERHZ/早期 MOUSEFILTER） | OH_NativeWindowManager_RegisterMouseEventFilter 计数 |
| ArkUI onMouse | 30-60 Hz（随刷新/UI 线程，偶发 5-20） | ArkTS MOUSEHZ 计数 |
| ring 入队→pump 派发 | 1-21 ms（~1 帧） | env 槽时间戳/DIAG |
| 窗口实际派发 vsync | **16.66 ms = 60Hz**（聚焦） | OH_NativeVSync_GetPeriod(RequestFrame 后) |
| 面板 | 90Hz（用户设置"高"可达 90） | 系统设置观察 |

## 二、关键因果
1. **ArkUI onMouse 频率=屏幕/引擎刷新**（官方 FAQ）：输入被 UI 线程按帧节流 → 光标高频动而 MC 低频收 = “东西在后面追”。
2. **聚焦窗口 60Hz 门控**：非我们 EGL 所致（关 vsync/`OH_SURFACE_SOURCE_GAME` 均无效）；失焦即 >60（自证 producer 能快）。90 请求（DisplaySync、窗口 NativeVSync `SetExpectedFrameRateRange`、XComponent node）**全部 rc=0 仍无效**；`OH_NativeVSync_GetPeriod` 证明聚焦窗口稳定 16.66ms。
3. **动态档仲裁不把我们当游戏**：请求是"期望"，整机控帧系统按功耗/分类决策；AppGallery 商店游戏能 90 走的是**游戏类平台通道**（OpenGTX/LTPO、游戏场景感知），**2in1 不在支持面且 SDK 未带**（文档实证）。全屏开局 90 只是窗口放大动画（所有 app 都会），动画结束即回 60（min=90 也压不住）。
4. **grab（转视角）60Hz 是结构性的**：`LockCursor(follow=false)` 冻结光标坐标（探针 dx 钉死）→ 无高频源；`follow=true` 可差分但**无光标归中 API**（pointer 只有 style/visible）；rawDelta 只在 ArkUI 内且随 60。
5. **音频 100-200ms**：一直存在（早于本轮全部改动），OpenAL/系统后端问题，另立课题。

## 三、保留的规范实现（清理后唯一方案）
**非 grab 窗口级鼠标直通**：
- native（meowcraftbridge）`meowMouseFilterStart(windowId, ox, oy)` 注册窗口 mouse filter：
  `MOUSE_ACTION_MOVE && !grabbing && isInputReady` → `local = displayPx − originPx` → `critical_send_cursor_pos`（display px 与 framebuffer 同物理像素，1:1；origin 由 ArkTS 换算 `(event.displayX − event.x) * pxPerVp`）。
- ArkTS `pushMouseMap`（每 ~100ms 低配刷新 origin，缓存 windowId）驱动；`FILTER_DIRECT=true` 时非 grab 移动走 filter，不再吃 ArkUI 30-60。
- 结果：**背包/菜单 hover 跟手、拖拽正常**（真实改善）。点击仍走原 ArkUI 绝对坐标路径（正确）。
- 附带保留：`eglSwapInterval(0)` ×2、`SET_SOURCE_TYPE=OH_SURFACE_SOURCE_GAME`（合理、无害）。

### 7.1 E3 实测（present 路径）
```
winopts: queue=5(rc=0) swapInterval=-1(rc=0) timeout=3000(rc=0)
swap block: n≈120/2s（稳定 60fps）, avg 0.5–11ms, min≈0.4ms, max 7–70ms
```
- **`eglSwapBuffers` 基本不阻塞**（无 16.6ms vblank 等待）→ 60 上限**不是合成器背压**，而是**系统显示/合成档位**（动态=60；"高"=90 见 §7.14 对比）。〔原文"MC 侧自限"已被 §7.14 #1 实验证伪，2026-09-09 更正。〕
- `queue=5` 是缓冲队列**容量**（在飞帧数未知）；`swapInterval=-1` 表示未设（`eglSwapInterval(0)` 没写进 OHNativeWindow）；`timeout=3000ms` 默认。
- 偶发 `max 20–70ms` 尖刺，与 Zink 拷贝告警吻合（见 7.4）。

### 7.2 #1 实测（ArkUI onMouse 投递节奏）
| 阶段 | n/2s | avgGap | ≈频率 |
|---|---|---|---|
| 非 grab 连续移动（最好窗口） | 120–121 | **16.67ms** | **60Hz（顶格）** |
| 非 grab 一般 | 43–97 | 20.7–47.2ms | 21–48Hz |
| **grab（转视角）** | 91–114 | **17.7–22.0ms** | **45–56Hz** |
| grab 起步/稀疏 | 44–76 | 31–69ms | 14–32Hz |

- 日志格式瑕疵：ArkTS hilog 不支持 `%{public}f`，参数错位，`maxGap=` 后那个带 6 位小数的数其实是 avgGap（真 maxGap 丢失）。修法：改用整数 `%{public}d`（如 `Math.round(avgGap)`）。

### 7.3 结论：grab 光标移动受制于 ArkUI onMouse（ArkTS 侧）
```
硬件鼠标报告
 → ArkUI onMouse（UI 线程投递）   ← ★瓶颈：grab 实测 ~45–56Hz，avgGap 18–22ms，抖动 30–69ms
 → handleMouse: vx += rawDelta*SENS（GameWindow.ets:776-785，同步）
 → critical_send_cursor_pos（最新值槽）
 → pojavPumpEvents（每 MC 帧一次 glfwPollEvents）  ← 再叠加 ≤1 帧
 → MC 渲染 → Zink → swap(4–6ms) → 合成/上屏
```
结构性原因（均为代码/头文件实证）：
1. 窗口 filter 在 grab 时**显式跳过**：`input_bridge.c:680` `if (env->grabbing) return false;`。
2. `LockCursor(follow=false)` 冻结 `displayX/Y` → 绝对坐标 filter 无增量可用。
3. SDK `Input_MouseEvent` **无任何 raw/relative delta 访问器**（只有 Action/ActionTime/Axis*/Button/CursorInfo/DisplayId/DisplayX/Y/GlobalX/Y/WindowId）。
4. `Input_CursorInfo` 只有 visible/style/sizeLevel/color/pixelmap，**无位置/增量**；**无光标归中/warp API**。
→ 系统未暴露相对位移，grab 下只能吃 ArkUI 的 `rawDelta`。

### 7.4 附带发现：渲染后端是 Zink（GL→Vulkan 翻译层）
日志：`Loaded from system paths: /system/lib64/ndk/libGLv4.so`、`selected Vulkan device (Maleoon 916) doesn't support base Zink requirements`、`ZINK: SSBO is readonly in vertex stage!`×N、`zink: PERF WARNING! > 100 copy boxes detected`。
→ 每次 GL 调用经 Zink 转 Vulkan，能解释偶发 `max swap 20–70ms` 尖刺；桌面是原生 GL 驱动，这是"桌面 vs 我们"的实质差异之一。

### 7.5 filter 线现状（确认）
- 生效证据：`meowMouseFilterStart ok window=164 ox=120.000000 oy=136.000000`（native rc=0）+ `pushMouseMap active win=164`（ArkTS `filterActive=true`）。
- 生效范围：**仅非 grab**（`MOUSE_ACTION_MOVE && !grabbing && isInputReady` → `critical_send_cursor_pos`）；grab 下按设计不参与。
- 早期 FILTERHZ 探针实测到达率 **150–500Hz**（§一）；当前构建未带逐次计数（如需再证可临时加聚合计数）。

### 7.8 #2 探针（窗口 filter 回调聚合）与 follow A/B —— grab 高频死路定论（2026-09-09）

探针：`input_bridge.c` `MeowMouseFilter` 每 ~2s 一条：
```
grabProbe gb= n= mv= sk= nmv= x[min..max] y[min..max] gx[min..max] gy[min..max] cbGap=ms devGap=ms k=
```
（`n`=回调数；`mv`=投喂；`sk`=被 grabbing/未就绪跳过；`nmv`=非移动；`k`=actionTime 单位/ms 自估）

**A. follow=false（现状）实测**
- 非 grab：坐标正常变化（如 `x[657..2338]`），`mv≈n`，直通生效。
- grab 稳态：`n≈1000/2s`（~500Hz 仍在触发）但 `mv=0 sk=n`（全被 `if (env->grabbing) return false;` 跳过）；
  且 **`x[2330..2330] y[1118..1118]` 完全冻结**（follow=false 把光标钉死）。
- 早期 grab 窗口有残余移动（`x[1551..2805]`），是锁生效前的过渡。

**B. follow=true A/B（改一行 `lockCursor(winId,true)` 实测）**
- grab 下坐标**确实活了**：`x[121..1399] y[81..799]`（窗口全域），~500Hz。
- 但用户持续向一个方向平移后：`x[1399..1399]` → **光标卡在窗口右边缘（窗口 x=120..1400）不再产生增量**。
- `devGap≈cbGap`（1.89 vs 1.97ms）→ 设备事件无合并丢步。
- 结论：follow=true 能拿 500Hz 活坐标，但**光标在窗口边界饱和**；全 SDK 无归中/warp API → 持续单向转视角 1–2s 内失效。**不可用**。

**C. 最终定论**：grab 光标高频在 API23/2in1 上**无解**：
1. follow=false → 坐标冻结；
2. follow=true → 边界饱和；
3. 无相对指针/raw delta 访问器（`Input_MouseEvent` 无 delta 字段）；
4. 无 cursor warp/归中 API（只有 `LockCursor`/`UnlockCursor`/`SetCustomCursor`）。
→ 只能吃 ArkUI `onMouse.rawDelta` 的 ~45–60Hz 投递（§7.2）。

**D. 探针修正**：`lag` 字段作废——`actionTime` 与 `CLOCK_MONOTONIC` **不同源**（固定差 ~102s、速率差 ~2%，k≈1021–1040≈µs），已改为 `devGap`（actionTime 间隔）用于查合并丢步。

**E. 长尾（未验，低期望）**：直接读 `/dev/input/event*` evdev（沙箱大概率无权限）；等 OS 新增相对指针/归并 API。

### 7.9 ArkUI NDK（ui_input_event.h）探路 → 106103 结案（2026-09-09）

**接口盘点（SDK 实证，`arkui/ui_input_event.h`，我们此前未用）**
- `OH_ArkUI_MouseEvent_GetRawDeltaX/Y`（@since 15）：硬件原始增量（native 侧）。
- `OH_ArkUI_PointerEvent_GetHistorySize`（@12）：**"当前事件与上一事件之间发生的原始事件数"**，仅 move 事件。
- `OH_ArkUI_PointerEvent_GetHistoryEventTime` / `GetHistoryX/Y` / `GetHistoryWindowX/Y` / `GetHistoryDisplayX/Y` / `GetHistoryPointerCount`（@12）：历史采样点（头文件明确适用于 **mouse/touch/axis**）。
- `OH_ArkUI_UIInputEvent_GetEventTime`（@12）。
- `ArkUI_UIInputEvent_Type`：TOUCH=1 / AXIS=2 / **MOUSE=3** / KEY=4。
- 入口限制：`OH_NativeXComponent_RegisterUIInputEventCallback` 头文件注明 **"Currently, only axis events are supported"**；legacy `OH_NativeXComponent_MouseEvent` 只有 x/y/screenX/screenY/timestamp/action/button（**无 delta**）。→ 只有 **ArkUI 节点事件 `NODE_ON_MOUSE`** 能拿到上述访问器。

**实测（临时探针）**：ArkTS `getAttachedFrameNodeById('game-xc')` → NAPI `bindNode` → `OH_ArkUI_GetNodeHandleFromNapiValue` → `addNodeEventReceiver` + `registerNodeEvent(NODE_ON_MOUSE / NODE_ON_HOVER_MOVE)`：
```
bindNode handle=0x.. add=0 mouse=106103 hover=106103   → rc=-1（注册失败，无 nodeMouse 日志）
```
- `arkui/native_type.h:2523`：`ARKUI_ERROR_CODE_ARKTS_NODE_NOT_SUPPORTED = 106103` —— *"The corresponding operation does not support nodes created by ArkTS."*
- → **NDK 节点事件不支持 ArkTS 声明的节点**；raw delta + history 这套在现有 ArkTS XComponent 结构下**不可达**（这解释了为什么"没人拿到 raw delta/history"）。

**可选路径（均未执行，用户决定结案）**
- A. NDK 透明覆盖节点（`NodeContent`+`ContentSlot` 叠在 XComponent 上，native `createNode(ARKUI_NODE_STACK)`）→ 可量出 NDK 节点事件频率与 history；探针期会吃掉鼠标事件。
- B. XComponent 改 NDK 创建（`createNode(ARKUI_NODE_XCOMPONENT)` + NodeContent）≈ SurfaceHolder/Stage B 迁移 → 拿 raw delta+history+直接 native window+节点帧率 API。
- C. **结案（本轮选择）**：`ui_input_event.h` 那套在 ArkTS 节点上不可用，60Hz 上限成立。

**状态**：全部探针已回滚（当时 HEAD = `ff9ff8a`，仅保留鼠标 filter 原点整数日志；现 HEAD = `114d56a`）。

### 7.10 突破：NDK 覆盖节点绕过 106103 → grab 原生输入落地（2026-09-09，commit `dcbeeb7`）

**方法**：ArkTS 放 `ContentSlot(NodeContent)`；native `createNode(ARKUI_NODE_STACK)` + `NODE_WIDTH/HEIGHT_PERCENT=100` + `NODE_HIT_TEST_BEHAVIOR=ARKUI_HIT_TEST_MODE_TRANSPARENT`（自己响应且不挡下层 XComponent），挂到 NodeContent 并注册 `NODE_ON_MOUSE`。

**实测**
- 注册成功：`bindNodeContent node=0x.. add=0 mouse=0 contentAdd=0` —— NDK 创建的节点**不受 106103 限制**。
- grab 下节点事件实测 n≈240/2s；**但当时同一 NodeContent 上挂了 2 个接收器**（`bindNodeContent` 调用 2 次、`pojavSetSurfaceId` 仅 1 次）→ **实际速率 ≈ 60Hz**（详见 §7.12 更正）。`rawNz≈n`、`histNz≈n`、`histTot≈2n`（每事件约 2 个 history 采样点）。
- `HitTestMode.Transparent` 下 XComponent 的 ArkTS 事件不受影响（用户确认点击/菜单/转视角正常）。

**落地**
- `input_bridge.c`：`meowGrabSetSens/meowGrabReset/meowGrabDelta`；虚拟光标移到 native，**仅 `env->grabbing` 生效**。
- `meowjrebridge.cpp`：覆盖节点 + `NODE_ON_MOUSE` 接收器，rawDelta → `meowGrabDelta`。
- `GameWindow.ets`：ArkTS grab 分支禁用（防双重累加）；grab 开始时 `meowGrabReset` 居中。

**坑（已修）**：`onSurfaceReady` 多次触发 → `bindNodeContent` 重复调用（实测 **14–44 次**），每次新建节点 + 注册接收器并挂到同一 NodeContent → **同一事件被处理 N 遍**，表现为"**窗口越小越灵敏**"（倍数 = resize 次数）。修复：native `g_boundContent` + ArkTS `overlayBound`，**同一 ContentSlot 只绑一次**。

**复验日志指纹**：`bindNodeContent node=.. add=0 mouse=0 contentAdd=0 sens=1.0`（每窗口一次）；`meowGrabReset` 每次进入 grab 一次；**无逐事件日志**。

### 7.11 backlog：`GetHistory*` 亚帧插值（**有缘再做，未实施**）

**现状**：`NODE_ON_MOUSE`（**= 显示帧率，60/90Hz**，见 §7.12）每个事件除 `rawDelta` 外还带约 2 个 history 子采样（实测 `histTot≈2n`、`histMax=3–4`），即设备真实上报 ~240Hz 被 ArkUI 合并进一个事件。可用 `OH_ArkUI_PointerEvent_GetHistorySize/GetHistoryX/Y/GetHistoryEventTime` 取到逐样本坐标+时间戳。

**三种"亚帧"用法与结论**
| # | 做法 | 结论 |
|---|---|---|
| a | **丢步兜底**：`meowGrabDelta` 改为 `Σ(history 逐样本 Δ) + 主 Δ`，而非只信 `rawDelta` | **唯一可能必要**——若 ArkUI 的 rawDelta 只反映"最后一段"而非累计，则高负载/合并时丢位移；用 history 求和可补回 |
| b | 时间对齐/插值：把样本按时间戳摊到帧内 | ❌ 不做：MC 每帧只读一次光标，摊开也取同一个总和 → 收益≈0 |
| c | 外插预测：按速度把运动外推到本帧渲染时刻 | ❌ 不做：省几 ms 延迟但方向突变过冲/抖动，FPS 易"甩过头"；且投递率已 ≥ 渲染率（60/90），边际小 |

**若将来要做，先做前置验证（无行为改变）**：同一段匀速鼠标动作、在不同窗口大小/负载下，比较 native 每 2s **总位移 `Σ|Δ|`**。
- 总位移稳定 → `rawDelta` 已累计 → **不做**（history 仅锦上添花）；
- 总位移随窗口/负载变小 → 有丢步 → **做 (a)**。

**背景依据**：剩余延迟大头是"输入投递（UI 帧量化）+ MC 每帧读一次 + Zink 渲染 + 上屏/合成"；history 只影响"最后一个样本→本帧"几 ms，故 (b)/(c) 不值得。

### 7.12 更正：native 节点事件速率 = 60Hz（"120Hz" 是重复接收器假象）

- 10:23 探针：`pojavSetSurfaceId` 仅 1 次（同一 surface），但 `bindNodeContent` **调用 2 次** → 同一 NodeContent 上 **2 个接收器** → 每个事件被处理 2 遍 → `nodeMouse n≈240/2s` 实际是 **~60Hz/接收器**。
- 修复 bind-once 后，左下角 overlay（`meowGetInputRate`，统计有效光标投喂/秒）实测 grab 下 **稳定 60Hz**。
- **实测结论：`NODE_ON_MOUSE` 派发速率 = UI 帧率 = 60Hz，与窗口大小 / FPS 无关**（用户拖大拖小均 60）；并不比 ArkTS onMouse 的 60Hz 高。**"2× 突破"结论作废。**
- 保留 native 路径的理由（用户决定保留）：实测比 ArkTS grab 路径（45–56Hz）略稳（60Hz）；原生 rawDelta 省掉 ArkTS→NAPI 一跳；可访问 `history`（未来丢步兜底，见 §7.11）。
- 含义：grab 采样率上限 = **UI 帧 60Hz**，与输入通道无关；要再提升只能等 OS 提供相对指针/归中 API（§7.9 的长尾）。

### 7.13 观察：系统刷新率设置（高=90 / 动态=60）显著改变背包拖拽跟手度（2026-09-09）

- **现象**：鼠标 filter 路径采样率不变（~500Hz）时，系统设"**高**"（90Hz）下背包拖拽明显比"**动态**"（锁 60）更跟手。
- **归因（用户已确认机制 1、2）**：差异在**显示/合成/渲染节拍**，不在输入采样（输入已远高于显示率）。
  1. **上屏节拍**：90Hz 每帧等待 ≤11.1ms（vs 60Hz ≤16.7ms）→ 视觉反馈更早、更新粒度更细；
  2. **系统光标**：随面板率合成（90 vs 60）→ 拖拽"锚点"更顺；
  3. **应用渲染帧率可能被放开**（动态档锁 60、高档可能允许 90）——**待验**（高档下看 MC FPS / overlay grab 读数）。
- **关键修正**：之前"聚焦窗口派发 vsync = 16.66ms（60Hz）"很可能是在**动态档**测的；**系统设置才是 90Hz 的总开关**（应用侧 API 请求全被拒）。→ "grab 上限 60Hz"应**按档位区分**。
- **含义**：对背包拖拽/整体跟手，瓶颈在**渲染与上屏节拍**，不在输入采样（与 §7/E3 的"输入已不是瓶颈"一致）。

### 7.14 上屏慢研究：四层来源 + env 杠杆 + 测量配方（2026-09-09，两路侦查）

**结论**：我们的渲染机制确实存在上屏慢，量级约 **1–2 帧（16–33ms）**，四层来源：

| # | 层 | 证据 | 量级 |
|---|---|---|---|
| 1 | **BufferQueue 深度 = 5** | hitrace `nodeId_28Surface queueSize: 5`（5 个 buffer seq）；SDK 无 `SET_BUFFERQUEUE_SIZE`（只有只读 `GET_BUFFERQUEUE_SIZE`） | 最深 ~4 帧；flush→acquire 实测 **4.5–14ms（~8ms）** |
| 2 | ~~RenderService 走 GPU 合成（非 HWC/直通）~~ **← 已被下文 hitrace 证伪** | 原 trace 见 `DrawImage(GPU)`；**实测为 HWC 直通**（`CommitTunnelLayer`、`DrawImage`=0） | ~~+2/3 帧~~ **不成立** |
| 3 | **present mode 很可能仍 FIFO** | `eglSwapInterval(0)` 在 `egl_gl.c:153` 调用于 `eglMakeCurrent(:188)` **之前 → 大概率 no-op**；`pojavSwapInterval`(:337-342) 强制 0 但**仓内无调用方**；`MESA_VK_WSI_PRESENT_MODE` 本构建**未编译** | 60 硬锁 + present 串行 |
| 4 | **Zink present 序列化** | present 跑在 `zfq0` 线程，`max_acquires=num_images-minImageCount+1`；`num_images==minImageCount` 时每帧等 present fence（`zink_kopper.c`） | 额外等待 |

**栈事实**：`libGLv4.so → libEGL.so → libEGL_mesa.so → libgallium-25.0.1.so`（Mesa **25.0.1**，Zink + kopper WSI）→ `libvulkan.so` → Maleoon 916。设备实为 **`apiversion=26` / `7.0.0.105`**（比 SDK 6.1.0(23) 新）。

**env 杠杆（本构建 `strings` 实测引用）**：
- ✅ `vblank_mode=0`（`libgallium`）：0=不同步；Zink 在 interval 0 时映射 **IMMEDIATE**（不支持则 MAILBOX）。**唯一能改 present mode 的**。
- ✅ `GALLIUM_THREAD=0`：去掉 threaded-context 中转线程（少一跳，代价 CPU 并行度）。
- ❌ `MESA_VK_WSI_PRESENT_MODE` / `__GL_SYNC_TO_VBLANK`：本构建**无引用**（0 hits）。
- **注入点**：`meowjrebridge.cpp` setenv 块（`:137-174`），在预 dlopen `libGLv4.so`（`:182`）之前——Mesa 在 screen init 时读 env。**JVM `-D` 属性进不了 `getenv()`**。

**测量配方（本机验证可用）**：
```
hitrace -t 5 -b 32768 --text -o /data/local/tmp/mc.txt graphic ace window app
grep 'RequestBuffer .*queueSize'            # 队列深度（实测 5）
grep 'AcquireBuffer name: nodeId_28Surface' # app FlushBuffer→RS Acquire 的 present 延迟
grep 'DrawImage(GPU)'                       # 有 → GPU 合成；无 → HWC
grep 'CommitLayers\|HwcPresentDisplay'      # 上屏时间；present 结束点 = RSHardwareThread::CommitAndReleaseLayers
```

**实验 A+B 结果（2026-09-09）**
- A：补 `eglSwapInterval(0)` 到 `eglMakeCurrent` 之后（`egl_gl.c` `egl_make_current_full`）；B：`setenv("vblank_mode","0")` + `setenv("GALLIUM_THREAD","0")`（`meowjrebridge.cpp` 预 dlopen 前）。
- **日志确认 B 生效**：Mesa `ATTENTION: default value of option vblank_mode overridden by environment.`；无 `zink: failed to set swap interval` 报错。
- **MC FPS 仍 60**，手感"跟手一点点"（用户主观）；**无撕裂/闪烁**。
- **判读**：60 的**速率上限不在 Mesa 侧**（否则 vblank_mode=0 会破 60）→ 在 **OS 合成器 60 档 / Vulkan WSI（可能只支持 FIFO）**。手感小幅改善更可能来自 **Mesa present 串行 / threaded-context 中转被移除**（相位延迟少几 ms），非心理作用。
- **决定**：保留 A+B（无害、略优）。速率要破 60 仍需系统"高"档或 OS 放开。

**hitrace 实测（2026-09-09，背包拖拽 ~8.3s，A+B 已上；文件 `stuffs/research/mc/mc_trace.txt`）**
- **合成路径 = HWC 直通**：`CommitTunnelLayer` 1694 次，`DrawImage` **0** 次 → §7.14 表中的"GPU 合成"在本轮**不成立**（覆盖节点也**没有**导致 GPU 合成）。
- **队列深度 = 5**（所有 `RequestBuffer ... queueSize: 5`）。
- **显示 vsync = 60Hz**（`GenerateVsyncCount` 496/8.27s）。
- **游戏面 `nodeId_28Surface` 生产者 ~81–91fps**（flush 间隔 p50 **10.93ms**）→ **快于 60Hz 显示**，与 `vblank_mode=0` 解锁一致；但 **MC 自报 FPS 仍 60**（疑其计数/上报被锚定 60）。
- **flush→acquire：avg 7.95 / p50 8.31 / p90 14.23 / max 16.68 ms**（app→合成器交接 ≈0.5 帧）。
- **判读**：上屏慢 ≈ **1 帧量级**（交接 0.5 帧 + 合成/扫描相位），**不是 GPU 合成、也不是深队列爆炸**；A+B 让生产者跑到 >60fps、最新帧更新鲜 → 手感略好。
- **待办**：① 用 photodiode/高速相机量绝对 input→photon；② 系统"高"档再抓一次看 90 路径。
- **#1 实验（stub `REFRESHRATE` 60→90，`tools/patch_glfw_refresh.py`）**：MC FPS 仍 60、overlay 仍 60、手感无变化 → **stub 上报的 monitor 刷新率不是限帧/锚定来源**（MC `maxFps=260`、`vsync=false`，其 FPS 显示的是实际渲染率）。**已回滚补丁**（tar + `EXTRAS_VERSION`），工具保留备用。

**hitrace 对比：系统"动态"(60) vs "高"(90)（2026-09-09，背包拖拽）**

| 指标 | 动态(60) | 高(90) |
|---|---|---|
| 显示 vsync（`GenerateVsyncCount`） | 60/s | **89.7/s** |
| 合成器档位（`CommitLayers rate`） | 60 | **90** |
| 合成路径 | HWC 直通（`DrawImage` 0） | HWC 直通（`CommitTunnelLayer` 2649） |
| `queueSize` | 5 恒定 | 4–5（偶 8） |

| **flush→acquire p90** | 14.23ms | **10.32ms** |

**判读**：系统"高"把**显示/合成抬到 90Hz**，且 **app→合成器交接延迟降 ~2.5ms**（p90 降 ~4ms）→ 这就是"高"档拖拽更跟手的量化原因。生产者本身 ~85fps（两档都够），90 档下被丢的帧更少（~5/s vs ~25/s）。

- **grab 采样率 = 显示帧率**（用户实测）："高"档下左下角 overlay 的 grab 读数 **>60、接近 90**；"动态"档 60。→ 坐实 grab 输入（`NODE_ON_MOUSE` 派发）与**显示刷新率同源**，并非独立的"鼠标采样率"短板。**系统刷新率档位是唯一总开关**（应用侧 90 请求无效）。

**怀疑点（已结案）**：透明覆盖节点**没有**把游戏面推向 GPU 合成——hitrace 实测 `DrawImage`=0、走 `CommitTunnelLayer` HWC 直通（见上文"合成路径 = HWC 直通"）。

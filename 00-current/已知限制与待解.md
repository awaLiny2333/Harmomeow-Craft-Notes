| # | 项 | 结论 |

| B2 | 上屏 ~1 帧交接 | OS 合成侧（HWC 直通 + 队列 5），应用层无杠杆 |

| B4 | 崩溃报告显卡信息为空 | oshi `getGraphicsCards()` 跑 `lspci` / `lshw`（OHOS 无）⇒ 空；F3 的 GPU 行来自 GL 字符串，正常。不做（仅崩溃报告可见）；见 [`../40-adaptation/oshi-cpu-info.md`](../40-adaptation/oshi-cpu-info.md) §6 |

| B6 | 触控设置文件（`touch-controls.json`）的**内存缓存**与**旧值迁移** | **定案：保留现状、都不做**（2026-09-21 用户决定）—— ① 模块级缓存**不失效** ⇒ 手改该文件后**重启 / 重开游戏窗生效**，**当作普通设置看待** ✓（"整份替换"同理，自下次读取起生效 ✓）；② **不做**从旧位置（`app-settings.json` 的 `global.launcher`）的迁移 ⇒ 8 项一律走默认值 ✓（与项目"不做迁移"惯例一致）。理由：这些 getter 只在开窗 / 开面板时被读很少几次 ⇒ **加失效机制或迁移都属于画蛇添足** ✓；真正的问题（两进程各自缓存互相覆盖）只在"手改文件 + 同时触发写盘"的极端组合下出现，暂不为此加逻辑。见 [`../20-design/launch/实例设置存储-方案.md`](../20-design/launch/实例设置存储-方案.md)。 |

| B7 | **菜单内移动鼠标后返回游戏，视角被 MC 原版 `accumulatedDX/DY` 带一点**（已接受） | **现象**：菜单里移动鼠标后返回游戏，视角会被带一点（用户决定"不管"）。**真因**：MC `MouseHandler` 把菜单内位移累加进 `accumulatedDX/DY`（grab/release 都不清零），恢复后由 `turnPlayer` 应用（`MouseHandler.java:294-300`；非 grab 用 `xpos-this.xpos`）。**动它需要改 MC ⇒ 违反"不改 MC"硬约束，故不动**。**重开条件**：若将来放宽"不改 MC"约束再议。取证报告 工作区根 `stuffs/research/input-audit/MC-SRC-mouse-resume.md`；平台侧"不存在 warp/归中 API"见 §A2、不变量见 [`../20-design/launch/决策与不变量.md`](../20-design/launch/决策与不变量.md) §24。 |

| B8 | **MC 朗读器（无障碍 TTS）不可用：JNA 不随包 + 沙箱路径进不了命名空间（已接受，不做）** | **现象**：MC 启动时 `[mojang/Narrator] Error while loading the narrator`（`Narrator$InitializeException: Failed to load library flite`），同一栈里可见 `UnsatisfiedLinkError: <cache>/mc-run/<key>-<id>/natives/jna<随机>.tmp: Error loading` 与 `NoClassDefFoundError: Could not initialize class com.sun.jna.Native`。**根因链**：朗读器走 `com.mojang.text2speech` → **JNA** → flite；而 **`libjnidispatch.so` 已于 2026-09-09 从随包件摘除（JNA 不再随包）**（见 [`../40-adaptation/oshi-cpu-info.md`](../40-adaptation/oshi-cpu-info.md) §2）⇒ JNA 只能从 `jna.jar` 里把自带的 dispatch 库解到 `jna.tmpdir`（= run 目录的 `natives/`）再 `System.load`，而平台加载器的**命名空间可达性检查**拒掉这条路径（日志形态 `load absolute_path …: check ns accessible failed namespace=moduleNs_<bundle>/meowjre`；同族判据的早期记录见 [`../90-archive/jvm-step1.md`](../90-archive/jvm-step1.md)）⇒ `com.sun.jna.Native` 类初始化失败。**非致命**：MC 只记一条 ERROR 并**关掉朗读器**，启动照常继续（同一次运行其后仍有 `Reloading ResourceManager` / `Sound engine started`，可正常游戏）；真库不可用时另有随包 no-op 桩兜住调用点（`meowcraft_extras` 内的 `Narrator`/`NarratorDummy`，来历见 [`../20-design/launch/Forge-1.13及以上-调研与方案.md`](../20-design/launch/Forge-1.13及以上-调研与方案.md) §5.4）。**影响面**：朗读器；其它 JNA 依赖路径（如 oshi 的 `platform.linux.Udev`）同样走不通 —— oshi 主线已改自编"无 JNA"合成，不受影响。**为什么不做**：要修就得把 `libjnidispatch.so` 重新随包 / 放进 el1 命名空间，与 2026-09-09「摘除 JNA」的决定相反，而朗读器不是游戏必要功能。**与沙箱目录改名无关（已排除）**：该失败自 2026-09-22 起、横跨 1.18.2 / 1.19.4 / 1.20.1 / 1.20.6 / 1.21.1 / 1.21.10 / 26.1.2 / 26.2 / 26.3 / 26.4-snapshot-2，且**旧前缀式布局下同样出现**（旧名 651 次 / 新名 99 次）。**重开条件**：有人需要无障碍朗读，或有 mod 硬依赖 JNA。 |

| B9 | **未选 Vulkan 时日志出现 `Failed to locate library: liblibmeow-no-vulkan.so.so`（预期噪声，非缺陷）** | **现象**：非 Vulkan 档启动时，游戏侧 stderr 有一条 `java.lang.UnsatisfiedLinkError: Failed to locate library: liblibmeow-no-vulkan.so.so`。**机制**：这正是我们**故意**用来关掉 Vulkan 档的手法 —— `VULKAN_LIB_DISABLED = 'libmeow-no-vulkan.so'`（`LaunchDefaults`）经 `-Dorg.lwjgl.vulkan.libname` 指向一个**不存在**的占位库，LWJGL 的 Vulkan 探测因此失败、MC 直接跳过 Vulkan 组（选 Vulkan 时同一参数指向真实存在的自研 shim，实测正常加载）⇒ 这条 ERROR 属**预期结果**，不影响启动。名字里的双重前后缀（`liblib…so.so`）= LWJGL 对本属性值再套一层 `lib`/`.so`。**不做**：纯日志噪声、代价为零；**判读注意**：它容易被误当成崩溃，看它后面有没有 `ExceptionInInitializerError` / 调用栈即可区分（有的才是真问题，如 §B8）。 |

| B10 | **`lockCursor` 失败会引发无限重试风暴（已记录，暂不修）** | **现象**：1.7.10+Forge+OptiFine 实例跑 64 秒，日志 `lockCursor windowId=3343 rc=1300002`（窗口状态异常）**15,872 次**、`rc=0` 仅 16 次 ⇒ 约 **15,888 次尝试 / 23,825 行日志（≈250 次/秒）**，hilog 被淹。**根因**：`GameInputController.setGrab()` —— 锁失败时只 `return`、**不提交 `grabApplied`**；而 `finally` 里有"边缘补偿"`if (grabApplied !== grabNative) setGrab(grabNative)` ⇒ 持久失败时**自我重入、无上限**。历史运行只有 8–60 行（偶发失败 2–20 次即成功）⇒ 一直潜伏。**危害**：不致命（游戏可玩，光标按"锁失败"降级，与 §A2 不冲突），代价 = 日志被淹 + 持续打 native + CPU 空转。**为什么暂不修**：用户裁决（第一次见，先记录在案）。**修法要点**：① 失败即提交状态（或加 `grabFailed` 标记）止重入；② native（`meowjrebridge.cpp` 的 `LockCursor`）与 ArkTS 两层改成**仅失败/状态变化时**打日志；③ 专项查 `1300002` 真因（窗口 id 用错〔XComponent 子窗口 vs 主窗口〕/ 失焦或全屏切换后不再允许锁）—— 失败时记 `windowId` + 窗口状态并试主窗口 id。**重开条件**：再遇该洪水日志，或做"光标锁/相对指针"专项。**落点**：`common/input/GameInputController.ets`（`setGrab`）、`libs/meowcraftlib/src/main/cpp/meowjrebridge/meowjrebridge.cpp`（`LockCursor`）、[`../20-design/input/输入-总览.md`](../20-design/input/输入-总览.md)。 |

## D. 性能：已确立的结论与待探测

- **基准模型**：26.2 + Fabric + Sodium｜16 视距 / 6 模拟｜2x 缩放 ⇒ **`帧时 ≈ 8ms 固定 + 7.5ms/MP`** ⇒ **固定每帧成本是大头**
  （4x 只渲 0.12MP 仍要 9.1ms）；固定 ~8ms = **CPU 侧**（MC 主线程 + Zink 提交/状态跟踪 + JVM），GPU 只在 1x(1.85MP) 附近成为主角
  ⇒ 「提高 FPS」= **削 CPU 固定成本** + **削每像素成本**（后者已有「显示缩放」）。
- **Vulkan 档性能差距（根因已确证，仍未消）**：present 模式 = `MAILBOX`（非垂直同步限帧）⇒ 菜单 **≈60 FPS** · 世界 **≈21–24 FPS**（2026-09-18 实测）；**GL 后端同场景 60–70 FPS**。**根因**（2026-09-19 确证）：同步**逐调用付费 + 每帧合流** ⇒ CPU 与 GPU 不重叠；GL 快靠 **Mesa glthread** 把调用入队交独立线程（用户实测 `GALLIUM_THREAD=0` ⇒ GL 也掉到 20–30 且各视角一致）。**F87 起已有实测收益**：掉帧视角 **20–30 → 30+ FPS**。F92–F98 **池健康有界**、实机核对通过（2026-09-19）。**「每帧均匀成本」假设已推翻**（判据：仅特定视角掉帧、多数视角 60 FPS ⇒ 成本随该视角命令数走，非固定每帧成本）。**原「剩余杠杆」已实机证否**：收窄 F69 阻塞等待（原判高风险、建议先加等待计数）经 F101 计数实测——`wait_drain=0`（F60 整队列 drain 从未触发、P1 无靶子）、100% 等待由 F69 服务、等待墙钟 **≈0.02 ms/帧**（下界；2026-09-19 用户实测）⇒ 同步面已 ≈0、无剩余空间。**收官结论：我方这一层（shim）的结构性收益已尽**（等待面 ≈0 / push 路径 0.22 ms/帧 / 环复用不可行 F100）；剩余 ~16 ms 差距（Vulkan ~30 vs GL 50–60）在 MC 自身 / 驱动 / GPU 侧。见 [`../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md`](../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md) 记录 9/16/17/18。
- **26.3 Vulkan 的实测与"我方已尽"的再确认（2026-09-20，用户实测 + 导出 `.logs`；**只研究 26.3**，26.2 不再考虑）**：
  - **帧率口径**：**简单/默认地形 ≈70–80 FPS**（2026-09-19 起多次）·**复杂场景 ≈42–45 FPS**（2026-09-20 三次可比运行 37.6 / 44.6 / 41.8；**37.6 那次系游戏内下雨**，属混杂，不可作基线）。
  - **帧时由 GPU 主导**：仪表实测**每帧恰好 1 次提交（2 条 entry）**、≈90 push / ≈320 draw / ≈540 bind / **≈36 barrier**，F72 池路径 `vkQueueWaitIdle` **0 次**，且 **60–64% 墙钟阻塞在 `vkWaitSemaphores`**（等"2 个提交之前"，`MAX_SUBMITS_IN_FLIGHT=2` 硬编码）⇒ **我方 shim 的 CPU 开销不是瓶颈**。
  - **已证否（2026-09-20）**：① `maxDrawIndirectCount` 上报开关（门控本就开、无可测效应；该 env 与 F103 仪表**已整体撤回**）② 图像布局转换（每帧 0 次）③ 提高 imageCount（in-flight 硬编码 2）。
  - **现存候选（排序，均"只改 shim"；尚未做 —— 用户决定先落档）**：诊断丢弃全量 mem barrier（量上限）→ 收窄其 mask → 相邻 barrier 去重 → 去重 clear → 合并同附件连续 pass → presentMode `FIFO→FIFO_RELAXED`。
  - **不可影响（仅记录）**：**OIT 把 TRANSLUCENT 地形重画 3 遍**（GPU 吞吐头号嫌疑，纯 MC 侧）、每帧 1 次 main→swapchain 整屏 blit。
  - 依据与素材：综合见 工作区根 `stuffs/research/vineflower/findings/00-synthesis.md`（§1–§7）；MC 侧调研见同目录 `a1–a8`、GPU 侧见同目录 `c1–c3`（均在工作区根 `stuffs/research/vineflower/findings/` 下）；见 [`../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md`](../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md) **记录 19**。
- **F72 描述符集环复用已证不可行（判据 + 结论）**：F99（`.77`）把环复用升默认开并加**运行时覆盖门**（不变量 I5）后，实机（2026-09-19 用户实测）进世界 ⇒ **满屏闪 + 帧数极低**；定量根因 = 环复用以自由表**替代** `vkResetDescriptorPool`，而池 `maxSets` 是两次 reset 间的累计分配预算 ⇒ `allocs` 触顶 `pools×maxSets`（`13634 ≈ 54×256`）⇒ `OUT_OF_POOL_MEMORY` ⇒ push 回退**坏的原生 `vkCmdPushDescriptorSet`** ⇒ `VK_ERROR_DEVICE_LOST`。结论：**覆盖门只保证内容正确，真正的墙是容量生命周期**（归还内存必须 reset，而 reset 使池内全部待复用 set 失效）⇒ **已定案不做**（收益仅推算 0.1–1 ms/帧）。F100（`.78`）已回退默认关（`MEOW_VK_F72_RING=1` 仅研究）⇒ 本条与「收窄 F69 等待」两条原「剩余杠杆」均已关闭（见上）。见 [`../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md`](../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md) 记录 17、[`运行时环境变量.md`](运行时环境变量.md) §1。

  **都生效**（`rc=0` / `bound 12-19`、无崩溃）但**无可感收益** ⇒ ~8ms 固定成本**非核心放置问题**；旋钮保留 opt-in（默认关）。

- **NeoForge patched client jar 落共享库区（未修）**：`PATCHED`（打补丁后的 client jar）由 profile `data` 的 maven 坐标展开、落在**共享 `libraries/`**（**26.x** = `net/neoforged/minecraft-client-patched/…`；**1.21.x** = `net/neoforged/neoforge/<ver>/neoforge-<ver>-client.jar`；`NeoForgeInstaller` 的 `set.patchedPath`），而安装**失败不回滚**（与 HMCL 同款：靠幂等续跑）⇒ **半完成**的安装理论上会留下陈旧产物，被后续 processor 运行（工具「存在即跳过」）复用。HMCL 同样把这一步交给 installer、无独立清理。**重开条件**：需在共享区引入「按实例 / 按运行标记产物新鲜度」，或在重装前清 `PATCHED`。见 [`../20-design/launch/安装链-总览.md`](../20-design/launch/安装链-总览.md) §6 与 [`../20-design/launch/NeoForge支持-调研.md`](../20-design/launch/NeoForge支持-调研.md)。
- **模块化 classpath 撞包：同一包被两个提供者导出（机制记录）**：
  **机制** = 若某加载器/bootstrap 把 `java.class.path` 上**每一条**都当模块候选做**模块解析**（**无包归属去重**），则"同一个包被两个提供者导出"会**硬失败** —— `java.lang.module.ResolutionException: Modules X and Y export package P to module Z`（`java.base` 的 `Resolver.checkExportSuppliers`）。
  **本项目的唯一已知命中** = `com.mojang.text2speech`（真实库 `libraries/com/mojang/text2speech/<v>/text2speech-<v>.jar` 与随包 `launcher.jar` 桩里的两个 no-op 类同时导出该包）。**随包 `launcher.jar` 桩件已退役、不再进任何 classpath** ⇒ classpath 上 `com.mojang.text2speech` 只剩真实库一个提供者 ⇒ **该撞包不再可能出现**（Forge ③ 代实测 `ResolutionException` 计数 = 0）⇒ ③ 代"划出支持面"是**政策选择**，不是技术必然。
  **已知不命中（避免误报）**：① 代 `cpw.mods.modlauncher.Launcher`（不做模块解析）；② 代 `cpw.mods.bootstraplauncher.BootstrapLauncher`（其 `PackageTracker` 按**包归属去重**）；NeoForge（`launcher.jar` 根本不进它的 classpath）。
  **同族陷阱（模块化加载器接入前需一并核查）**：自动模块名取自**文件名**；随包 jar **不得声明 `Multi-Release` 而无 `META-INF/versions/**`**（否则 NeoForge 1.20.2 的 bootstraplauncher 在 `SecureJar.from` 崩）；`oshi` 属"同名替换"而非第二提供者；`org.lwjgl` 是双向跳过（设计性）；`com.google.gson` 靠 shade 成 `meow.gson` 已消除。
  **指针** = 细节与取证见 [`../20-design/launch/Forge-1.13及以上-调研与方案.md`](../20-design/launch/Forge-1.13及以上-调研与方案.md)（§5.2 C 撞包取证、§5.4 桩包来历）与 [`../20-design/launch/决策与不变量.md`](../20-design/launch/决策与不变量.md) §0.4、§21。

- **手机 Fabric 首次 remap 崩（用户存储 FUSE 拒 chmod）**：已解决（2026-09-27，用户实机确认能进游戏 + 装 mod）—— 手机游戏目录在用户存储（FUSE/hmdfs）**拒绝 chmod** ⇒ Fabric tinyremapper 经 `jdk.zipfs` 写 `.fabric/remappedJars/*.jar` 时 `ZipFileSystem.sync()` 的 `Files.setPosixFilePermissions` 抛 `EPERM` ⇒ Fabric 崩。修法 = 把该 chmod 改为 **best-effort**（jar 字节不变）+ JDK 官方 **`--patch-module jdk.zipfs=`** 投放（不动 jimage/jmods/模块哈希）；数据令牌升 **r2**。见 [`现状基线.md`](现状基线.md) §5 第 27 条、[`../20-design/launch/安装链-总览.md`](../20-design/launch/安装链-总览.md) §2、[`../20-design/launch/环境与载体.md`](../20-design/launch/环境与载体.md) §6、主仓 `tools/jre26/README.md` §6。

## H. Vulkan 后端（收官后在册）

> 两条渲染链（GL / Vulkan）的架构与逐项机制见 [`../20-design/render/渲染链-结论.md`](../20-design/render/渲染链-结论.md) §2；本节只登记未决项。
> 可用性与当前口径以 [`现状基线.md`](现状基线.md) §5 第 24 条为准。

- **H1 GL 档间歇性闪（沿用观察）**：F78 已把「GL 路径上的窗口 usage 写操作」**彻底摘除**（该逻辑现只服务 Vulkan WSI）；**但用户实测仍有偶发闪**。用户线索：「平时玩 Fabric + Sodium 无此问题；可能是先于本役就存在」——Sodium 会替换原版渲染 ⇒ **不能据此断言因果**。见 工作区根 `stuffs/research/vulkan/fixes/F78-gl-flicker-and-fence-fix.md`。
- **H2 性能差距（未修，登记）**：同场景 **Vulkan 世界 ≈21–24 FPS vs GL 60–70 FPS**。**26.3 的实数与结论见 §D 末条与 [记录 19](../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md)**（复杂场景 ≈42–45 FPS；帧时由 GPU 主导、我方 shim 无结构性余量）。**根因已确证**（2026-09-19）：同步逐调用付费 + 每帧合流 ⇒ CPU 与 GPU 不重叠；GL 快靠 Mesa glthread（`GALLIUM_THREAD=0` ⇒ GL 同为 20–30）。**F87 起有实测收益**（掉帧视角 20–30 → 30+）；F92–F98 池健康有界、实机核对通过（2026-09-19）⇒ **差距未消**。见 [`../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md`](../20-design/perf/Vulkan后端-性能瓶颈清单与实验计划.md) 记录 9/16 与 §D。
- **H3 未决小项**：① MC 版本 <26.2 选 Vulkan **不给 MC 传 `--graphicsBackend vulkan`**（静默走 GL；**无启动期告警**，但**编辑面板副行现显示"生效后端"** = GL 档，与启动路径同源 `RendererPolicy.vulkanBackendRequested`，故无专门的"禁用 / 告警"文案）；② 一处 CMake 注释仍说「只在 `MEOW_VK_SHIM` 打开时」（已过时，实际是「被加载即挂钩」）；③ `tools/jre26/inject_malloc_slack.py` 未被任一 `tools/` README 登记（内部 helper，由 `linux_build_jvm.sh` 调用）。
- **F69 计数口径不一致（2026-09-19 新观察，未定性质）**：26.3 Vulkan 档日志出现 `F69 map full sem=…; evicted oldest fence=… (evict#8000+)`（节流告警）、收尾 `fences=64`，但同一 `F72b push totals` 行里 **`f69_evict=0`** —— 两处计数对不上，**不得据此判「有无丢等待」**；下次动 shim 时一并核对。物证 工作区根 `stuffs/research/sdl/reports/vulkan-mc263.md` §5。
## I. GL3 core 入口面：静默 no-op 陷阱（在册）

> core 后端 = 一份 `libgl4es.so` 把桌面 GL 3.3 → 原生 GLES 3.2（服务 MC 1.17–1.21.x）。
> 逐轮细节见 [`../20-design/render/GL33到GLES32-后端-方案.md`](../20-design/render/GL33到GLES32-后端-方案.md) §19；审计报告 工作区根 `stuffs/research/gl4es/noop-audit/`。

- **机制**：`meowcore_GetProcAddress` 只按**裸名**查包装表 / `dlsym(libGLESv3.so)`，都不中即返回**空操作**（**永不 NULL**）⇒ 凡「没包装 + 裸名无 + 设备用 `…EXT` 后缀」的入口**静默失效、对 LWJGL 不可见**（本机 `libGLESv3.so` 把多批 core 名只导出为 `…EXT`）。
- **已修（2026-09-26，r11–r13，用户实机验证）**：`glBindAttribLocation`、`glMultiDrawElementsBaseVertex`（**这两条是「MC 1.20.6 + Fabric + Sodium 方块全透明」的真凶**）、`glBindFragDataLocation`。
- **在册（同类，当前不触发）**：`glBufferStorage`（被"不报 `ARB_buffer_storage`"挡住）、`glGetQueryObjectiv`/`i64v`（被 `ARB_timer_query` 门住）。**设计-实现偏差**：`glGetTexImage` 仍是纯 no-op（方案 §3.1 要求 FBO+`glReadPixels` 模拟 ⇒ 若被调用会**脏读**未初始化缓冲；是否真调用未证）。
- **参数层潜在项**：`glEnable/glDisable` **吞表之外**的桌面 cap 会透传 → `1280` → **MC ≥1.21.9 会主动 `glGetError` 抛异常**（当前 10 条表对已测版本够用）；`glGetIntegerv` 未 patch `GL_CONTEXT_PROFILE_MASK/FLAGS`；proxy `s_proxyW/H` 单槽串味；`glMapBuffer` 缺 `MAP_INVALIDATE_BUFFER`。
- **能力被报成"不存在"（性能类，非崩溃）**：`glGetStringi` 透传真 ES 扩展表、**零 ARB 合成** ⇒ mod 探测 `GL_ARB_*` 全为假 → 禁特性/走慢路径。
- **其它层**：GLFW overlay `glfwExtensionSupported` 恒 false、窗口 hint（MSAA/sRGB/depth-stencil）被丢、`glfwSetGamma`/vsync no-op（不影响渲染路径）。
- **设备专属 `…EXT` 入口（2026-09-27 登记）**：手机 OHOS GLES wrapper 会**静默吞掉**它不支持的 `…EXT` 调用（只记一条 E 日志，**不置 GL 错误**）⇒ 既不能用于核心路径、也**无法运行期探测**（`glGetError()` 恒 0）。已据此把 `glMultiDrawElementsBaseVertex` 改为 ES 3.2 core 循环（见 [`../20-design/render/GL33到GLES32-后端-方案.md`](../20-design/render/GL33到GLES32-后端-方案.md) §21）。**判据**：设备日志出现 `<name> is invalid` ⇒ 该 `…EXT` 入口在该设备被吞、勿依赖。
- **（在册·可诊断性缺口，2026-09-27）** `mc_glMultiDrawElementsBaseVertex`：core（`glDrawElementsBaseVertex`）与 `…EXT` 两个入口**都缺失**时会**静默返回**（裸名已登记 ⇒ 不触发 `mc_note_noop`）⇒ 无任何输出；同理 `mc_log_relevant_extensions()` 在"零命中"时不打行、无法区分"设备无相关扩展"与"诊断没跑"。修法（**未做**，用户决定只记录）：各加一条一次性 `fprintf`。

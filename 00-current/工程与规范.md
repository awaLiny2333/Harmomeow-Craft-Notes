## 一、工程配置

### 工程身份（脚手架参数）

工程位于 `Harmomeow-Craft-Launcher/`；工作区根下还有 `notes/`、`ref/`、`stuffs/` 与本工程并列。

| 参数 | 值 |
|------|-----|
| bundleName | `meow.liny.craft.awa` |
| App 名 label | `Harmomeow Craft`（品牌：**Harmomeow Craft Launcher**） |
| API Level | SDK target/compatible `6.1.0(23)`，modelVersion `6.1.0`（设备实为 API 26） |
| runtimeOS | HarmonyOS |

- 新增功能区块做成**平级组件**放 `components/`，`Index` 只负责组合。
- **命名规范**：持久化/数据操作工具类以 `XxxTools` 命名；纯函数扫描模块用 `XxxScanner`；全局共享状态用 `XxxState`；Picker 访问独立 `FileAccess`。
- `common/` 子目录按**职责**组织：`constants`（纯常量）/ `data`（数据持久化与扫描）/ `access`（系统访问能力）/ `state`（跨组件共享状态）。

### git 工作流

- **★ 提交信息一律用英文（铁律）**：标题 = `type(scope): subject`，**标题与正文都用英文**，`type` ∈ `feat` / `fix` / `perf` / `refactor` / `docs` / `chore`…；
  正文可长可短，但同用英文。**主仓与 notes 一致**（两个仓的既有历史都是英文标题）。
  - **教训（2026-09-28 用户明确）**：本节原先只写了"语义化风格"，没写语言 ⇒ agent 按"没规定"自行推断，连写 8 个中文标题提交（主仓 2 个已 push、notes 6 个），破坏既有约定后才被指出。
    标题语言**不要"看仓库里中文 commit 多不多"来猜** —— 本仓的规矩就是英文。
- 提交遵循语义化风格（`feat:` / `fix:` / `chore:` 等），**按功能点小步提交**。
- **任何 `git push` 和 `commit`（任何仓库 / 任何分支）都必须先让用户审核并明确批准**：先展示待推改动
  （`git diff` / `git log` / 文件清单），**用户明确说"可以 push / commit"后才执行**。
  （`--force` / `--force-with-lease` 属重写已发布历史，风险更高 ⇒ **必须单独说明并单独获批**。）

### 工作区与产物归档（铁律）

- **临时 / 调研 / 构建产物一律放工作区 `stuffs/`**，不用 `~/deveco/`（那个目录应该保持干净，特别告诫子 agents 一定也要保持干净）。
- **`stuffs/` 必须整洁有序**，按用途分子目录：
  - `stuffs/.minecraft/` / `stuffs/test-fabric/` / `stuffs/test-neoforge/`：用户游戏目录（**只读，不动**）。
  - `stuffs/backups/`：各个版本可以重复利用的东西，做 A/B 测试或者排除法 debug 的时候可能用到。用来装曾经检验过 / 确保一定程度上能用的东西，只是被新版本淘汰了。
  - `stuffs/research/<主题>/`：调研 / 构建临时产物（`jna` / `openal` / `jre` / `lwjgl` / `mc` / `misc`…），每区一个主题、配 `README.md`；新产物先归到对应主题目录，膨胀再细分。
- **notes 自身工具随文档走**：放 [`notes-tools/`](../notes-tools/README.md)，**不散在 `stuffs/` 根下**（它们服务文档，应随 notes 仓版本化）。
- **产物 ↔ notes 一一对应**：notes 引用产物用**工作区根相对路径 `stuffs/research/...`**；移动 / 改名要同步更新 notes + 记忆。
- **路径书写约定**（消除"同一仓两套基准"歧义）：
  - **notes 内部的相对路径一律相对本文件所在目录**（[`check_links.py`](../notes-tools/check_links.py) 与 [`notes_stalepaths.py`](../notes-tools/notes_stalepaths.py) 均按此解析、校验）。
  - **指向兄弟仓 / 工作区的路径必须带明确基准词**（`主仓 …`、`工作区根 stuffs/…`、`<workspace>/…`），**不得写成会被误读为"相对本文件"的裸相对路径**；确实不存在的路径显式标注"（现不在本机）"，**不假造路径**。
- 临时产物**应删**（非构建依赖），保留配方到 notes（适用于所有构建）或 `主仓` tools（适用于在 App 里用到的构建，比如 lwjgl 的自编），需要时按重建。
- **`tools/` 构建脚本对外只用工程内路径（铁律）**：**`tools/` 下不得引用 app 工程（主仓）之外的路径；基础构建脚本（"编某个组件"的那种）必须环境无关** —— 其外部输入（SDK / 源码树 / 输出目录）**一律由参数传入、无本机默认值**（默认输出只能是工程内或 `$TMPDIR` 之类环境无关的位置）。**环境绑定只允许出现在"我们对基础脚本的包装"里**（`tools/*/rebuild_for_meowcraft.sh`、`tools/jre*/` 这类本机配方），且须在文件头注明它是本机包装件、参数从哪来。
  **为什么**：基础脚本是给**别的开发者**复现用的 —— 一旦写死 `$HOME/devecow/...`、`/data/service/...`、`<workspace>/stuffs/...`、`ref/...` 这类本机 / 工程外路径，别人换台机器就编不动。把本机绑定收进 wrapper，才能"基础脚本可复用、本机一键跑"两全。

### 文档「引用完整性」

- **引用代码：符号名优先**（函数/类名不随重构失效）；**行号只作辅助并注明其基准**。
- **引用 commit / HEAD：SHA 必须 git 可证**（`git rev-parse` / `git show`），勿照抄记忆或旧文档里的 SHA；
  **基线 SHA 只能有一个「当前值」**（[`现状基线.md`](现状基线.md) 顶部），其余一律写「该文撰写时基线」。
- **数字必须带口径**（例："so 数"须写明范围：仅 `libs/arm64-v8a/` vs el1 全量——范围不同会被读成矛盾）。
- **实机结论必须能溯源**：写明是谁确认的；未单独验收的写「实现已核实、验收状态见现状基线」；拿不准就问项目拥有者，**不编造**。

### 文档「活状态单一事实源」

- **一句话纪律**：**现役档（设计 / 机制档）只写"现行事实与契约"** —— 不写"当年怎么改的、改了几轮"这类过程；
  **历史与过程一律进 `90-archive/`**；**活状态（会变的那一类：验证态 / 未决 / 在办 / 待办 / 进度 / 提交态）只写在下面 4 个「家」**，
  别处一律写**指针**（`状态见 现状基线.md §5 第 N 条`）。**事实变了就直接改写那一段**，不保留"原文 → 新文 / ★更新"这类补丁式痕迹。
- **不写变更痕迹与更新日期**：不写"某日更新 / 某日新增 / 某日改了什么"这类说明 —— **git 已记录**，写进正文只是噪声。
  结论溯源写"谁确认（实测 / 定案）+ 出处"即可；日期只在**区分多次实测**确有必要时保留。
- **不变量（定案事实、很少变：JRE 家族、现代 LWJGL 单代、命名对照、后端选型、支持窗口）可复述**：
  它们在现役档里**只能有一处权威表述**，其它地方一律**指针**指向它（不作多份各说一遍）。
- **活状态的唯 4 个「家」**（白名单，只有这 4 个文件可裸写活状态）：[`现状基线.md`](现状基线.md)（权威，§5 编号条目）、
  [`项目总览与新人上手.md`](项目总览与新人上手.md)（新人投影 §3）、[`已知限制与待解.md`](已知限制与待解.md)（未决/受限登记册）、
  [`../README.md`](../README.md)（极简投影）。
- **`20-design/` 与 `40-adaptation/` 是设计 / 机制 / 证据档，不复述活状态**：每篇顶部横幅标注。
  机器检查 = [`../notes-tools/notes_statusdup.py`](../notes-tools/notes_statusdup.py)（输出 `0` 才过）—— 这等于**"设计档不得含活状态词"的硬约束**（**有意如此**）。
  脚本会跳过"带日期的观测"行，但**现役档不再依赖这个豁免**：现役档应做到**零活状态词**；若某处确实必须提状态，**改写成指针**（"见 `00-current/…`"）。
- **历史只进 `90-archive/`**：归档档顶部允许**一行**"已归档（日期 + 为什么）"（那是对归档件本身的说明，不是给活话题打补丁）；正文里历史陈旧不影响现役检索（脚本对 `90-archive/**` 整体豁免）。

## 二、开发规范（编码铁律）

> 本规范来自项目拥有者的明确要求；写代码前必须遵守。

### 1. UI 极简

- 开发期间**不做任何额外样式、装饰、艺术设计**；用最朴素的内置组件，最高效率 + 最简代码。
- 不引入多余的字号变化：需要弱化次要信息（如完整路径）时用 `.opacity(0.x)`，不靠改字号做层级。
- 注释保持朴素：不用 `----` 之类装饰性格式化注释，简单单行注释即可。

### 2. 独立思考，官方文档优先

- 不照抄 `ref/`（只做参考），要有自己的设计思考。
- ArkTS/API 问题用 `devecocli docs search` 查官方文档，不翻 ref；**搜索关键词要少、精简**（太多会命不中）。

### 3. 验证策略

- **开发机 = 运行机 = 目标设备（同一台机器）**：当前 shell 所在即 hdc 连上的**鸿蒙 PC —— ARM `aarch64`、`KirinX90`、MateBook Fold（2in1）**（API 26 / OpenHarmony 7.0.0）。
- **★★ agent 的边界：可构建、可安装运行；不抓日志、不操作设备（铁律）**
  - **允许构建**：agent **可以**调用 `devecocli build`（含 `--modules entry meowjre meowjrelegacy`）产出 / 签名 HAP、HSP。
  - **允许安装与启动**：agent **可以**调用 `devecocli run`（装包 + 拉起 App），
    或在它不可用时用 `hdc app install -r` + `hdc shell aa start` 走**最小安装 / 启动**路径。
  - **使命终点 = 安装 / 启动完成**：到此为止；**不再往下做任何设备侧动作**，实机表现由拥有者观察并回报。
  - **不抓日志**：**不得主动**抓 `hilog` / `devecocli log`（及任何等价手段），不得把日志落盘 / 导出；
    需要日志时**请拥有者导出**。
  - **不操作设备**：不得代点（`uitest` / `uinput` / `snapshot_display` / 截图及任何等价手段）；
    不得 `force-stop` / `uninstall` / `bm uninstall` / 改系统参数 / 改设备设置 —— **只有"装 + 起"是允许的**。
  - **判据（一句话，用来裁边界）**：**这个动作是不是"把包装上去并启动"** —— 是 ⇒ 允许；不是（看日志、点界面、改设备状态）⇒ 归拥有者。
  - agent 的交付 = **代码改动 + 静态检查**（`check_ets_files` / `check_cpp_files`）+ **验收步骤**
    （怎么验 / 验什么 / 期望什么 / 失败时看哪行日志）；实机结果由拥有者回报。
- **除 app 包外，`tools/` 下的「自编件」构建脚本同样可跑**（本条不构成限制） —— 产物是**组件件 / 仓内文件**，不是 app 包。
  例：python 打包（`pack_jar.py`、`pack_extras.py`、`relocate_gson.py`、`meow-launcher/finalize_for_meowcraft.sh`）、
  CMake/ninja 交叉编 `.so`（`tools/*/rebuild_for_meowcraft.sh`、`build_lwjgl_*`、`build_libffi.sh`）、
  `lwjgl/install_natives.sh` 铺名与 manifest 维护。
  ⇒ **20-design / 40-adaptation 里「agent 可跑 / agent 可编」的记录依然成立**；
  主仓 `tools/README.md` 开头的同款约定（"native 与 python 打包 agent 可跑；javac 必须由人跑"）亦不变。
  - 附注（构建入口）：IDE 与 `devecocli` 是**两套 SDK**、且共用 `build/` 与 `.cxx/`
    ⇒ 两边交替构建会互相清产物、反复 reconfigure；**同一次改动尽量只用一条线**（本项目默认 `devecocli`）。
- **★★ 兼容铁律：目标是「与 HMCL 双向兼容」，不是「只读」（2026-09-29 用户明确）**
  - **目标**：HMCL 产出的游戏目录/数据我们**能用**；我们产出/写入的东西 HMCL **也认、也不受影响**
    （互操作验收 = *HMCL 装 → 我们启*、*我们装 → HMCL 可读*，即 [`Forge支持-改动方案.md`](../90-archive/Forge支持-改动方案.md) 的 C 档）。
  - **推论 ①（不破坏第三方状态；★2026-09-29 用户澄清「本意是**双向 HMCL 兼容**，不是"只读 / 绝不写游戏目录"」）**：
    **判据三条** —— ① HMCL 产出的实例我们**能用**；② 我们安装 / 产出的实例 **HMCL 也能玩**；③ **不得静默破坏或挪用**别的启动器 / 上游（Forge / MC）的文件。
    ⇒ **"写进游戏目录"本身不禁**：安装器写它**本应拥有**的文件（`versions/<id>/{<id>.json,<id>.jar}`、共享 `libraries/**`；**含装进用户已有的游戏目录**）可以；
    **安装期落一份"上游自己就认"的配置也在候选内**（先例候选 = FML 自己的 `config/splash.properties: enabled=false`，落**每实例**目录 / 相对 CWD —— 见 [`../20-design/launch/Forge-splash-崩溃根因与共享上下文修复.md`](../20-design/launch/Forge-splash-崩溃根因与共享上下文修复.md) §5.4）。
    **启动路径**仍**零写入**第三方文件（`versions/<id>/<id>.json`、`libraries/**`、`assets/**`、`launcher_profiles.json`；平铺 / 解压一律进应用沙箱 `cacheDir/mc-cp/<key>-<id>/`，见 `ClasspathStager.ets`）。
    - **保留的边界（仍禁止）**：**静默破坏 / 挪用第三方状态** —— 不改、不删、不重命名别的启动器 / 上游**拥有并读回**的文件；也**不**把我们**私有**的状态塞进它们会读的路径（我们自己的状态放"推论 ②"的 `.hmmcraft/`）。
    - **先例（作为「兼容性」教训，而非「禁止写游戏目录」）**：曾被删的"替用户关 Forge splash"策略（`tools/meow-launcher` 的 `MeowLauncher.java`）**写错了目录**（写 `GameDirs.game`，而 FML 读相对 CWD 的 `config/splash.properties`）⇒ **从未生效**；它还是从 Pojav 血统继承来的 ⇒ 删它是对的（**真问题**改在 shim 侧处理，见 [`已知限制与待解.md`](已知限制与待解.md) C11）。
    - **义务不变**：凡我们安装写出的东西，必须是 **HMCL 也认的格式**。
  - **推论 ②（我们自己的状态放自己的命名空间）**：新增状态落**点上目录**
    `<gameRoot>/versions/<id>/.hmmcraft/`（逐实例设置 + `logs/`），HMCL 不认识它也不受影响
    （用户 2026-09-29 定为现状口径；依据见 [`../20-design/launch/实例设置存储-方案.md`](../20-design/launch/实例设置存储-方案.md)）。
  - **推论 ③（共享语义照 HMCL 的口径写）**：凡与 HMCL **共享语义**的字段，一律用 HMCL 的表示法，不自创。
    现有先例：隔离不是裸布尔，而是 `overrideProperties` 含 `"runningDirectory"` 且
    `runningDirectory = "versions/<id>"`（键名是契约，勿改名）。
  - **推论 ④（适配只在我们这一侧）**：上游数据形态与假设不符时（loader 识别、classpath 形状、
    `--tweakClass` 顺序、旧版 OptiFine 的家族 jar、patches 形态…），改的是**我们的判据/常量/代码**。
    实例（2026-09-29，历史）：Forge + OptiFine 崩在 `NoClassDefFoundError: ITweaker` ⇒ 改我们自己的
    `LOADER_FAMILY_PATH_SEGMENTS` 补 `/optifine/`，**对游戏目录零改动**。（该常量**已随方案 A「`MeowLauncher`
    退役，2026-10-01」一并删除** —— 现 legacy 走 `ordered` 显式有序列表 + OptiFine 置末，「改我们这一侧」的原则不变。）
  - **明确不做**：任何"改上游件 / 改用户数据来适配我们"的方案（改写 forge jar、改 instance json、
    动 `libraries/`、替用户重排 `--tweakClass`…）。
- **`hdc` 操作手册（★ agent 只允许用它做「装 + 起」）**：**裸 `hdc` 直接可用**（`which hdc` → `/data/app/bin/hdc`，指向 `hdc_5.0.1`）；**不再需要** SDK 内那条 `toolchains/hdc`。
  - 查设备：`hdc list targets [-v]`；**hdc 侧显示名 = `localhost`**（真机名仍是 `HUAWEI MateBook Fold | ULTIMATE DESIGN`，见 `hdc shell param get const.product.name`）。
  - `list targets` 为空 ⇒ **手动连本地 TCP**：`hdc tconn 127.0.0.1:$(param get persist.hdc.port)`（当前 `40229`）。
    **端口真值 = 系统参数 `persist.hdc.port`（`persist.hdc.mode = tcp`），设备重启会变、勿写死**；默认 8710/5555 **连不上，勿盲试**。
  - 连上后 `hdc list targets -v` ⇒ `127.0.0.1:<port>  TCP  Connected  localhost`；指定设备用 `hdc -t 127.0.0.1:<port> <cmd>`。
  - 首次 `tconn` 可能打印 `[Fail]Connect failed` 但**实际已连上**（重连时提示 `Target is connected, repeat operation`）⇒ **以 `list targets` 为准**。
- **部署入口**：优先 `devecocli run`（必要时显式 `--device 127.0.0.1:<persist.hdc.port>`）；
  它不可用时走 §二 3.1 的 `hdc app install -r` + `aa start`。
  `devecocli device list` 曾报 `No active devices`（2026-09-28）⇒ **以实际 `run` 结果为准**，不据此禁用该入口；`devecocli build` 本就不依赖设备。
- **日志一律由拥有者导出**：需要日志时请拥有者操作后导出 `.logs`；需要点 UI 才能推进时，**明确告知点哪里**，然后等反馈。
- **禁止大范围查找（铁律）**：**严禁** `find` / `grep -r` 扫**整个工作区**、`ref/` / `stuffs/`、或**整仓 / 整模块目录**找字串
  （浪费时间且常被 kill / Signal 15）。**动手查找前必须先对"范围"心里有数**：已知在哪，就只去那一个地方
  （`read` 指定文件、`glob` 指定模式、`grep` 指定**最小目录 + `include`**）。确需跨多目录时**派子 agent 并行**，
  且给每个子 agent **明确的文件清单**——**禁止**在子 agent prompt 里写"全根搜 / 全工作区搜"。
  - **★ 2026-09-18 事故（用户严斥，写死）**：我为找一份探针日志，跑
    `grep -rl '<串>' --include='*.txt' stuffs/research/vulkan .`——**末尾那个裸 `.` 就是工作区根**，
    把 `ref/` 下十几个上游巨型仓库、**几百万文件**整片扫掉，进程被 **Signal 15** 杀死。
    用户原话：「不要全盘 grep……grep 我得等到明年。把这个狠狠记住。」
  - **★ 硬性自检（跑任何搜索前逐条过）**：① 命令里**不得出现**裸 `.`、`/`、工作区根、
    或任何**包含 `ref/` 的目录**作为搜索起点；② 起点必须是**最深的、已知有货的那个目录**；
    ③ 必须带 `--include`/`-g` 收窄文件类型——**注意：`--include` 只收窄"匹配"，不限制"遍历"**，
    决定遍历范围的是**起点路径**（本事故就是被 `--include='*.txt'` 骗了：遍历照样走遍 `ref/`）；
    ④ 若一时找不到**直接问用户要路径**，
    **不要扩大范围重试**（找不着就升级范围 = 本事故的成因）。
  - `ref/` 之下**只准 `read` 具体文件**（外层定位用 `glob` 精确模式）；**绝不在 `ref/` 内递归搜**。
- **`.logs/` 不是持久验证凭据**：用户不定期清理该目录 ⇒ 结论必须**落 notes**（写明"用户实测定案" + 具体版本号），不得以日志是否留存为准。
- 结构性 / 语法风险改动**先做** `check_ets_files` / `check_cpp_files` 静态检查；**构建 / 安装 / 启动 agent 可做**（见上「agent 的边界」条），**日志与实机行为验证归拥有者**。
- **部署顺序（铁律：3 个包）**：**有 3 个包上机** —— `meowjre` HSP（现代 JRE）+ **`meowjrelegacy` HSP（Java 8 / legacy 那一套）**（`meowcraftlib` / `meowlwjgls` 是 **HAR**，编译期静态并入，**不单独上机**）+ `entry` HAP。
  ⇒ **构建必须点名两个 HSP**：`devecocli build --modules entry meowjre meowjrelegacy`（漏掉 legacy 那个 ⇒ 设备上用不到 Java 8 那套）。
  **同版本重装 ⇒ 先 HSP 后 HAP；`versionCode` 递增 ⇒ 先 HAP（抬 app 版本）后 HSP**（否则 HSP 报 `9568284 install version not compatible`）。
  改任一 HSP 的 native / resource 后**必须把该 HSP 一起装**，否则设备上资源包过期；明细见 §二 3.1。
- **可复现 / 一致性断言必须自证（铁律）**：声称「逐字节一致 / 可复现 / 已验证 / 通过」前，必须**本次会话自己实跑**对应检查。
  可复现编译的标准做法：**≥2 次（建议 3 次）干净重建 + `cmp` 逐字节比对**（不要只比 sha256），并说明适用范围（同 tag / SDK / 构建路径）。
  **禁止凭「应该可以」下结论**。

#### 3.1 构建与安装（hdc 实测流程，2026-09-28）

**一次完整的 build + install**（下例全部本会话实测通过）

```sh
cd <workspace>/Harmomeow-Craft-Launcher
hdc list targets                                   # 空 ⇒ hdc tconn 127.0.0.1:$(param get persist.hdc.port)

devecocli build clean                              # 干净重建（实测 ~4 s）
devecocli build --modules entry meowjre meowjrelegacy   # ★必须带 --modules，否则只出 HAP、不出 HSP；★两个 HSP 都要点名（meowjrelegacy = Java 8 那套）

hdc shell "aa force-stop meow.liny.craft.awa"      # 先停：避免"装上了但跑的还是旧库"
hdc app install -r <meowjre hsp>                   # ①（现代 JRE）
hdc app install -r <meowjrelegacy hsp>             # ②（Java 8 / legacy JRE）
hdc app install -r <entry hap>                     # ③
hdc shell aa start -a EntryAbility -b meow.liny.craft.awa
```
- `-r` = 覆盖安装（保数据，不必先卸载）；HSP **不需要** `-s`（`-s` 是"跨应用 shared bundle"）。
- ArkTS warning（`NeoForgeInstaller` 未处理异常、`FileAccess` 需 `canIUse`）属既有噪声，**不是 error**。

**★ 用 IDE 构建的两个坑（2026-09-28 实测）**

1. **IDE 与 `devecocli` 是两套 SDK**：IDE 用 DevEco 内置的 `hmos-clt`（`/data/service/hnp/hmos-clt.org/hmos-clt_<ver>/sdk`），`devecocli` 用 `~/devecow/deveco_tools/sdk`。**两套头文件会不同步** ⇒ 改 native 后**两个入口都要编一遍**（实例：`hmos-clt` 的 `oh_input_manager.h` 删掉了 `OH_PixelmapNative` typedef，只 `devecocli` 编会漏掉该错误）。
2. **IDE 的 `--mode module -m entry@default assembleHap`（单模块构建）会 clean 掉全部 5 个模块的 build 产物，却只产出 entry HAP** ⇒ **`libs/meowjre/.../*.hsp` 会被删掉且不重建**（实测撞到）。⇒ **走 IDE 构建后，必须再跑一次多模块构建**（`devecocli build --modules entry meowjre meowjrelegacy`，或 IDE 里构建整个工程）才有 HSP 可部署；否则就是"新 HAP + 无/旧 HSP"。

**产物（3 个要上机）**

| 产物 | 路径（相对主仓） |
|---|---|
| entry HAP | `entry/build/default/outputs/default/entry-default-signed.hap` |
| meowjre HSP | `libs/meowjre/build/default/outputs/default/meowjre-default-signed.hsp` |
| meowjrelegacy HSP | `libs/meowjrelegacy/build/default/outputs/default/meowjrelegacy-default-signed.hsp` |

`meowcraftlib` / `meowlwjgls` 的类型是 **HAR**（`type: har`）⇒ 由**两个 HSP 的 `oh-package.json5` 都依赖**（`libs/meowjre/` 与 `libs/meowjrelegacy/`）、**编译期静态并入各自 HSP**，设备侧没有它们自己的包。

**★ 安装顺序取决于版本是否递增**（2026-09-28 实测，判据 = `9568284`）

| 场景 | 顺序 | 说明 |
|---|---|---|
| **同版本**重装（内容变了、`versionCode` 没变） | **先 HSP 后 HAP** | 两边版本相同 ⇒ 两种顺序都行（旧口径即此） |
| **`versionCode` 递增** | **先 HAP 后 HSP** | 先装 HSP 被拒：`error: failed to install bundle. code:9568284 error: install version not compatible` —— 新 HSP 的版本**高于设备上 app 已装版本** |

**验证**

```sh
hdc shell bm dump -n meow.liny.craft.awa | grep -E '"versionCode"|"versionName"' | tail -4
hdc shell bm dump -n meow.liny.craft.awa | grep '"packageName"' | sort -u   # 期望 entry + meowjre + meowjrelegacy
hdc shell ps -ef | grep meow.liny.craft.awa                                 # 进程在跑
```

**升版本号（实测：不必重新签名）**

- 版本号是**全工程单点**：只改 `AppScope/app.json5` 的 `versionCode` / `versionName`（HAP 与 HSP 的内嵌 `module.json` 都会带上它）；**不需要**动各模块 `oh-package.json5` 的 `version`。
- **签名材料与版本号无关**：`.p7b` profile 绑 **bundleName / appIdentifier / 设备**，不含 `versionCode` ⇒ 既有 `~/.ohos/config/default_*.{p12,cer,p7b}` 直接复用，**无需重新生成签名**；要在意的只是上面的**安装顺序**。

**清历史遗留的旧版号模块（如 `meowjre25` / `meowjre26`）**

```sh
hdc shell bm uninstall -n meow.liny.craft.awa -m meowjre25
```
- 这类 HSP 是**挂在 app bundle 内的模块**（`moduleType: 3`，`/data/app/el1/bundle/public/<bundle>/meowjre25.hsp`），**不是独立 bundle** ⇒ `hdc uninstall meowjre25` 报 `failed to get information`，**必须用 `bm uninstall -m`**。
- **卸载模块会杀掉 app 进程** ⇒ 之后要重新 `aa start`。
- 该目录 `hdc shell` 读不到（uid 2000，Permission denied）⇒ 残留文件是否真删除**无法从 agent 侧证实**，只能以系统登记为准。

**改动类型 → 叠加动作**

| 改了什么 | 额外动作 |
|---|---|
| `libs/**/*.so`（**增 / 删 / 改**） | hvigor **不追踪 libs 增删** ⇒ 先清模块 build（`devecocli build clean`，或 `rm -rf libs/{meowlwjgls,meowjre,meowjrelegacy,meowcraftlib}/build entry/build`）再 build；否则 HSP 不重打、设备报 `... not found` |
| **组件库 `.so`（gl4es / lwjgl）换件** ⚠️ 已被咬 3 次 | ① 同一份件在 `meowjre` **与** `meowjrelegacy` **两个 HSP 里各有一份副本** ⇒ **必须同步**；② `build clean` 后 `devecocli build --modules entry meowjre meowjrelegacy`，并**把两个 HSP + HAP 都装上**；③ **判据不能只看文件/`strings`** —— 看**运行期自证行**（gl4es：`[meow-gl4es] build=<tag> …`；lwjgl：`shared ctx created: …`）。反例：雾的 E1 那轮日志里 `forced` 一次都没出现 ⇒ 跑的是旧件、整轮结论作废 |
| 随包 jar（`lwjgl-<gen>.jar` / `asm9/*`）/ `meowcraft_extras.tar.gz` 内容 | **人跑打包脚本**（沙箱无 JVM）→ 重打 tar → **升 `EXTRAS_VERSION`**（`launcher.jar`/`gson-for-launcher.jar` 已于 2026-10-01 随方案 A 退役，不再打） |
| 随包 JRE 数据（模块集 / `lib/patch/jdk.zipfs` / 文件） | 重打 `meow_jre.tar.gz` → **升 `JRE_DATA_TOKEN`**（native + ArkTS 两处同值） |
| 只换 JRE 的 el1 `.so`（数据没变） | 令牌**不动** |
| native 桥源码（`meowcraftlib` 的 cpp） | 正常 build 即可；自证 HSP 真重打：`unzip -l <hsp> \| grep <so>` |

### 4. 状态管理：只用 V2

- 页面/组件：`@Entry` + `@ComponentV2`；组件内部状态：`@Local`；数据模型：`@ObservedV2` class + `@Trace` 属性。
- **禁止 V1 装饰器**（`@Component` / `@State` / `@Prop` / `@ObjectLink` / `@Observed`）。
- ArkTS 不支持确定赋值断言（`!:`），需要非空字段时用 `field: T | null` + 惰性 getter。

### 5. 循环渲染：只用 Repeat

```ets
Repeat<T>(this.arr)
  .each((obj: RepeatItem<T>) => { /* 只写组件语法 */ })
  .key((item: T) => item.xxx)   // 稳定唯一键
```

- **禁止 ForEach 系列**；`.each` 内**禁止声明 `const` 中间变量**（"Only UI component syntax"），直接用 `obj.item.xxx`。
- `@Trace` 属性变化可精确刷新单项，key 用稳定唯一键即可（如 uri），无需拼可变字段。

### 6. 常量集中，禁止 magic

- 有含义的常量统一放 `common/constants/Constants.ets`，按分类注释组织：日志（`LOG_DOMAIN` / `LOG_TAG`）、路由（`ROUTE_INDEX`）、
  布局（`LAYOUT_SPACE` / `LAYOUT_SPACE_SMALL` / `LAYOUT_PADDING` / `OPACITY_SECONDARY`）、设置存储。
- **设置存储位置**：**应用级**（目录枚举 + 账户 + 全局设置 + 触控）存应用沙箱
  `<filesDir>/meow-settings/{app-settings,accounts,touch-controls}.json`
  （`app-settings.json` 含 `dirs` / `selectedDir` / `selectedAccount` / `global` 段；`touch-controls.json` 装**触控 8 项**：
  `touchAsMouse` / `touchControls` / `touchSensitivity` / `touchControlsScale` / `insetTop` / `insetRight` / `insetBottom` / `insetLeft`，
  扁平 + `format:1`、写回保留未知字段、文件不存在写一份默认、解析失败先备份 `.bad` 再用默认）；**逐版本**设置存各实例目录内
  `<gameRoot>/versions/<id>/.hmmcraft/instance-settings.json`；**不使用 Preferences**（相关常量已删）。
  见 [`../20-design/launch/实例设置存储-方案.md`](../20-design/launch/实例设置存储-方案.md) §3。
- 禁止在业务代码散落 magic string / magic number。

### 7. UI 字符串走 resource

- 静态 UI 文案一律放 `entry/src/main/resources/base/element/string.json`，代码中用 `$r('app.string.xxx')` 引用
  （Button / Text / Select.value / SelectOption.value 均支持）。
- **禁止任何 UI 文案 magic string**（含 placeholder、Toast、标题等）；带参数用 `$r('app.string.xxx', arg)`（`%d` / `%s` 占位）。
- **输入框 placeholder 显示"解析后的实际值"**：自动值可确定时（如本机核数）直接显示该值，不写"自动（N）"；只有不可确定的自动值（如 JVM 默认堆）才用 resource 的"自动"。
- 动态数据（用户昵称、URI）保持运行时字符串。
- **展示文本一律 resource**：逻辑层（如 Tools / Policy）**不得写死展示文本**，可用 `$r(...)` 构造 `ResourceStr` 返回
  （`$r` 是**构建期**解析成资源对象，放在非组件函数里安全）。
- **日志用独立、不本地化**的稳定诊断串（英文 / 机器可读标识，便于 grep）：同一份理由同时供 UI 与日志用时，
  拆成两份 —— UI 用 `ResourceStr`（`$r` 构造）+ 日志用稳定串（如 `reasonDiag: string`）；**不要**把 `$r` 资源塞进日志。
  （此条**覆盖**旧的"纯逻辑文件不允许碰 `$r`"口径 —— 用户 2026-09-29 指示。）

### 8. TextInput 必须做 .onSubmit

- 每个 TextInput 在 `.onChange` 之外**必须加 `.onSubmit()`**，让键盘回车触发确认逻辑（无 onSubmit 时回车无反应，用户困惑）。

```ets
TextInput({ text: this.editingName })
  .onChange((v: string) => this.editingName = v)
  .onSubmit(() => this.confirmEdit())
```

### 9. 输入 / 窗口约定

### 10. 研究与重实现：用子 agent 并行（省主上下文）

- **重调研 / 重实现（多轮取证、通读大文件、逐项核对、跨多文档施工）一律优先派子 agent**，
  主会话只做**派活 / 裁决 / 综合**（2026-09-18 用户明确要求：这样可以节约主上下文）。
- 大范围调研、跨多文档同步、机械性全库核对：**并行派多个子 agent**（Task 工具，`general`），各自负责一组**互不重叠**的文件；
  主会话只保留其**紧凑结论**（每文件 1–2 行），避免把长文档内容灌进主对话。
- 主会话职责：① 先钉死**权威事实表**（唯一事实源口径）；② 按文件集**互斥分派**；③ 最后统一做**一致性校验**
  （`python3 notes-tools/check_links.py .`）与提交。
- 子 agent 同样受本规范约束：**先读后改、禁臆造**、只改过时内容、**不跑 `git commit`**；结论**先落** [`现状基线.md`](现状基线.md)，再回写其余文档。
- **派活 prompt 的必备四件套**（缺一即易跑偏）：① **互斥的文件清单 / 精确起始目录**（禁"全根搜"）；
  ② 本规范的**相关摘录**（尤其禁止大范围查找、临时件放 `stuffs/`、禁设备/UI/日志）；
  ③ **交付物落盘路径**（报告写成 `stuffs/research/<主题>/…` 或 `notes/…`）；
  ④ **最终回复的字数上限**（如 ≤18 行），并列出"查不到就写未查到"。
- **★ 路径必须是绝对路径（2026-09-18 两次事故，写死）**：`stuffs/` 是**工作区根**（`<workspace>/stuffs/`）的平行目录，
  **不是主仓的子目录** ✓。我的命令与**派活 prompt** 里凡写**相对** `stuffs/...`，子 agent 的 cwd 常是主仓 ⇒ 就会在
  **主仓下长出 `Harmomeow-Craft-Launcher/stuffs/`** ✗（污染产品仓 `git status`，用户两次严斥）。
  ⇒ **一律给绝对路径**：命令里用 `$WS/stuffs/...`（`WS` = 工作区根 ✓）；**prompt 里直接贴完整绝对路径**，
  并加一句「**临时产物只放这个绝对路径下的 `stuffs/`，绝不在任何仓库目录内创建 `stuffs/`**」✓。
  ⇒ **每次派活后自查**：`git -C 主仓 status --short` 出现 `?? stuffs/` ⇒ 立刻按"先校验再并、再删空树"清理 ✓。

# 26.x 渲染栈差异（相对 ≤1.21；glthread 崩溃的候选放大器）

> 日期：2026-09-13 ｜ 只读调研（版本 json + jar 条目对比，未反编译）
> 素材：`stuffs/test-fabric/versions/{1.18.2,1.20.6,1.21.10,26.2-Fabric}/` 的 version json 与客户端 jar
> 结论定位：**当初判断「崩溃与 MC 版本无关」**（老版本在 `GALLIUM_THREAD=1` 下同样崩）——**后经修正：致命崩溃为 26.x 特有**（老版本只出良性噪声、进程不死，见 [`../perf/性能实验台与glthread-结论.md`](../perf/性能实验台与glthread-结论.md) §2.2）。本页记录 26.x 的渲染重写，解释**为何 26.x 更易触发**（放大器），而非先决条件。
> 本文为决策记录 / 证据存档，**不复述现状**；当前状态见 [现状基线.md §5 第 16 条](../../00-current/现状基线.md)。

## 3. 候选放大器（按证据强度；非"就是它"）

1. **持久映射缓冲 + 多缓冲轮转**（`GlTransientMemory$PersistentMapping$Rotation`）——glthread 下缓冲生命周期/轮转错位 ↔ 观测到的"`libgallium` 读已 munmap 缓冲"。
2. **`BufferStorage`（不可变缓冲）+ DSA**——glthread 异步入队与 Zink 模拟层的 buffer 指针生命周期冲突 → 越界/踩 guard。
3. **`GlFence` 跨线程等待**——glthread 下同步本就敏感（`egl_drop_surface` 前需 `glFinish` drain）。
4. **`GlCommandEncoder`+帧图+`TransientMemory`** 的延后执行/回收——"缓冲已回收仍被读"。
5. **管线/着色器预编译量激增**（`GlDevice$ShaderCompilationKey`/`GlProgram`/`RenderPipelines`）——加载屏正是驱动 `Create/Get pipeline cache` 密集期，放大 glthread×Zink 竞态窗口。
6. **Vulkan LWJGL 模块被加载/探测**（`lwjgl-vulkan/shaderc/spvc/vma` + `NativeLibrariesBootstrap` 强载）——间接因素。

## 4. 研究进展：26.x 实际用到的 GL 特性（`unzip -p <jar> <class> | strings | grep 'gl[A-Z]'`）

26.2 的 GL 后端**大量使用"现代"GL 特性**（旧版 `GlStateManager` 路径不用）：

| 类 | 关键 GL 调用 |
|---|---|
| `opengl/GlTransientMemory$PersistentMapping` | **`glBufferStorage`**（不可变）+ **`glMapBufferRange`**（持久映射）+ **`glDeleteBuffers`**（轮转回收）+ **`glFinish`**；`$Rotation` 做 N 缓冲轮转 |
| `opengl/GlTransientMemory$Fallback` | `glBindBuffer` + `glMapBufferRange` + `glUnmapBuffer`（每帧 map/unmap） |
| `opengl/DirectStateAccess$Core` | DSA：`glCreateBuffers`/`glNamedBufferStorage`/`glNamedBufferSubData`/`glMapNamedBufferRange`/`glFlushMappedNamedBufferRange`/`glCopyNamedBufferSubData`/`glBlitNamedFramebuffer`… |
| `opengl/DirectStateAccess$Emulated` | 绑定式（`glGenBuffers`/`glBufferData`/`glBufferStorage`/`glMapBufferRange`/`glUnmapBuffer`…） |
| `opengl/GlCommandEncoder` | **fence**（`glFenceSync`/`glClientWaitSync`/`glDeleteSync`）、**多次间接绘制**（`glMultiDraw*Indirect`）、`glTexBuffer`… |
| `opengl/GlBuffer$Direct` | `glDeleteBuffers` |

**选路是"按扩展能力"的**（`GlDevice` strings 实测）——检查 `GL_ARB_buffer_storage` / `GL_ARB_direct_state_access` / `GL_ARB_multi_draw_indirect` / `GL_ARB_draw_indirect` / `GL_ARB_base_instance` / `GL_ARB_vertex_attrib_binding` / `GL_ARB_clip_control` / `GL_ARB_debug_output`，再决定用 `BufferStorage{Immutable,Mutable}`、`DirectStateAccess{Core,Emulated}`、`GlTransientMemory{PersistentMapping,Fallback}`。

**假设（候选）**：本机系统 GL 为 **Zink（Mesa 25.0.1）上报 GL 4.2 core + 大量 ARB 扩展** → 26.x 很可能走 **`glBufferStorage`（不可变/可能持久映射）+ `GlFence` + 多次间接绘制** 这条现代路径；而 **Mesa glthread + Zink 对这套路径的内存生命周期管理**在加载末期（管线/瞬时缓冲轮转密集）出现 **UAF** → `libgallium → memcpy` 读已释放/未映射缓冲（对齐 `MEOW_BT` 现场）。旧版本用 `GlStateManager` 老路径 → 不触发。

**可测的规避假设（零重编，实验台）**：用 **`MESA_EXTENSION_OVERRIDE`**（libgallium 实测存在）**反向隐藏**这些扩展，逼 26.x 走 `Mutable`/`Fallback`/`Emulated` 路径：

```
GALLIUM_THREAD=1
MESA_EXTENSION_OVERRIDE=-GL_ARB_buffer_storage
```
（再逐步加 `-GL_ARB_direct_state_access` / `-GL_ARB_multi_draw_indirect` / `-GL_ARB_draw_indirect` / `-GL_ARB_base_instance`。）
- **不崩** → 既确认触发点（不可变/持久缓冲路径），又是一条**可用规避**（代价：MC 回退到 `glBufferData`/map-unmap，CPU 略高）；
- **仍崩** → 排除该组特性，转 fence/多绘/其它。

> 用户观察：**26.x 崩溃绝大多数在"加载末期"**——与"渲染后端初始化/首帧管线与瞬时缓冲开始轮转"的时机吻合。

### 4.1 验证结果（2026-09-13/14，`MEOW_GLINFO=1` 实测）

`GL_VERSION=4.2 (Core Profile) Mesa 25.0.1 (git-69e48f9182)`，`zink Vulkan 1.2(Maleoon 916)`，**211 扩展**；26.x 门控的那些扩展**默认全在**（`GL_ARB_buffer_storage/direct_state_access/multi_draw_indirect/draw_indirect/base_instance/vertex_attrib_binding/clip_control/shader_draw_parameters/debug_output` 全 `YES`）。

| 轮 | env | `num_extensions` | `GL_ARB_buffer_storage` | 崩溃 |
|---|---|---|---|---|
| A | `MEOW_GLINFO=1` | 211 | YES | 否 |
| B | + `MESA_EXTENSION_OVERRIDE=-GL_ARB_buffer_storage` | **210** | **no** | **是** |

⇒ ① **`MESA_EXTENSION_OVERRIDE` 确认有效**（扩展数 −1、该扩展消失）——是**可靠的定向关扩展手段**；② **但隐藏 `GL_ARB_buffer_storage` 会把 MC 打崩**（不是 glthread 的崩溃）：MC 原生崩溃报告 `stuffs/test-fabric/crash-reports/crash-*-client.txt` 显示——
```
Description: Initializing game
java.lang.IllegalStateException: Failed to map buffer
  at GlBuffer$Direct.map(GlBuffer.java:126)                    ← glMapNamedBufferRange
  at BufferStorage$Immutable.createBuffer(BufferStorage.java:46)
  at GlDevice.createBuffer → MappableRingBuffer → DynamicUniformStorage → DynamicUniforms
  at RenderSystem.initRenderer(RenderSystem.java:169)          ← 渲染器初始化
GL debug: 'GL_INVALID_VALUE in glMapNamedBufferRange(access has undefined bits set)'
Features: DeviceFeatures[... persistentMapping=true ...]
```
即 **MC 的 `$Immutable` 持久映射路径仍被选中**（其 `DeviceFeatures.persistentMapping=true` 没随 override 变），而驱动已关该扩展 → access 位被判非法 → 建 buffer 失败 → **MC 自我崩溃**。**MC 不优雅回退**。
⇒ **结论修正**：用 `MESA_EXTENSION_OVERRIDE` 隐藏这些扩展**无法二分 glthread 触发点**（会把 MC 打崩，且该崩溃**与 glthread 无关**——那几次都没开 `GALLIUM_THREAD`）；早先"buffer_storage 不是触发点"**作废**。**这是死胡同**。

> **新诊断资产**：MC 原生崩溃报告落在 `<gameDir>/crash-reports/crash-*-client.txt`（含渲染调用栈、`DeviceFeatures`、GL 扩展/`GL debug messages`、oshi 系统信息）——以后排查 26.x 渲染问题优先看它。

**补充（2026-09-14，run1/run2）**：
- **run1**（`MEOW_BT=1`+`GALLIUM_THREAD=1`，无 override）→ 原生崩；dumper v3 的 `KEY` 行给出 `libgallium-25.0.1.so` 基址 **`0x5b99200000`** → 致命帧 = **`libgallium+0xE26CC4`**（`0xe26cc0 bl memcpy@plt`；`src=caller arg(x5)`、`n=0x4df0`、**Render 线程**、src 悬空）。详见 [`../perf/glthread崩溃-Bug报告.md`](../perf/glthread崩溃-Bug报告.md) §C。
- **run2**（藏 `GL_ARB_direct_state_access`）：**无** glthread 时 MC 正常跑（走 `$Emulated`）；**带 glthread 仍原生崩** ⇒ **DSA 路径不是触发点**。
- ⇒ **"藏扩展"两条路都堵**（buffer_storage → 崩 MC；DSA → 无效）。

## 5. 改行为的可行性：B（应用侧 GL 转发层）/ C（自编 Mesa）

> 2026-09-14 两个只读 agent 调研结论（要点）。前提：崩链 = `glTexSubImage2D → … → tc_texture_subdata(glthread) → zink_buffer_subdata`，memcpy 读**已释放源指针**。

### B：应用侧包一层（给 GL 入口补"同步拷贝"）
- **拦截点确定存在**：LWJGL 从 `-Dorg.lwjgl.opengl.libname` 指定的库解析 GL 函数（主路径 = 该库的 `glXGetProcAddress`/`eglGetProcAddress`；次路径 = 对该句柄 `dlsym`）⇒ **把 `libname` 指向自造 forwarder**（导出 `glXGetProcAddress`/`eglGetProcAddress`，只劫持少数名字、其余转发）**可行**；或改我们 **overlay 的 `GLCapabilities`** 槽位（`glTexSubImage2D`=3.4.3 槽 307）**可行**。靠 `RTLD_GLOBAL` 插桩**不可行**。
- **关键不确定（决定 B 有没有用）**：悬空源指针**是 MC 的客户端指针，还是 Mesa TC 自己的 staging**？若是后者，在 GL 入口拷贝也救不了。
- **其余风险**：要保证 wrapper 的 staging 生命周期正确（否则同款 UAF 复现）；覆盖面 = 所有"客户端内存入口"（纹理/缓冲/绘制/顶点/ReadPixels/ShaderSource…），逼近重写一层转发（2270 槽、按世代维护）。
- **工作量**：最小集约 **中**；全覆盖 **大**。**是补偿性 workaround，不是根因修复**。

### C：自编 Mesa 替换系统 GL 链
- **工具链基本齐**：clang/cmake/ninja/sysroot 在；sysroot 有 `vulkan/`(含 `vulkan_ohos.h`)/`EGL/`/`GL/`/`zlib`。**缺**：**meson**、python **mako/ply**、**expat**、**libdrm**（Mesa 25 用 **Meson**，非 CMake）。
- **分水岭（P2）**：**上游 Mesa 无 OHOS 平台后端**（无 `EGL_PLATFORM_OHOS_KHR`/`VK_OHOS_surface` 的 Mesa 侧 glue，Huawei 私补）⇒ 需自行移植，**数周级不确定**。
- **集成不能赌同名遮蔽系统库**（命名空间硬、DT_NEEDED/RUNPATH 解析、EGL↔gallium 版本配对）：应**自有命名 + 绝对路径 + 重建 bridge 改运行期 dlopen 自有 EGL**。
- **更省的一档（C′）**：只自编 **`libgallium`**（同版本+补丁，保留系统 `libEGL_mesa`（Huawei WSI））——**可能绕开 OHOS 后端移植**；但仍要解决"让系统 `libEGL_mesa` 加载我们的 `libgallium`"（命名空间/SONAME/ABI 配对）。
- **工作量**：P1 打通（Meson/依赖裁剪/headless zink）**数天**；P2 窗口后端 **数周级**；C′ 视集成而定。

### 下一步的判别动作 —— **已做，结论决定性**

反汇编 `tc_texture_subdata`（`0xCCEA10`，符号来自 `.gnu_debugdata`）：

```
0xCCEA50  mov x25, x5              ; x25 = 本函数 data 入参（caller 的客户端像素指针）
...
0xCCEDB8  mov x5, x25              ; 直接把【客户端指针】当 src
0xCCEDBC  blr x8   ([pipe+928])    ; → 驱动的 buffer_subdata = zink_buffer_subdata（bt#0=0xCCEDC0 ✓）
```

⇒ **`tc_texture_subdata` 把客户端像素指针"原样转发"给驱动、自己不做同步拷贝**；崩溃在 **Render 线程**（app 线程触发的 TC flush）⇒ **glthread 把贴图上传延后，flush 时才去读 MC 已释放的客户端缓冲**。**这正是"glthread 未在入口拷贝客户端数据"的缺陷**：
- **B 路可行**：在 GL 入口（`glTexSubImage2D` 等）**同步拷贝客户端数据**即可挡住（拷贝时指针还有效）——但必须让这份 staging **存活到 TC 消费完**（fence/池化回收），否则同款 UAF 复现。
- **C 路（改 Mesa）是根治位**：在 `tc_texture_subdata` 内同步拷贝。

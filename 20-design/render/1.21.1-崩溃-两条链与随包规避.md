# 1.21.1 崩溃：两条独立链 + 随包规避（2026-09-16 定案）

> 结论摘要见 [`../../00-current/现状基线.md`](../../00-current/现状基线.md) 第 23 条。
> 原始物证（hs_err / 抓栈转储 / 凶手 SPIR-V / MC 日志）见 `stuffs/research/1.21.1-crash-2026-09-16/`。
> 适用面：1.21.1 + NeoForge + Create（内含 Flywheel），OHOS + Mesa/Zink + Maleoon。

## 0. TL;DR —— 两件互不相干的事

| 链 | 触发条件 | 现象 | 处置 |
|---|---|---|---|
| **A** 厂商 GPU 着色器编译器 | Flywheel 走 **INDIRECT**（compute 剔除）后端 | `libbishenggpucompiler_v210.so.15` 内 NULL 解引用（`addr=0x0`，由 Zink→`vulkan.hvgr_v210.so` 调用）| `config/flywheel-client.toml`: `backend = "flywheel:instancing"` |
| **B** JVM C 堆被**某 native 越界写**坏 | **写者仍未识别**（曾归因的"Flywheel 光照 18³ 越界"已经字节码核验排除，见 §2）| SymbolTable 被写坏：或 `addr=0x5d00000008`（HeapBase+8）SIGSEGV，或 JVM 自报 `Cannot resize table: Node hash code has changed` | **随包**给 `os::malloc` 加尾部富余（默认全尺寸 4096 B）——**布局掩盖**，完整性未证 |

**为什么容易搞混**：两者都表现为"进世界/加载期崩"，且都在同一台机器上；但 A 只在 compute 路径出现，B 撤掉富余就复发。**必须分开做单变量**（本文各节末尾就是各自的判据）。

## 1. 链 A：厂商 GPU 着色器编译器崩（NULL / 无效地址解引用）

### 证据（**4 次**复现，每次都是会话**最后一条** fault）
| # | addr | pc / lr（全部在 `libbishenggpucompiler_v210.so.15`）| 线程 |
|---|---|---|---|
| 1 | `0x0` | `+0x84d94c`（pc）/ lr `+0x84d91c` | `meow.lin:zcfq0`（Zink 异步编译队列）|
| 2 | `0x0` | `+0xc2970` / lr `+0xb9618` | `meow.lin:zcfq1` |
| 3 | `0x0` | `+0xc2970` / lr `+0xb9618` | `meow.lin:zcfq1` |
| 4 | **`0xffffffffffffffff`** | `+0x1262ec` / lr `+0x120da4`（`bt#0..#16` 全在该库内，`bt#17..#19` → `vulkan.hvgr_v210.so`）| **Render thread** |
- 线程名 `meow.lin:zcfqN` 的 `zcfq` 是 `libgallium` 里的字面量 ⇒ 那是 **Zink 的 `gfx_compile_queue` 异步管线编译线程**。
- 同一会话更早的 fault 多为**良性**：`0x8/0xc/0x14`（正常 Java NPE）、`0x5b8a2b8000`（safepoint 轮询页）、
  退出瞬间 `VM Thread` SIGABRT（收尾噪声）。判读要点见 `ohos_meowbt_dump_reading_pitfalls`。
- 另有**一次全静默猝死**（同配置：无 fault、无 hs_err、无 cppcrash、launcher 仍存活）⇒ 同族崩溃也会发生在
  **驱动内部线程**上（该类线程若屏蔽 SIGSEGV ⇒ 我们与 DFX 都看不到）⇒ **上报时两种显形都要写**。
- **凶手着色器**：`ZINK_DEBUG=spirv` 取回一次运行的 38 个 dump，`dump00–33` 是 17 组 Vertex/Fragment（正常），
  **`dump34–37` 是仅有的 4 个 `GLCompute`**，与 Flywheel 源码逐条对上：
  `cull.glsl`(local 32) / `scatter.glsl` / `downsample_first.glsl`(256) / **`downsample_second.glsl`(256, 4×barrier, mip_0..mip_6)** ← 崩前最后一个。
  ⚠️ 判别特征是「GLCompute」本身，**不是** Vulkan memory model（38 个 dump 全带 `VulkanMemoryModel` 能力，Zink 对该驱动的默认）。

### 规避原理 / 已实测排除的杠杆
`Backends.INDIRECT`（compute 剔除）priority **1000**，`Backends.INSTANCING`（classic，**全程不用 compute**）priority 500
⇒ `"DEFAULT"` 必然选中 INDIRECT。配置值是**资源位置**：`backend = "flywheel:instancing"`（`"DEFAULT"` 是特殊字符串）。
代价：失去 GPU 剔除、性能略降（Flywheel 自己在 Intel 上也是这个降级）。

### ★★2026-09-16 第二轮收官：**通用能力屏蔽接口** + **版本组诚实化**（实机 4/4 判据通过）

**(1) 为什么前三次拦截全无效**（已实测穷尽，别再试）：

  `glDispatchCompute`（`libgallium-25.0.1` 里该符号在 ✓）。
- 真正让 Flywheel 走 INDIRECT 的是 `GlCompat.isIndirectSupported()` 的**版本组直通**：

**(2) 修复：两层，职责分离** ✓

- **策略层（我们对这台设备的声明）**：**通用能力屏蔽接口** —— **一份清单（数据）→ 两个执行点**：

**(5) ★第三轮：版本组不能只靠"扩展表"，要读真实 `GL_VERSION`**（2026-09-16 实机 ✓；叙述经同日独立复核订正）
- 复原守卫后发现**反向不准** ✗。**准确机制**（复核时读 `ref/lwjgl3` 源码后确认）：LWJGL **自己**会往 ext 里加
  **当前版本**那一个名字 —— `GL.createCapabilities` 执行 `supportedExtensions.add("OpenGL" + major + minor)`
  （取自 `GL_MAJOR_VERSION`/`GL_MINOR_VERSION`）⇒ 本机 4.2 上下文里该家族**只有 `OpenGL42`** ⇒ 上游守卫让
  `OpenGL43..46` 为假（**正确** ✓ —— 这正是 `OpenGL46` 捷径死掉的原因）但**也让 `OpenGL11..41` 为假** ✗
  （低报：它们本来就该是支持的）；而当年删光 234 处守卫是另一个极端（高报 4.6 ✗）。
  ⚠️ 我最初的叙述"Mesa **从不公布** `OpenGLxx` 伪扩展名"**并不准确** ✗（Mesa 里确实没有这些字符串 ✓，但
  `OpenGLxx` 是 **LWJGL 自己合成**的 ✓）—— **结论不变**（要读真值），措辞已按复核更正 ✓。
- ⇒ **两个极端都不对**：删守卫 = **高报**（4.2 谎报成 4.6，Flywheel 因此走 compute ⇒ 撞驱动 bug ✗）；
  恢复守卫 = **低报**（连 4.2 都不报 ✗）。**真值只能来自上下文的 `GL_VERSION`** ✓。
- ⇒ **正解**：`RendererInit.allowsVersionGroup(ext, maj, min)` = `ext.contains("OpenGL<maj><min>")`
  **或** `atLeastVersion(maj, min)`；版本号在 caps 构造期用 **LWJGL 自带 API** 读：
  `provider.getFunctionAddress("glGetString")` + `JNI.invokeP(0x1F02, addr)` + `memASCII(ptr, 64)`（有界读）
  ⇒ **纯 Java、零 native 改动** ✓。扩展仍按上游契约（公布名 + 入口可解析）✓。
- **自证**：`RendererInit: GL_VERSION=[4.2 …]` + `RendererInit: groups 4.2; OpenGL11..OpenGL42 on, higher off` ✓
  （该行最初**整段丢失**，根因与修法见下面的 (6)）。
- **gl4es 路径**（`strict=OFF`）仍按"入口可解析"判定：它自报版本低而更高入口可用 ⇒ 需要宽容 ✓（保持既有行为 ✓）。

**(6) ★日志被截断的根因：不在平台，在"我们自己把含 NUL 的串当 C 串传"**（2026-09-16，实测 ✓）
- **现象**：`RendererInit: GL_VERSION=[…] -> 4.2; …` 在 hilog 里只有 **90 字节**、恰好停在 Mesa 字符串结尾
  ⇒ 在整份捕获里搜尾部特征串（`-> 4.2` / `higher off` / `OpenGL11..OpenGL42`）= **0 次** ⇒ 尾部**从未被记录**
  （**不是**导出/采集截断 ✗）。
- **先排除平台**（按纪律查文档）：hilog **单条上限 4096 字节**（`faqs-performance-analysis-kit-58`），且
  **超限机制是整条丢弃**、不是截断 ⇒ 85 字节的截断**不是它** ✗。
- **真因**：`MemoryUtil.memASCII(addr, len)` 的语义是 "**decode `length` BYTES**" ⇒ 它把 **NUL 终止符及其后
  的字节**一起解进 Java 串 ✗；我们的转发器又把整行作为 `%s` 参数交给 `OH_LOG_Print` ⇒ **C 串在那个 NUL 处
  结束**，其后内容（含我们自己的派生信息）**静默消失** ✗。
- **修法（两层，都在该在的层）**：
  ① **Java**：解出的串**截到首个 NUL** ✓ + 自证拆成**短行** + 打 `len=` 便于核对；
  ② **转发器**（`meowjrebridge.cpp`）：上抛前**清洗控制符**（NUL→空格，绝不吞后续 ✓）+ **按 1024 字节分段**
     （远低于 hilog 的 4096 上限 ✓）。
- **验收**：`GL_VERSION len=47`（= Mesa 串精确长度 ⇒ NUL 已去掉 ✓）+ `GL_VERSION=[4.2 (Core Profile)
  Mesa 25.0.1 (git-69e48f9182)]`（**闭合 `]` 出现** ✓）+ **`groups 4.2; OpenGL11..OpenGL42 on, higher off`**
  （原先丢失的那行 ✓）。

- ❌ **`ZINK_DEBUG=nobgc`**（禁用 Zink 异步管线编译）：编译挪到 **Render thread** 后**仍崩**（`DEFAULT` 两轮都在载入
  ~40 s 内死；第 4 次 fault 就落在 Render thread，`bt#0..#16` 全在编译器内）⇒ **本 bug 是"着色器确定性"的，
  **不是线程竞态** ⇒ 别再用它（徒增变量与卡顿）。
- ❌ **厂商侧 env**：反汇编三个厂商库的 `getenv` 调用点 ⇒ 只读 `TEMP*/TMP*/PWD/TERM/HOME/PATH` 与 dump/log 类
  （`DUMP_LLVM` / `AS_SECURE_LOG_FILE` / `REINJECT_LLVM` / `WRITE_SUPER_CACHE_INSTANTLY`）⇒ **没有**能关掉编译路径
  或某个优化的开关；设备上**只有一个**编译器版本（无 `.16`）；内部优化开关（`ShaderConfig.yaml` 的 `disable_*`）
  是**驱动内设定**，无 env 接口。
- ⚠️ **`MESA_EXTENSION_OVERRIDE`（此条结论已被 (2)/(5) 取代）**：当时的推理是"GL 4.2 下 INDIRECT 靠 ARB 扩展
  分支存活 ⇒ 藏任何必需扩展会**直接关掉 INDIRECT**（比 INSTANCING 更差）"。**现状**：它**正是**我们下发的两个
  执行点之一 ✓ —— 只藏 `GL_ARB_compute_shader`（**不碰** SSBO/图像族 ✓），且与 LWJGL 标志层配合使用 ✓；
  而"藏必需扩展会更糟"这条**本身仍然成立**（别去藏 SSBO/图像族 ✗）。
  `ZINK_INLINE_UNIFORMS=0` / GL 版本覆盖**未试**（会改 SPIR-V，但预期收益低）。
- ❌ **平台文档层**：无任何 app 可达的 GPU/着色器调试开关、兼容模式或 Vulkan 验证层（60+ 查询的负结论）。
- 🔲 **未试但值得跟进**：① 驱动内部 `ShaderConfig.yaml` 的 **sandbox 路径**（`compiler_set_sandbox_path`）是否可由
  app 提供自定义 YAML（若可 ⇒ 或许能关掉出事的那个编译 pass）；② ~~用**隐式 Vulkan 层**（`VK_INSTANCE_LAYERS`）隐藏
  `VK_KHR_vulkan_memory_model`/把 `apiVersion` 夹到 1.1~~ **已证死**（2026-09-17：本机 loader 忽略 `VK_INSTANCE_LAYERS` 等全部 `VK_*` env，见 [`Vulkan后端-取证存档.md`](Vulkan后端-取证存档.md) §3.4）。

  证据是库内字面量：`SPIRVRegularizeLLVM` / `SPIRVLowerBoolPass` / `SPIRVLowerConstExprPass` /
  `"MBB exits via conditional branch … but ends with a barrier instruction!"` / `"Too many shared variables declared."`。

- **两个崩点机制**（与我们 dump 的寄存器逐位吻合 ✓）：
  - `+0x84d94c`：一个极小的 **MBIN IR 节点构造函数**，其 name 指针 `[[node]+24]` **为 NULL** 被 `ldrb` 解引用（dump 里 `x0=0x0` ✓）；

  … → **共享变量结算函数**（就是那个印 `"Too many shared variables declared."`、按 `0x8000` 卡上限的函数）→ … → 崩溃节点
  ⇒ **崩在"compute 管线的后端编译"里，且路径穿过 workgroup/shared 记账**。

## 2. 链 B：JVM C 堆被**某 native 越界写**坏（**写者仍未识别**）

### ⚠️ 更正：原"Flywheel 光照 18³ 越界"归因**错误**（2026-09-16 晚，用随包 jar 字节码核验）
| 项 | 原以为 | 实际（`LightStorage.class` 常量池 + `<clinit>`）|
|---|---|---|
| `LIGHT_SIZE_BYTES` | 4096 | **5832**（= `BLOCKS_PER_SECTION = 18³`）|
| `SOLID_SIZE_BYTES` | 512 | **732**（183 longs × 4）|
| `SECTION_SIZE_BYTES` | 4608 | **6564** |
| 光照写最大地址 | 越界 ~1.7 KB | `732 + 5831 = 6563 = SECTION_SIZE_BYTES − 1` ⇒ **零越界** |

`512/4096` 是 **vanilla `DataLayer` 的 16³** 常量（**拿错了参照** ✗）。Flywheel 1.0.x **所有版本**都是 18³
（`git diff` / `git log` 无相关改动）⇒ **上游无物可修**；唯一非零偏差 = `collectSolidData()` 的 BitSet→`toLongArray()`
写 736 B 进 732 B solid 区 ⇒ **溢出 4 B 且仍在同一 section 内**（随后又被 `collectLightData` 覆盖）⇒ 无害。
> 教训：关键尺寸要用**字节码/`.class` 常量**核，不要拿另一个类的同名常量类比。

### 仍然成立的 A/B 与更锐的推论
A/B 证明的是："**存在某个 native 越界写，且它发生在由 `os::malloc` 分配的块上**"（只有加 slack 才被吸收）——
**不是**光照引擎。
- 收窄成「只给 ≥1 KB 加富余」⇒ **加载 16 s 崩** ⇒ slack 只有加在**写者自己的块**上才有效 ⇒ 肇事**分配 < 1 KB**
  （不是"被撞目标 <1 KB"）。Flywheel 的 `ScatterList`/`TransferList` 起步 72 B、各类 scratch/uniform 块都在此区间，
  但扫遍 Flywheel raw-memory 写入**未发现逃逸越界** ⇒ 写者在**别处**（任何走 `Unsafe.allocateMemory` /
  `MemoryUtil.nmemAlloc` / JNI 的 native 写者）。
- ⇒ **识别写者**：**GWP-ASan**（平台自带，`app.json5` `"GWPAsanEnabled": true` 或 `hidebug.enableGwpAsanGrayscale()`；
  文档 id `bpta-stability-gwpasan-detection` / `js-apis-hidebug`）能在越界写的**当下**给出 alloc/free/access 三处栈；
  备选：MemDebug（DevEco Testing，文档 id `faqs-stability-basic-quality-test-3`）或自建 **slack 金丝雀**
  （slack 填 `0xAA`、`free` 时报告最深脏字节 ⇒ 直接量出越界深度）。

### 判据（单变量 A/B，已闭环）
| 动作 | 结果 |
|---|---|
| 关掉富余（`MEOW_MALLOC_SLACK=0`，或旧版无 env）| 4 分钟内两次 `Service Thread @ 0x5d00000008`；另有 JVM 自报 `concurrentHashTable.inline.hpp:675 Cannot resize table: Node hash code has changed possibly due to corruption of the contents` |
| 打开富余（4096，全尺寸）| **9 / 7.5 / 6.4 分钟三轮干净**；破坏族零出现 |
| 收窄成「只给 ≥1 KB」（**错误尝试**）| **加载 16 秒**即崩 ⇒ **写者自己的分配 < 1 KB**（slack 必须加在写者的块上才吸收）⇒ 回到全尺寸 |

行为特征也是旁证：**反复命中同一地址、偶发可恢复（某次 fault 后游戏还活了 3 分钟）、最终致命** = 典型持续破坏，不是确定性 JVM bug。

### 随包规避
`tools/jre26/inject_malloc_slack.py`（`linux_build_jvm.sh` step 2.7 注入）：
- **默认全尺寸生效**：`os::malloc` 每条分配多要 4096 B 尾部富余（不返回给调用者）；`os::free/realloc` 靠头部 magic 识别。
- 两个**运行时**旋钮（不必重编）：`MEOW_MALLOC_SLACK`（默认 4096，0 = 关）、`MEOW_MALLOC_SLACK_MIN`（默认 0）。
- **零落盘**：仅在首次分配时往 **stderr** 打一行自证（`[meow] os::malloc tail slack = …`，→ hilog）。
- 覆盖范围：2 参 `os::malloc` 会汇入被注入的 3 参版本 ⇒ `Unsafe.allocateMemory`（Flywheel 竞技场）也被覆盖 ✓。
- 绕过 NMT 记账 ⇒ 仅 NMT 关闭时使用（默认关）。

### 残留风险（诚实记录）
- **写者未识别 ⇒ "完整性"未证**：若某次越界**超过** 4096 B，仍会静默砸到邻居 ⇒ 症状回归。这是**布局掩盖**，不是修复
  ⇒ 要么先抓到写者（GWP-ASan / 金丝雀），要么把"slack 是否被写穿"做成**可报警的哨兵**。
- **内存代价**：每条分配多 4096 B（含 16 B 头）⇒ 存活的小分配被放大（8 B 请求 ≈ 4 KB）；**RSS 从未量过**。
  若在意：`MEOW_MALLOC_SLACK=1024`（= 1/4 代价）或 `2048` 可**免重编**立减；但**前提是写者越界 < 该值**
  （1024 是否够**未知** ⇒ 需用金丝雀/哨兵实测越界深度后再定）。
- ⚠️ 同一天在 **A 链**上还出现过**一次静默猝死**（同配置、无 fault、无 hs_err）⇒ 提醒："没抓到 fault"≠"没问题"（见 §1）。

## 3. 落盘约定：`.hmmcraft/logs/`（铁律：不污染硬盘）

游戏目录 = 进程 cwd；以下三类默认会写它，现已全部改道到**实例内的** `<实例>/.hmmcraft/logs/`：

| 来源 | 处置 |
|---|---|
| `hs_err_pid*.log`（JVM 崩溃报告）| 启动器传 `-XX:ErrorFile=<logsDir>/hs_err_pid%p.log` |
| `meowbt-dump.txt`（抓栈转储）| **默认只打 stderr**；要落盘须显式 `MEOW_BT_FILE=<…>/.hmmcraft/logs/meowbt-dump.txt` |
| `hotspot_pid*.log`（`-XX:+Log*` 的默认落点）| 启动器**不设** Log* 参数（默认无此文件）；需要 Log 时用户自己在「额外 JVM 参数」里指定落点 |

`<logsDir>` = `versionDir(gameRoot, versionId)/.hmmcraft/logs`（**即使未开版本隔离也按实例归位**，各实例的
hs_err 不互相覆盖），由 `InstanceSettings.ensureInstanceLogsDir()` 在启动前尝试创建；**建不出则退回沙箱目录**
（`<runDir>-logs`，再失败才让 JVM 用默认）。⚠️ **不能**把 `-XX:ErrorFile` 指到不存在的路径：HotSpot 会**静默**
回退成 cwd 下的默认名（`vmError.cpp` 的 `default_pattern`）⇒ 又写回游戏目录，正是本节要消除的污染。

### ★坑（2026-09-16 实测，代价 = 游戏直接起不来）
`-XX:LogFile` 是**诊断**参数，没前置 `-XX:+UnlockDiagnosticVMOptions` 时 JVM **拒启**：
```
Error: VM option 'LogFile' is diagnostic and must be enabled via -XX:+UnlockDiagnosticVMOptions
Error: The unlock option must precede 'LogFile'.  →  Error: Could not create the Java Virtual Machine.
```
⇒ 随包默认**只留 `-XX:ErrorFile`**（产品参数）。此类失败**没有** hs_err、MC 的 `logs/latest.log` 也不更新，
只能靠平台捕获里我们的 `[jre_stderr] …` 转发看到（启动器把 JVM stderr 转 hilog）。

## 6. ★GL 能力屏蔽：正确且全面的途径（维护者 / 用户操作规范）

> 定位：**通用**（不限于 compute）。目标 = 让"某个 GL 能力在本进程/本设备上不可用"这件事
> **可配置、可验证、可撤销**，而不是散落的特例补丁。实现面见 §1(2)；旋钮清单见
> [`../../00-current/运行时环境变量.md`](../../00-current/运行时环境变量.md)。

### 6.1 四条硬规则（先看这个）
1. **先问"消费者从哪拿这个信息"，再选层** —— 屏蔽点必须落在**它真正读的那份数据**上。本机实测反例：
   过滤 `glGetStringi` ✗（LWJGL 不吃我们的 GL 包装）、只改扩展表 ✗（**函数槽型**探测如
   `check_ARB_compute_shader` 不含 `ext.contains`，够不着）、`MESA_EXTENSION_OVERRIDE` 单独用 ✗（改不了标志）。
2. **"能力"与"版本组"是两种东西，真值来源不同**：
   - **能力**（`GL_ARB_*`/`GL_EXT_*`）= "驱动**公布** + 入口**可解析**"（上游语义）；
   - **版本组**（`OpenGL11..OpenGL46`）= 上下文自报的 **`GL_VERSION`**
     （LWJGL 自己只塞**当前版本**那一个名字，所以低版本组必须靠版本号补 ✓）。
3. **至少落两个执行点，它们互补**：
   - ① **LWJGL 能力标志**（`MEOW_MASK_EXTENSIONS` → `RendererInit.isMasked`）⇒ 让**经 LWJGL 读能力**的模组
     走它自己设计好的降级路径（**不依赖它捕获异常** ✓）；
   - ② **Mesa 扩展表**（`MESA_EXTENSION_OVERRIDE`，启动器从**同一清单**派生、只取 `GL_*`）⇒ 让**绕过
     LWJGL** 的消费者也只会拿到**干净的 GL 错误**，而不是驱动崩溃 ✓。
4. **只做"真→假"**：伪造（假→真）需要驱动真能解析入口 ⇒ 不保证 ⇒ **不做** ✗。

### 6.2 操作步骤（照做即可）
1. **选清单**：能力名写 `GL_ARB_x`；要压版本组写 `OpenGLxy`（如 `OpenGL46`）。
2. **下发**（都是**数据**、免重编，任选）：
   - 临时/排障：在「**额外渲染环境变量**」写 `MEOW_MASK_EXTENSIONS=GL_ARB_x,OpenGL46`
     （启动器自动派生 `MESA_EXTENSION_OVERRIDE=-GL_ARB_x` ⇒ **两层都生效** ✓）。
     ⚠️ **它是"整体替换"而不是追加** ✗：想"再补一个能力"必须**把默认那条一起写上**
     （本机默认 = `GL_ARB_compute_shader`），否则 compute 屏蔽会**两层同时消失**、Kirin 上崩溃回来 ✗。
     想**关掉**屏蔽则写**显式空**：`MEOW_MASK_EXTENSIONS=`（两层都不发 ✓）。
   - 长期默认：改 `GameLauncher.ets` 的 `defaultMask`（本机现为 Kirin + 现代路径 ⇒ `GL_ARB_compute_shader`）。
   - **面向用户的开关**：「编辑版本 → **屏蔽 GL_ARB_compute_shader**」（**逐实例**，**默认开 = 屏蔽** ——
     与 `MEOW_MASK_EXTENSIONS` 的"设/不设"语义一致 ✓）。**关掉它 = 不屏蔽**该能力、两层都不下发 ⇒
     模组可用 compute，但本机驱动不稳**可能直接崩** ⇒ 知情承担 ✓。它只影响 `defaultMask` 的取值，
     **优先级仍低于**显式 `MEOW_MASK_EXTENSIONS` ✓；落在
     `versions/<id>/.hmmcraft/instance-settings.json` 的 `hmmcraftComputeShaderMasked`，
     **仅显式 false 才写键**（稀疏文件 ✓，与 glthread 同构），启动自证行打
     `computeShader=on(default)/off(user)` ✓。
     **⚠️ 关掉它不会让用户在「额外渲染环境变量」里设的其它屏蔽失效** ✓：那份 `MEOW_MASK_EXTENSIONS` 会
     **整份覆盖**默认清单（`capMask = maskOverride === null ? defaultMask : maskOverride`）⇒ 此时开关
     **根本不参与** ✓；用户直接写的 `MESA_EXTENSION_OVERRIDE` 也因"后写覆盖"而仍然生效 ✓。

**实现位置（排查用；覆盖关系契约表在 [`../../00-current/运行时环境变量.md`](../../00-current/运行时环境变量.md) §1.2）**：
`meowjrebridge.cpp` 的 setenv 顺序 —— ① 桥内默认 `229–304` · ②③ 启动器拼行 + 用户文本 `308–333`（每行打
`extra render env: K=V` 日志）· ④ GL guard 失效安全 `376–379`（同时打 WARN）；启动器拼行在 `GameLauncher.ets`
的 `renderEnv`（顺序：`GALLIUM_THREAD` → `MEOW_GUARD_SYNC` → 屏蔽行 → 用户文本）✓。
   ⚠️ **两种入口影响的层数不同**：**env = 两层总闸**（启动器从它派生 Mesa 那半 ✓）；
   `-Dmeow.maskExtensions`（走「额外 JVM 参数」）**只驱动 ①**（与 env **并集**、只加不减；Mesa 那半看不到
   JVM 属性 ✗）⇒ 想两层都生效就写 env ✓。
3. **验证四判据**（缺一不可）：
   - **自证行**：`RendererInit: capability mask armed: […]` + 启动器 `capMask=on(…)`；
   - **行为判据**：该能力**不再被尝试**（本例：`Compiled culling/` ×0、`GL_INVALID_VALUE` **0**）；
   - **反例判据**：别信"没崩"——要看它走的是不是**设计好的降级路径**（本例 `pipeline/instancing` ×26 ✓）；
   - **不失真**：`groups …` 与 `GL_VERSION` 自证行一致（4.2 就报 4.2 ✓），别让屏蔽连带把版本组压坏 ✗。

### 6.3 禁止清单（全是**实测**或**结构性**反例）
| ✗ 别做 | 为什么 |
|---|---|
| 在 **GL 层**包装 `glGetStringi`/`GL_NUM_EXTENSIONS` | 到不了 LWJGL 的能力集（实测**零影响** ✗）|
| 只改**扩展表**（Mesa 或自建包装） | **函数槽型**探测（如 `check_ARB_compute_shader`）不含 `ext.contains` ⇒ 够不着（实测 ✗）|
| 去藏**必需**扩展（`SSBO`/`GL_ARB_shader_image_load_store` 等） | 会直接关掉依赖它的路径，**比降级更糟** ✗ —— 只藏那一个出问题的能力 |
| 用**版本号钝器**（`MESA_GL_VERSION_OVERRIDE` / `MESA_EXTENSION_MAX_YEAR`） | 会连带藏掉一片必需扩展 ✗（本机 Mesa 侧也没有 `MESA_VK_*` 之类可夹版本，见 §1 负结论）|
| **伪造**能力（假→真） | 需要驱动真能解析入口 ⇒ 不保证 ⇒ 不做 ✗ |
| 把"屏蔽"当成**修复** | 它把"驱动崩"换成"能力不可用"（性能代价）⇒ **真解在上游驱动**，要并行上报 ✓ |

### 6.4 边界（诚实：通用 ≠ 万能）
- 只覆盖**能力标志**，**不动函数槽** ⇒ "忽略标志硬调该函数"的模组不会被拦住（由 **Mesa 层**兜成干净 GL 错误 ✓）。
- 只屏蔽**经 LWJGL** 的视图；模组若自带 JNI 直接查 GL ⇒ 只有 Mesa 层兜底 ✓。
- 键名 = LWJGL 字段名（= 扩展名；版本组 = `OpenGLxy`）；**换 LWJGL 世代要重生成** overlay
  （`gen_glcap.py` 带**硬失败**守卫：形状变了会报错，而不是静默生成**未经校验**的文件 ✓）。
- **实机范围的记录（2026-09-16）**：当时只在 NeoForge 1.21.1 + Create/Flywheel 上跑过；原版 / Fabric /
  1.20.2 / 26.x / gl4es 只核了**代码可达性**。⚠️ **当前状态一律以
  [`../../00-current/现状基线.md`](../../00-current/现状基线.md) §5 第 23 条为准**（本文件只记机制与规范，
  不承担状态声明 ✓）。

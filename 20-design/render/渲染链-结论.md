# 渲染链测绘 & SurfaceHolder 迁移评估（结论）

> 目的：① 完整测绘游戏渲染链（**GL 与 Vulkan 两条**，见 §2）；② 评估 `OH_NativeXComponent` → `OH_ArkUI_SurfaceHolder` 迁移的收益与难度。
> **证据原文（代码测绘 / 官方文档 / SDK 头文件 / 备用计划 / OpenGTX 结案 / 跨层精确时序）** 全部在
> [`../90-archive/渲染迁移评估/`](../../90-archive/渲染迁移评估)（`01`–`06`），本页只留**结论与索引**。

## 1. 结论先行

| 问题 | 结论 |
|---|---|
| 迁移 SurfaceHolder 有收益吗？ | **基本没有。** 对延迟/帧率**零收益**（60Hz 是 OS 合成仲裁，不是 XComponent 的锅）；唯一实打实的好处是 NDK 节点手势系统，而 MC 要的是原始鼠标/键盘，用不上。 |
| 难度多大？ | **中高（3–6 人日 + 全链路回归）**，且会倒退两个现有能力：尺寸从 px 退化为 vp（光标 1:1 映射要重算）、输入从 ArkTS 组件事件改成 NDK node 事件。 |
| 最关键的事实 | **代码里 `OH_NativeXComponent_*` 用量 = 0。** ArkTS `XComponent` 只当 "surfaceId 生产器"，native 用 `OH_NativeWindow_CreateNativeWindowFromSurfaceId(sid)` 拿窗口。所以不存在 "从 NativeXComponent 迁移"，只有 "把窗口/输入生产者从 ArkTS 组件换成 NDK 节点"。 |
| 建议 | **暂不迁移。** 将来要迁则按 "窗口生产者可插拔" 分阶段做（见 §5），不要一次性重写。 |
| **渲染后端按什么选？** | 当前**只按 MC 版本**（≥1.17 → 桌面 GL `openglv4`），**不判设备能力**。手机没有桌面 GL（`/system/lib64/libGLv4.so` 不存在）⇒ `openglv4` 在手机上**永远不可能成功**，表现为启动 ~14s 后**无声闪退**（2026-09-21 Mate XT 实测；换 Vulkan 即通）。必须在自动选择/默认档处加**设备能力门**（库存在性 / `devicetype`）。见 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) §A8、工作区根 `stuffs/research/phone-26.3-vulkan/`。 |

## 2. 当前渲染链（GL 与 Vulkan 两条；结论级；逐行证据见 archive）

> 行号为**本文件记录时的现值**（会随重构失效，符号名稳定）；精确的逐行/逐符号证据见

>
> 游戏渲染链有**两条**，共用同一「**窗口 / 几何 / 显示缩放**」链与同一 bridge/输入环，只在
> **① 预 dlopen 的渲染器库** 与 **② LWJGL 的库名 `-D`** 处分叉：**GL 档（§2.1）** 用
> `libmeowglguard.so`（≥1.17）/ `libgl4es.so`（≤1.16、legacy）；**Vulkan 档（§2.2，MC ≥26.2）** 用
> `libmeowvulkan.so`。逐版本「渲染后端」下拉四档 = 推荐 / OpenGLv4 / GL4ES（旧版本兼容）/
> Vulkan（26.2+，实验），存 `<gameRoot>/versions/<id>/.hmmcraft/instance-settings.json`。


**链路关键事实（GL 档；`呈现`与 `glguard` 行为 GL 专属，其余为两条链共有）**
- 上下文归属：**JVM 渲染线程**持有 GL context；`meowcraftbridge` 内**没有**自己的渲染线程。
- 呈现：`eglSwapInterval(0)` 硬编码两处；`meowSwapInterval()` 忽略 MC 传入值。`OH_NativeVSync` / `DisplaySync` 已全部清除。
- 尺寸来源：唯一来源是 `XComponentController.onSurfaceChanged` 的 `SurfaceRect.surfaceWidth/Height`（**px**），喂给 `frameW/frameH`，再算 `pxPerVp` 做光标映射。
- 窗口尺寸变化：UI 线程只标记 `env->width/height`，渲染线程节流 50ms 做 `internalWindowSizeChanged` 上抛 + 重建 EGL surface。
- 无 `setPreferredOrientation` / `setWindowKeepScreenOn` / 运行时窗口背景色（只有启动图白底 + XComponent 黑底）。
- 包图：`meowcraftlib`(HAR，含 `libmeowjrebridge.so` + `libmeowcraftbridge.so` + `libmeowvulkan.so`) 静态并入 `meowjre`(HSP，`libIsolation:true`)；
  `meowlwjgls`(HAR) 提供 lwjgl（现代单代 3.4.3）/ openal / freetype 等随包 native。
- **跨层精确时序**（`launchJvm` 先后 / 线程归属 / surface 与 JVM 顺序 / want 字段 / glguard 转发链）⇒
  [`../../90-archive/渲染迁移评估/06-cross-layer-timing-evidence.md`](../../90-archive/渲染迁移评估/06-cross-layer-timing-evidence.md)（含逐行证据）；
  **结论级要点**：NAPI 收到参数后立即 spawn detached 线程并返回；surface 注入与 JVM 启动在**同一回调内串行、surface 先**；
  `want` 只有 3 字段（`gameRoot` / `jsonPath` / `versionId`），几何走 `startAbility` 的 StartOptions，账户走沙箱文件；
  glguard 的转发链是 **guard → `libGLv4.so` → Zink → Vulkan**（前两跳由 guard 代码可证，后两跳是系统实现）。

### 2.2 Vulkan 档（MC ≥26.2；界面「渲染后端」选 `Vulkan（26.2+，实验）`）

```
ArkTS (GameAbility, process ":game")
 └─ GameWindow.ets  ← 与 GL 档共用同一「窗口 / 几何 / 显示缩放」链
     ├─ GameXComponentController : XComponentController      （三回调同 §2.1）
     ├─ XComponent({type: SURFACE, controller}) + 隐形 TextInput（IME）
     └─ injectAndLaunch(ctx, sid, w, h)                      （先 surface、后 JVM，同 §2.1）
          ▼ import('meowjre') → 'meowcraftbridge'
NAPI (libmeowjrebridge.so, 在 meowjre HSP)
 ├─ setGameSurface / resizeGameSurface → libmeowcraftbridge.so
 └─ launchJvm → detached std::thread；setenv → 预 dlopen 渲染器 → dlopen libjli → JLI_Launch
               │ 渲染后端=Vulkan ⇒ -Dorg.lwjgl.vulkan.libname=libmeowvulkan.so
               │ （不再注入任何 env；GL 库/环境仍就绪，供 MC 内部回退）
               ▼
libmeowcraftbridge.so（净室自研，随 meowjre HSP 合并）
 ├─ egl_gl.c：OH_NativeWindow_CreateNativeWindowFromSurfaceId(sid) → env->window
 │   SET_SOURCE_TYPE / SET_BUFFER_GEOMETRY(px) / resize 节流 50ms —— 与 GL 档同
 │   WSI：glfwCreateWindowSurface → vkCreateSurfaceOHOS(env->window)
 └─ input_bridge.c：SPSC 环形队列 → 渲染线程 pump → GLFW JNI 回调
               ▼
libmeowvulkan.so（自研 loader shim；被加载即挂钩，MEOW_VK_SHIM=0/空 = 纯透传逃生）
 ├─ 门控修面：补本机 ICD 被裁扩展名（dynamic_rendering / push_descriptor /
 │            vertex_attribute_divisor + VK_KHR_get_physical_device_properties2）
 │            + 补被清 0 的 feature 位 + vkCreateDevice 前从副本剔名 + KHR→core 名映射
 ├─ F66 vkQueueSubmit2 多 entry → 合并成一条 v1 提交（本机只接受 1 条 entry）
 ├─ F69 时间线信号量 → 真实 VkFence（vkWaitSemaphores→vkWaitForFences；禁主机侧伪造）
 ├─ F72 vkCmdPushDescriptorSet → 普通描述符集（另建去 push 位的镜像 set layout）
 └─ F73/F74 默认强制 preTransform=IDENTITY（本机 surface 报 ROTATE_90 且 WSI 照做）
               │ dlopen("/system/lib64/libvulkan.so")
               ▼
官方 loader → OHOS ICD（vulkan.hvgr_v210.so，Maleoon 916）
   MC 自身仍走 graphicsBackend 机制（--graphicsBackend vulkan；失败时 MC 内部回退 GL）
```

**Vulkan 链路关键事实**
- **选择与注入**：逐版本「渲染后端」选 Vulkan ⇒ `RendererPolicy` 输出 `graphicsBackend='vulkan'`（GL 侧 lib/env 与 auto 相同，留作 MC 内部回退）；`MinecraftLauncher` 把
  `-Dorg.lwjgl.vulkan.libname` 指向 `libmeowvulkan.so`、并给 MC 追加游戏参数 `--graphicsBackend vulkan`。
  **零必配 env**：`MEOW_VK_SHIM` 不再是总开关，shim **被加载即挂钩**（`MEOW_VK_SHIM=0`/空 = 纯透传逃生）。
- **版本门槛**：仅 MC `≥26.2` 才给 MC 追加 `--graphicsBackend vulkan` —— 门控 = **`RendererPolicy.vulkanBackendRequested(mcVersion, backend)`**（后端选 Vulkan **且** `supportsVulkanBackend(mcVersion)`），**启动路径与编辑面板同源**；更老版本选该档**不追加**该参数（静默走 GL）、**无启动期告警**，但**编辑面板副行显示生效后端**（选 Vulkan 会显示 GL 档）。登记于 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) §H3；**26.3 未验**见该文 §H4。
- **shim 两类修正**（`meowvulkan.c`）：
  - **门控修面**：补本机 ICD 被裁的扩展名（`dynamic_rendering` / `push_descriptor` / `vertex_attribute_divisor` + `VK_KHR_get_physical_device_properties2`）+ 被清 0 的 feature 位；
    `vkCreateDevice` 前从**副本**剔名；`...KHR`→core 名映射。
  - **四个翻译**：**F66** 多条 `VkSubmitInfo2` entry **合并成一条** v1 提交（本机 ICD 只接受 1 条 entry）；**F69** 时间线信号量 → 真实 `VkFence`（`vkWaitSemaphores`→`vkWaitForFences`；本机 ICD 不从 GPU 侧推进时间线，且禁止主机侧伪造）；
    **F72** `vkCmdPushDescriptorSet` → 普通描述符集（`vkAllocateDescriptorSets`+`vkUpdateDescriptorSets`+`vkCmdBindDescriptorSets`，另建去掉 push 位的镜像 set layout）；**F73/F74** 默认强制 `preTransform=IDENTITY`。
  - 此后 `dlopen("/system/lib64/libvulkan.so")` 走官方 loader → **OHOS ICD**（`vulkan.hvgr_v210.so`，Maleoon 916）。
- **WSI**：`glfwCreateWindowSurface` → `vkCreateSurfaceOHOS`，复用 `env->window`；**与 GL 档共用同一窗口/几何/显示缩放链**。**MC ≥26.3 改由 SDL 驱动做这步**（见下条）。
- **MC ≥26.3 的 WSI 落在 SDL 侧，不在桥**：26.3 弃 GLFW 改 SDL3 后，`vkCreateSurfaceOHOS` 由我方 SDL `ohos` 驱动的 `SDL_Vulkan_CreateSurface` 完成（`主仓 tools/sdl/src/video/ohos/SDL_ohosvulkan.c`），实例扩展报 `{VK_KHR_surface, VK_OHOS_surface}`。loader 由该驱动选：调用方路径（**实测 MC 传的就是 shim 的绝对路径**）→ `SDL_HINT_VULKAN_LIBRARY`（含环境变量回落）→ 系统 loader。**建面前的窗口策略（几何 pin + usage/format）已定案不在 SDL 路径执行**（桥/ArkTS 已在 surface id 发布时设好，实测省略亦正常）。机制与事实见 [`SDL3适配-复盘.md`](SDL3适配-复盘.md) §七。
- **根因（shim 为何存在）**：本机唯一 ICD 是 1.4 时代实现、只按 **1.2 档**裁剪**上报面**（3 个 MC 硬需扩展名与相关 feature 位缺失，实现却在；`vkCmdPushDescriptorSet` 被真实管线消费会丢器件 ⇒ 由 **F72 翻译为普通描述符集**；`vkCmdCopyBufferToImage` 的历史「崩」实为 shim 自身包装参数表错位所致，shim `.7` 已修 ⇒ **图像上传走直转发、F53 默认关**）。
- **两条独立修复（勿混为一谈）**：**① 材质/描述符**（推送描述符被消费丢器件）⇒ **F72 / F72c 描述符池健壮化**；**② 图像上传（image transfer）** ⇒ **原始 `vkCmdCopyBufferToImage` 直转发**（F53 重定向默认关，本役未启用）。登记于 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) §F。
- `divisor` 特性**必须继续谎报**（撤掉它 MC 直接拒绝建 Vulkan 后端）；实测 MC 从不使用 divisor 状态 ⇒ 对 vanilla 无害。
- **现状**（可用性 / 性能差距 / GL 档偶发闪）见 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) §H，不在此复述。

## 3. SurfaceHolder 是什么（详见 archive `02`/`03`）

- `OH_ArkUI_SurfaceHolder` **不是新渲染组件**，是 **XComponent 节点的 native 侧 Surface 生命周期管理器**：由 `ArkUI_NodeHandle` 创建，在 `onSurfaceCreated` 回调里用 `OH_ArkUI_XComponent_GetNativeWindow(holder)` 拿 `OHNativeWindow*`，再照常 `eglCreateWindowSurface`。
- 头文件在 `ace/xcomponent/native_interface_xcomponent.h`（**不是** `arkui/` 下）；**核心 API 起始版本 19**，show/hide + 节点帧率 + Accessibility = 20，`SetSurfaceConfig(isOpaque)` = 22。项目 `targetSdkVersion=6.1.0(23)` ⇒ **可用**。
- `OH_NativeXComponent` **没有正式 `@deprecated`**（仅 `Attach/DetachNativeRootNode` 于 20 废弃）。官方指南只是"**建议**用 SurfaceHolder 代替"，理由：① `OH_NativeXComponent` 生命周期与组件强绑定、销毁后操作可能崩；② 事件接口贫瘠（只有基础触摸/鼠标/键盘，无长按拖拽）。
- `OH_ArkUI_SurfaceCallback` 是**不透明类型**，无公开字段；事件靠 `SetSurfaceCreatedEvent/ChangedEvent/DestroyedEvent` 注册，**回调里没有事件对象、没有窗口**，输入必须另走 node event。
- `onSurfaceChanged` 的 width/height 单位是 **vp**（不是 px），且**不提供 density** ⇒ 迁移后需自补密度换算。

## 4. 收益评估（逐项：几乎为零）

| 维度 | SurfaceHolder 能带来什么 | 对本项目的价值 |
|---|---|---|
| 帧率/90Hz | 帧率 API 挂在**节点**上（`OH_ArkUI_XComponent_SetExpectedFrameRateRange`，API 20），**不是** SurfaceHolder 的能力 | **无。** 已实测：请求全 `rc=0` 但窗口仍 16.66ms 派发，是 OS 按应用分类仲裁 |
| 呈现延迟 | 文档**无**任何 "SurfaceHolder 比 XComponent 更快/刷新率更高" 的表述 | **无** |
| 输入能力 | 可接入 NDK 节点手势（长按/拖拽/点击）；节点事件 `NODE_ON_MOUSE` / `NODE_ON_KEY_EVENT`(14+) / `NODE_ON_AXIS`(17+) / hover | **无正收益，反有风险**：MC 只需原始 mouse move/delta + key，现 ArkTS 组件事件已跑通且低延迟 |
| 生命周期 | `SetAutoInitialize`/`Initialize`/`Finalize`、show/hide 事件（20）、`isOpaque`（22） | **边际收益**：可用 `onSurfaceHide` 做窗口隐藏时暂停 MC（现在没有），属锦上添花 |
| 稳定性 | 解决的是 `OH_NativeXComponent` 的生命周期缺陷 | **无关**：我们根本没用 `OH_NativeXComponent` |
| 尺寸精度 | 回调给 **vp**，无 density | **负收益**：现用 px，迁移要补换算，光标 1:1 映射有回归风险 |
| 架构整洁 | 直接拿 `OHNativeWindow*`，省掉 surfaceId→window 转换 | **微小正收益**：`egl_gl.c` 一行可简化 |

## 5. 难度评估与分阶段方案（若真要做）

**必须改动的点（现状 → 迁移后）**

| # | 项 | 现状 | 迁移后 | 风险 |
|---|---|---|---|---|
| 1 | 节点创建 | ArkTS 声明式 `XComponent` | NDK 建节点（`NodeContent`+`ContentSlot` 或 `NodeController`/typeNode），ArkTS `.onAttach` 把 node 交给 native | 中：需 `OH_ArkUI_GetNodeHandleFromNapiValue` 跨语言传句柄 |
| 2 | Surface 生命周期 | `XComponentController` 三回调 | `OH_ArkUI_SurfaceCallback_*` + `OH_ArkUI_XComponent_GetNativeWindow` | 中：拆除顺序须手写（Remove→Dispose cb→Dispose holder→disposeNode） |
| 3 | 窗口获取 | `OH_NativeWindow_CreateNativeWindowFromSurfaceId(sid)` | 直接拿 `OHNativeWindow*` | 低（`env->window` 契约不变，是好事） |
| 4 | **输入** | ArkTS `.onKeyEvent/.onMouse/.onAxisEvent` + 焦点/IME 协作 | NDK `registerNodeEvent(NODE_ON_MOUSE/KEY_EVENT/AXIS…)` + 事件接收器 | **高**：键/轴节点事件 API 14/17 起；焦点、`requestFocus('ime-input'/'game-xc')`、隐形 TextInput IME 协作全要重做 |
| 5 | **尺寸/DPI** | `SurfaceRect` px | 回调 vp + 自取 density | **中高**：光标 1:1、`pxPerVp`、mouse filter 原点全部要重新验证 |
| 6 | 关窗联动 | `onSurfaceDestroyed` → 请求关 MC | `SetSurfaceDestroyedEvent` 等价 | 低 |
| 7 | 全链路回归 | — | 重测 hover 跟手、转视角、IME 中文、resize、关窗、多窗口/最小化 | **高** |

**工作量**：节点 + Surface 生命周期 ~1 天；输入/IME/焦点重构 ~2–3 天；尺寸/DPI 与光标映射 ~0.5–1 天；全链路实机回归 ~1 天。
合计 **3–6 人日**，大概率在 IME/焦点与 px 映射上踩坑。

**建议路径**
1. **现在：不迁移。** 保持现状（`env->window` 契约 + ArkTS 组件事件）。
2. 将来若迁，做"**可插拔窗口生产者**"而非重写：
   - 先立契约：native 只认 `env->window`，新增 `meowSetSurfaceWindow(void* nativeWindow)`（`egl_gl.c`）。
   - 阶段 A：保留 ArkTS XComponent，仅把 window 获取改为可外部注入（纯重构、零行为变化，可单独回归）。
   - 阶段 B：新增 NDK 节点 + SurfaceHolder 路径，复用同一 `meowSetSurfaceWindow`；输入先仍走 ArkTS 事件（两套并存），只切窗口。
   - 阶段 C：再切输入到 node 事件，逐项回归 IME/焦点。
3. **低成本替代（若只为帧率）**：帧率 API 挂在节点上，可先用 ArkTS 侧 XComponent 帧率接口做 A/B（不动渲染链）；若仍无效果，说明瓶颈不在 API，迁移同样无解。
4. **真正的 90Hz 出路**不在 SurfaceHolder：应用分类 / 游戏通道（AGC / OpenGTX）或平台放开治理层。
   **OpenGTX 已实测排除**（本机 2in1 无 `RenderAccelerate` syscap、无 `libopengtx.so`）⇒ 见
   [`../../90-archive/渲染迁移评估/05-opengtx-feasibility.md`](../../90-archive/渲染迁移评估/05-opengtx-feasibility.md)。

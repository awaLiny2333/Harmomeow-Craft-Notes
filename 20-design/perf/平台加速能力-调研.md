## 0. 结论速览

| 平台能力 | 官方支持设备 | 对本工程 | 判定 |
|---|---|---|---|
| **OpenGTX / LTPO**（GPU Turbo X 开放入口） | Phone / Tablet（6.1.0(23) 起 +TV） | 2in1 不在支持面；本机亦无 `RenderAccelerate` syscap / 无 `libopengtx.so` | ❌ **排除**（双重：文档 + 实测） |
| **超帧（内插 / 外插 / AI）** | 同上（Graphics Accelerate Kit「游戏渲染加速服务」） | 需引擎侧逐帧 `HMS_FG_Dispatch_GLES(颜色/深度/相机矩阵)` → 等于改 MC 渲染管线；且"上架后有效" | ❌ **排除** |
| **超帧·系统送显模式**（`FG_PRESENT_BY_SYSTEM`） | 同上 | 仍须 `Dispatch` 三大件 + `module.json5` 声明 `GraphicsAccelerateKit_FusionAware` | ❌ **排除** |
| **ABR**（自适应 Buffer 分辨率） | 同上（且仅 OpenGL ES） | 同为引擎侧集成 | ❌ **排除** |
| **XEngine Kit**（空域/AI 超分、自适应 VRS、Subpass Shading、光追、HPS） | **Phone / Tablet / PC-2in1 / TV** ✅ 马良 GPU 专属 | 接口形态是**在应用自己的 GL 上下文里执行**（`HMS_XEG_RenderSpatialUpscale(GLuint inputTexture)`）→ MC 的 draw 不经过我们代码 | ❌ **排除**（除非改 MC；唯一理论入口见 §2.1 备注） |
| **游戏启动加速** | 需 AGC 申请 + 引擎侧配合 | 只省启动时间，不提 FPS | ⏸ 侧向，暂不立项 |
| **QoS 线程优先级**（Kernel Enhance Kit） | `SystemCapability.Resourceschedule.QoS.Core`，API 12+ | 只需桥 native 一行 + 线程名判定 | ✅ **首选**（官方最佳实践背书，见 §3.A） |
| **`sched_setaffinity` 绑核** | OHOS libc 提供（`sched.h:92`）；官方最佳实践**就是 QoS + 绑核一起用** | 需先探明大核拓扑（`/proc/cpuinfo` 禁读） | ✅ **可做**（A/B 试，见 §3.A） |
| **`systemLoad` / `thermal`** | `SystemCapability.ResourceSchedule.SystemLoad`，API 12+ | 只读遥测 → 驱动自适应画质 | ✅ 可做（止损，不提速） |
| **GameServiceKit `game_performance`** | `SystemCapability.GameService.GamePerformance`，C API 5.0.2(14)+ | 读 GPU/CPU/热；并**上报场景让系统改资源调度** | ⚠️ **待探测**（2in1 是否在面 + 是否需 AGC） |
| **HWC 硬件合成** | 系统能力 | 我们已是 HWC 直通；但「显示缩放 `.scale()` 是否让自渲染图层失去 HWC」**未验** | ⚠️ **新增待验假设** |
| **Vulkan 原生后端**（去掉 Zink 二次翻译） | 驱动侧 | 结构性最大收益 | ⛔ 平台卡死（A6） |
| **刷新率档位 60/90** | OS 仲裁 | 无程序化 API | ⛔ 平台卡死（A1） |
| **NativeVSync / 帧率请求** | `native_vsync.h` | 已实测 rc=0 无效（OS 按应用分类仲裁） | ❌ 已排除 |

**一句话**：华为给"游戏"的加速套件（OpenGTX / 超帧 / ABR / XEngine）**全部要求在游戏引擎内部集成**，而我们的硬约束是**不改 Minecraft** → 这一整类能力对本工程**结构性不可用**。真正能做的落在三处：**CPU 调度（QoS/绑核）**、**Mesa/Zink 软件栈旋钮**、**游戏侧 mod 与画质预设**。

## 1. 瓶颈定性（复核）

基线（用户定义，2026-09-13）：`26.2 + Fabric + Sodium ｜ 16 视距 / 6 模拟距离 ｜ 2x 缩放 ｜ 窗口最大化 ｜ 固定世界/位置/视角`

| 缩放 N | 渲染像素 | 帧时 | FPS | 分解（按 `帧时 ≈ 8ms + 7.5ms/MP` 拟合） |
|---|---|---|---|---|
| 1x | 1.85 MP | 22.2 ms | ≈45 | 13.9ms 像素相关 + 8.3ms 固定 → **GPU 主导** |
| 1.5x | 0.82 MP | 16.7 ms | ≈60 | 6.2 + 10.5 |
| 2x | 0.46 MP | 11.1 ms | ≈90 | 3.5 + 7.6 → **固定成本主导** |
| 4x | 0.12 MP | 9.1 ms | ≈110+ | 0.9 + 8.2 → **纯固定成本** |

**定性结论**：

1. **固定 ~8ms/帧是 CPU 侧成本**（MC 主线程 + Zink 的 GL→Vulkan 提交/状态跟踪 + JVM），GPU 只在 1x 附近成为主角。
2. 因此"提高 FPS"有两条**正交**战线：
   - **削 CPU 固定成本** ← 直接对应「麒麟 X90 单核性能不足」这一命题；
   - **削每像素成本** ← 降分辨率/降画质（「显示缩放」已有机制）。
3. 已排除的旁支：合成器上采样成本（固定渲染分辨率、只变窗口大小 → FPS 近似）、`eglSwapBuffers` 背压（swap 不阻塞）、MC 自限帧率（已证伪）。

## 2. 平台能力盘点

### 2.1 判定为「不可用」的（含证据）

#### (a) OpenGTX / LTPO — ❌

- 文档：`开发指南/Graphics_Accelerate_Kit_图形加速服务/游戏渲染加速服务/业务概述/graphics-accelerate-overview`
  > 「游戏渲染加速服务支持 Phone、Tablet 设备，并且从 6.1.0(23) 版本开始，新增支持 TV 设备。」
  **2in1（PC）不在列**。
- 本机实测（2026-09-09，见 [`../../00-current/已知限制与待解.md`](../../00-current/已知限制与待解.md) A4）：无 `SystemCapability.GraphicsGame.RenderAccelerate`、无 `libopengtx.so`。
- 头文件确实随 SDK 下发（`$HMS/native/sysroot/usr/include/graphics_game_sdk/opengtx_base.h`），但**下发 ≠ 设备支持** → 与 2in1 判定一致。

#### (b) 超帧（Frame Generation）— ❌

- 内插模式语义（`.../超帧功能开发/内插模式/概述/graphics-accelerate-fg-interpolation-overview`）：
  > 「利用相邻两个真实渲染帧进行超帧计算生成中间的预测帧…会新增 1~2 帧的响应时延。」
- **系统送显模式**（`.../系统送显模式/OpenGL_ES平台/graphics-accelerate-fg-systempresent-gles`）的业务流：
  1. `HMS_FG_CreateContext_GLES` → 2. `HMS_FG_SetAlgorithmMode_GLES`（必选，选内插/外插）→ 3. `HMS_FG_SetIntegrationMode_GLES(FG_IntegrationInfo{presentMode=FG_PRESENT_BY_SYSTEM,…})` → 4. `HMS_FG_Activate_GLES` → 5. **每帧** `HMS_FG_Dispatch_GLES`（传入**真实帧颜色 + 深度 + 相机矩阵**）生成预测帧 → 6. 绘 UI → 7. 送显。
- 还需要 `module.json5` 声明 `metadata: {"name":"GraphicsAccelerateKit_FusionAware","value":"GLES"}`；`HMS_FG_SetTargetFps_GLES` 注明「**游戏上架后有效**」。
- 支持 API（`.../Graphics_Accelerate_Kit常见问题/游戏渲染加速服务/超帧和ABR支持的图形API有哪些/graphics-accelerate-faq-1`）：GLES + Vulkan 都支持超帧；**ABR 仅 GLES**。
- → **必须拿到引擎每帧的颜色/深度/相机矩阵**。MC 内部有这些（`RenderTarget` / `MainTarget`），但我们在桥层拿不到，且"不改 MC"是硬约束 ⇒ **结构性不可用**。

#### (c) XEngine Kit — ❌（但值得记下唯一理论入口）

- 简介（`开发指南/XEngine_Kit_GPU加速引擎服务/XEngine_Kit简介/xengine-kit-introduction`）：
  - 设备面：「Phone、Tablet、**PC/2in1**、TV」→ **2in1 在支持面内**；「仅在使用马良 GPU 芯片的设备上受支持」→ 本机 Kirin X90 / Maleoon **符合**。
  - 特性查询：GLES 用 `HMS_XEG_GetString`；Vulkan 用 `HMS_XEG_EnumerateDeviceExtensionProperties`。
  - 三个超分（空域 GPU / 空域 AI / 时域 AI）设备起始：空域 GPU 自 **5.0.2(14)** 起支持 Tablet + PC/2in1；空域 AI / 时域 AI 自 **5.1.0(18)** 起支持 Tablet + PC/2in1。
- 但接口形态（`$HMS/native/sysroot/usr/include/xengine/xeg_gles_spatial_upscale.h`）：
  ```c
  typedef void (GL_APIENTRYP PFN_HMS_XEG_RENDERSPATIALUPSCALE)(GLuint inputTexture);
  GL_APICALL void GL_APIENTRY HMS_XEG_RenderSpatialUpscale(GLuint inputTexture);
  ```
  → **在应用自己的 GL 上下文里、由应用主动调用**，把低分辨率纹理超分到当前绑定的 framebuffer。MC 的绘制不经过我们的代码 ⇒ 现代路径（≥1.17）**无插入点**。
- **唯一理论入口**：**legacy / ≤1.16 走 gl4es 时我们确实在 GL 调用路径上**（gl4es 是我们自编并初始化的）。但我们的「显示缩放」已经**做到了同一件事**（低分辨率渲染 + 上采样），XEngine 只提升**画质**、不提升 **FPS** ⇒ **不值得**（且增加一层不确定依赖）。
- 自适应 VRS / Subpass Shading 同理——都是"引擎在 render pass 内插入"，与我们无关。

#### (d) 游戏启动加速 / 游戏预启动 — ⏸

- `.../游戏启动加速服务/开发准备/graphics-accelerate-launch-prepare`：需在 AGC 提交「游戏启动加速服务」能力开关申请；「仅对游戏类应用开放」；「游戏冷启动时长需大于 5 秒」。
- `最佳实践/游戏预启动开发实践/bpta-game-prelaunch-practice`：系统级预启动，靠 `want.parameters["ohos.params.gamePrelaunch"]` 识别，需引擎侧上报预启动结果。
- → **只影响启动时间，不影响 FPS**；且需要"游戏类应用"身份。侧向课题，暂不立项。

### 2.2 判定为「可用 / 待探测」的

#### (e) 线程 QoS（Kernel Enhance Kit）— ✅ 首选

- 头文件 `$SDK/openharmony/native/sysroot/usr/include/qos/qos.h`（`libqos.so`，`SystemCapability.Resourceschedule.QoS.Core`，`@since 12`）：
  ```c
  typedef enum QoS_Level {
      QOS_BACKGROUND = 0, QOS_UTILITY, QOS_DEFAULT,
      QOS_USER_INITIATED, QOS_DEADLINE_REQUEST, QOS_USER_INTERACTIVE,
  } QoS_Level;
  int OH_QoS_SetThreadQoS(QoS_Level level);   // 0 成功 / -1 失败
  int OH_QoS_ResetThreadQoS();
  int OH_QoS_GetThreadQoS(QoS_Level *level);
  ```
- 等级语义（`开发指南/基础功能/Kernel_Enhance_Kit_内核增强能力/QoS_开发指导/qos-guidelines`）：

  | 等级 | 使用场景 | 负载特征 |
  |---|---|---|
  | `QOS_BACKGROUND` | 后台且用户不可见（同步/备份） | 几分钟~几小时 |
  | `QOS_UTILITY` | 不需立即响应（下载/导入） | 几秒~几分钟 |
  | `QOS_DEFAULT` | 默认 | 几秒 |
  | `QOS_USER_INITIATED` | 用户触发且可见进展（打开文档） | 几秒内完成 |
  | `QOS_DEADLINE_REQUEST` | 越快越好的关键任务（页面加载） | 几乎瞬间 |
  | `QOS_USER_INTERACTIVE` | **用户交互任务（UI 线程、刷新界面、动效）** | 即时 |

- **使用限制（关键）**：「QoS 接口**只能设置当前任务**的 QoS 等级。」→ 不能远程给别的线程设，只能在**目标线程自己跑到我们代码里**时设。
- 官方量化收益（同文档）：RN 框架 benchmark 1500view **270.8ms → 236.6ms（≈13%）**；并给出「线程 2 优先级低 → 线程 1 长时间睡眠/被抢占」的典型劣化图。
- 与 ArkTS `taskpool.Priority` / Worker 优先级是**两套逻辑**（后者面向任务，底层同源但接口不同）。FFRT 的 QoS 是**面向任务**的（`ffrt_qos_inherit(-1)` ~ `ffrt_qos_user_initiated(3)`），对 JVM 线程不适用。

#### (f) CPU 绑核 `sched_setaffinity` — ✅ 可做（需 A/B）

- OHOS libc 提供：`$SDK/openharmony/native/sysroot/usr/include/sched.h:92`
  ```c
  int sched_setaffinity(pid_t, size_t, const cpu_set_t *);
  ```
- 官方最佳实践**就是 QoS + 绑核一起用**（`最佳实践/高负载场景线程优先级设置/bpta-thread-priority-setting`）：
  ```c
  OH_QoS_SetThreadQoS(QOS_BACKGROUND);
  cpu_set_t mask; CPU_SET(*g_affinity, &mask);
  sched_setaffinity(0, sizeof(mask), &mask);
  ```
- **风险 / 未知**：设备 `/proc/cpuinfo` 沙箱禁读（oshi 结论），大核编号未知；绑错核（或被系统覆盖）可能反噬 ⇒ 必须 A/B。

#### (g) 系统负载 / 热档位遥测 — ✅ 可做（止损用，不提速）

- `@ohos.resourceschedule.systemload`（`$SDK/openharmony/ets/api/@ohos.resourceschedule.systemload.d.ts`，`SystemCapability.ResourceSchedule.SystemLoad`，`@since 12`）：
  - `systemLoad.getLevel(): Promise<SystemLoadLevel>`、`on('systemLoadChange', cb)`、`off(...)`
  - `SystemLoadLevel`：`LOW=0 / NORMAL=1 / MEDIUM=2 / HIGH=3 / **OVERHEATED=4** / WARNING=5 / EMERGENCY=6 / ESCAPE=7`
  - 语义：「系统根据当前温度、负载以及是否处于高负载场景等信息决策出系统负载融合档位」。
- `@ohos.thermal`（热管理）同族。
- **用途**：档位下滑时**自动降视距 / 降渲染缩放**，把"越热越卡"变成"稳住可玩帧率"。**这是止损，不是提速**。

#### (h) GameServiceKit 游戏场景感知 — ⚠️ 待探测

- `$HMS/native/sysroot/usr/include/GameServiceKit/game_performance.h`（`SystemCapability.GameService.GamePerformance`，C API `5.0.2(14)`+，库 `libgame_performance.z.so`）。
- 双向能力（`开发指南/Game_Service_Kit_游戏服务/游戏场景感知_可选/开发指导_C_C/gameservice-gameperformance-access-procedure-c`）：
  1. **上报**（给系统做资源调度的输入）：`HMS_GamePerformance_UpdatePackageInfo / UpdateConfigInfo / **UpdateSceneInfo** / UpdateNetInfo / UpdatePlayerInfo`；
  2. **读取**：`QueryGpuInfo / QueryCpuInfo / QueryThermalInfo`；`RegisterThermalLevelChangedCallback`。
- 概述（`.../游戏场景感知_可选/概述/gameservice-gameperformance-introduction`）：「通过感知游戏场景和运行状态的不同，使用不同策略**调度系统资源**」。
- **待探测**：2in1 是否在支持面；是否需要 AGC/游戏身份；`Init` 返回码。
- ⚠️ 官方注记：「**Mali 系列 GPU 不支持采集 GPU 性能信息**，调用订阅和查询设备状态信息接口时无法获取设备 GPU 性能信息。」→ 本机是**马良（Maleoon）非 Mali**，理论上不受此限，但**实测时若 GPU 字段为空，先回看这一条**。
- 注：ArkTS 侧也有同名 API（`API参考/Game_Service_Kit_游戏服务/ArkTS_API/gamePerformance_游戏场景感知/gameservice-gameperformance`，字段如 `gpuLoadLevel` / `vertexLoadLevel`，1~10 档）。

#### (i) HWC 硬件合成 — ⚠️ 新增待验假设

- 现状：我们已是 **HWC 直通**（hitrace `DrawImage`=0、`CommitTunnelLayer`，见 [`../render/渲染链-结论.md`](../render/渲染链-结论.md)）。
- 但两份官方最佳实践给出了 HWC **失效条件**：
  - `最佳实践/应用功耗分析/自渲染图层未使用硬件合成问题分析/bpta-hwc-self-rendering-layer-analysis`：**自渲染图层设了透明度** → 必须 GPU 合成；**高阶视效（模糊等）与自渲染图层交叠** → 必须 GPU 合成（RS 要读回自渲染内容）。判据 = Profiler / trace 搜 `DrawImage(GPU)`，非 0 即 GPU 合成。
  - `最佳实践/应用功耗优化/前台任务低功耗/高效利用HWC的低功耗设计/bpta-utilize-hwc-efficiently`：同结论 + 建议避免交叠。
- **新增待验假设（H4）**：**「显示缩放」的 `.scale({x:S,y:S})` 是否让 XComponent 自渲染图层失去 HWC？**
  - 若失去 → 显示缩放在省 GPU 渲染成本的同时**增加了 GPU 合成成本**（此前"固定渲染分辨率、只变窗口大小 → FPS 近似"的实验**只变了窗口大小，没测 `.scale()`**，故未覆盖此问题）。
  - 判据：S=1 vs S=2 各抓一次 trace，看 `DrawImage(GPU)` 是否从 0 变非 0；并对比同帧时下 GPU 负载。
- **注意**：`.opacity()` 也在同一失效条件里（透明度 → GPU 合成）——**游戏窗上的任何 overlay 都要检查**（采样率 overlay 目前是 `Stack` 里的 `Text`，需确认不透明/不交叠）。

#### (j) 其它已评估但不用

| 能力 | 为什么不用 |
|---|---|
| `OH_NativeVSync`（`native_vsync.h`，含 `ExpectedRateRange` / `Create_ForAssociatedWindow`） | 帧率请求已实测 rc=0 无效（OS 仲裁）；MC 自带帧同步，桥不做帧驱动 |
| FFRT（`ffrt`，面向任务的 QoS） | MC 的关键线程是 **JVM 线程**，不是我们的 ffrt 任务；无法迁移 |
| `Graphic.Graphic2D.GL4` / `Vulkan` 系统库 | `libGLv4.so` 已在用；Vulkan 见 A6 |
| 游戏预启动 | 侧向（启动时间），见 (d) |

## 3. 候选路径（A–F）

> 全部可用现有**实验台零重编**起步（渲染 env / 额外 JVM 参数），只有 A 需要改桥 native。

### A. CPU 调度 —— 直击「单核性能不足」（官方最佳实践背书）

| # | 手段 | 落地方式 | 风险 |
|---|---|---|---|
| **A1** | **QoS**：把 MC 的 `Render thread` / `main` 提到 `QOS_USER_INTERACTIVE`（或 `QOS_DEADLINE_REQUEST`） | 在桥 native 里，于**目标线程必然经过的入口**做一次幂等设置：渲染线程走 `meowSwapBuffers` / `meowPumpEvents`；主线程走 GL/GLFW 入口。用 `pthread_getname_np`（或 JNI `Thread.currentThread().getName()`）判线程名 | 低（`-1` 即失败，可无操作降级） |
| **A2** | **绑核** `sched_setaffinity` 到大核 | 与 A1 同处；大核编号**已解 = `12-19`**（§6 P3） | 中（被系统覆盖可能反噬） |
| **A3** | A1 + A2 组合 | 官方范例即两者同用 | — |

**设计要点**：QoS 只能设"当前线程" ⇒ **必须由目标线程自己触发**；桥的入口天然满足（渲染线程每次 `glfwPollEvents`/`glfwSwapBuffers` 都会进我们的 native）。设一次即可（避免热路径反复调用）。

### B. 渲染栈（Zink / Mesa + 马良 GLES 反模式）

马良 GPU 官方文档（`最佳实践/GPU加速/马良GPU渲染优化/bpta-maleoon-gpu-best-practices`）里**直接命中我们**的几条：

> **Shader 编译（仅适用于 OpenGL ES）**
> 「Shader 的首次编译（`glCompileShader`，`glLinkProgram`）耗时长，若在应用运行时进行实时编译，容易引起卡顿和丢帧…**【推荐】**建议将 Shader 编译提前至应用启动时进行。」

> **Renderpass / OpenGL ES**
> 「一个 framebuffer 的 render pass 通常开始于该 framebuffer 被绑定为 `GL_DRAW_FRAMEBUFFER`…」
> 【推荐】render pass 开头加 `glClear`；不再需要的 attachment 调 `glInvalidateFramebuffer`。
> 【不推荐】来回切换 FBO；**在一个 render pass 内部调用 `glFlush` 和 `glFinish`**；**使用 `glReadPixels`（CPU 阻塞等 GPU 完成，破坏 CPU/GPU 并行）**。

> **Filtering**
> 「各向异性滤波和三线性滤波会降低纹理采样的性能。」
> 【推荐】仅在必要时使用 AF 和三线性滤波。

> **HEBC（马良独有硬件压缩）**
> 【推荐】GLES 侧条件：**纹理尺寸 > 32 且 ≤ 8192**；支持的 internal format 含 **`GL_SRGB8_ALPHA8` / `GL_RGBA8_OES`** …
> 【不推荐】把已压缩纹理 `glBindImageTexture` 到 image unit 后再 `imageLoad/imageStore`（触发解压且不再重压）。

> **Blend（仅 OpenGL ES）**
> 【推荐】Maleoon 920 及以上，**单三角形覆盖全屏**的场景才推荐 `EXT_shader_framebuffer_fetch`；其余场景「建议识别为 Maleoon GPU 时**关闭** framebuffer fetch」。

| # | 手段 | 说明 |
|---|---|---|
| **B1** | **Mesa 磁盘着色器/管线缓存落地**：`MESA_SHADER_CACHE_DIR=<沙箱可写持久目录>`；先用 `MESA_SHADER_CACHE_SHOW_STATS=1` **验证是否真在写/命中** | 零重编。命中马良文档"别在运行期编译 shader"的建议。若原先因目录不可写而静默不缓存 → 二次启动 + 首次进世界卡顿改善，**且可能削固定成本**。配套 `MESA_SHADER_CACHE_MAX_SIZE` |
| **B2** | **`GALLIUM_THREAD=1`（glthread）重开** | 已知**"确有显著帧数提升"**，唯一未定嫌疑 = 磁盘管线缓存（`MESA_SHADER_CACHE_DISABLE=true` 曾 50/50；glthread 单开 0/7）。**与 B1 是同一处代码路径** → 两条联合实验：① glthread + 缓存**禁用**；② glthread + 缓存**落可写目录**。这是目前**唯一还值得再赌一次的高收益项** |
| **B3** | 其它 Zink/Mesa 旋钮（实验台 A/B）：`ZINK_DESCRIPTORS=lazy`、`MESA_VK_WSI_PRESENT_MODE=immediate/mailbox`、`GALLIUM_HUD`（测量） | 已设：`vblank_mode=0`；**`GALLIUM_THREAD` 2026-09-14 起改为逐版本开关（默认开，走 OpenGLv4 时开；历史曾固定 `0`）** —— glthread 曾不可用，已由 GL guard 应用侧修复，见 [`glthread-GL-guard-方案.md`](glthread-GL-guard-方案.md) |
| **B4** | **复核我们自己的 GL 用法是否撞马良反模式** | ① 桥里 `egl_drop_surface()` 的 glthread drain `glFinish`（仅 glthread 时触发）—— glthread 关时 no-op，但**开 glthread 时正撞"不推荐"**，需重新评估；② `meowSwapBuffers` 的失败自愈路径有没有引入额外同步；③ 确认无 `glReadPixels` 热路径 |
| **B5** | MC 侧画质项：**关各向异性/三线性滤波**（对上马良 Filtering 建议） | 走 `options.txt` 预设（D2） |
| **B6** | `EXT_shader_framebuffer_fetch` 在 Maleoon 上的开关 | 属 MC/驱动侧，**观察项**：确认我们没主动启用它（gl4es / Mesa 路径可能自选）。不作结论 |
| **B7** | `glMapBufferRange` 带 `MAP_UNSYNCHRONIZED_BIT`（仅当确保无读写依赖） | 属 MC/驱动侧，**观察项**，不擅自改 MC |

**好消息（已在吃到的红利）**：MC 的纹理格式（`GL_SRGB8_ALPHA8` / `GL_RGBA8_OES`）与尺寸（大纹理 >32 且 ≤8192）**正好落在马良 HEBC 自动生效条件内** ⇒ 这部分带宽压缩红利天然生效，无需我们做任何事。**要避开的坑**：别把 MC 纹理绑到 image unit（会触发解压）。

## 5. 实验顺序与判据

> 原则：先动用现成实验台（**零重编**），把高收益低风险项打穿，再考虑改桥 native。

| 轮次 | 做什么 | 判据 | 重编？ |
|---|---|---|---|
| **R1** | **C1** `ActiveProcessorCount` A/B（6 / 8 / 10 / 自动） | 基线场景帧时 + 帧时抖动 | 否 |
| **R2** | **B1** 着色器缓存落地 + `SHOW_STATS` 验证是否命中 | 二次启动是否变快；命中后帧时是否降 | 否 |
| **R3** | **B2** glthread × 缓存策略（2×2：开/关 × 缓存禁/落可写） | 能否**既拿帧数又不崩**（唯一未定点） | 否 |
| **R4** | **A1** QoS（按线程名设 `QOS_USER_INTERACTIVE`） | 帧时 + 掉帧抖动 | **是**（桥 native） |
| **R5** | **A2** 绑核 A/B（不同 `CPU_SET` 组合） | 帧时；观测是否反噬 | 是 |
| **R6** | **C2/C3/C4** 对象头 / GC / AOT-CDS | 启动时间 + 卡顿计数 + 帧时 | 否 |
| **R7** | **D1/D2** mod 组合 + options 预设 | 直接 FPS | 否（launcher 侧一键安装） |
| **R8** | **H4** 显示缩放 × HWC 判定 | trace `DrawImage(GPU)` 是否由 0 变非 0 | 否 |

**每轮要求**：同一固定场景、同一世界/位置/视角；**A/B 单变量**；结论落 notes（`.logs/` 不是凭据，见 [`../../00-current/工程与规范.md`](../../00-current/工程与规范.md)）。

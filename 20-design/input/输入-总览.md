## 2. 当前上马方案

```
                        ┌─ 非 grab ─ 窗口级 mouse filter（150–500Hz 绝对坐标）
鼠标 ──┬─ ArkUI onMouse ─┤              local = displayPx − originPx
       │                │              → critical_send_cursor_pos（最新值槽）
       │                └─ grab ─ NDK 覆盖节点 NODE_ON_MOUSE（60Hz = UI 帧）
       │                           rawDelta → native 虚拟光标 → critical_send_cursor_pos
       │                           （meowGrabReset 已 no-op：指针真值只来自用户输入）
       └─ onKeyEvent/onAxisEvent → critical_send_* → SPSC ring
键盘 ─── Tab / F 行 ─ 窗口级 key filter（native 接管并自转发）→ critical_send_*
（其余键仍走 ArkUI 那两条路径；所有生产者共用同一个 ring）
                                              ↓
                    meowPumpEvents（每 glfwPollEvents 一次，渲染线程）
                                              ↓
                        GLFW JNI 回调 → Minecraft
```

| 环节 | 实现（关键位置） |
|---|---|
| 非 grab 直通 | native `meowMouseFilterStart(windowId, ox, oy, scale)`（`input_bridge.c`）；条件 `MOUSE_ACTION_MOVE && !env->grabbing && env->isInputReady` → `local = (displayPx − originPx) / S`（S = 显示缩放，1 = 原状）→ `critical_send_cursor_pos`；ArkTS `pushMouseMap`（`GameInputController.ets`）按 `(displayX − S·event.x)·sx` 反算原点、**仅在变化时重推** |
| 点击 | 仍走 ArkUI 绝对坐标（保证判定点正确） |
| grab | NDK 覆盖节点 `NODE_ON_MOUSE` → `OH_ArkUI_MouseEvent_GetRawDeltaX/Y` → native `meowGrabDelta`（虚拟光标在 native，仅 `env->grabbing` 生效）；ArkTS 侧 grab 分支已禁用；**grab 开始不再归中**（`meowGrabReset` 已 no-op，见下规则） |
| **规则：`ContentSlot` 单次绑定** | 同一 `ContentSlot` **只能绑一次**；`onSurfaceReady` 会多次触发，重复 `bindNodeContent` 会**叠加接收器**（实测 14–44 个）⇒ 同一事件被处理 N 遍 ⇒ **灵敏度随 resize 次数爆炸**（"窗口越小越灵敏"）。已用 native `g_boundContent` + ArkTS `overlayBound` 双保险 |
| 光标锁 | `OH_WindowManager_LockCursor(winId, **false**)` + `pointer.setPointerVisibleSync(false)`；失焦自动解锁 |
| 键/滚轮/字符 | ArkUI 事件 → `critical_send_key/mouse_button/scroll/char`（SPSC ring）；**IME 激活时**可打印键经 **`onKeyPreIme`** 在输入法之前转发（见 §2.2） |
| **Tab / F 行** | 由**窗口级按键 filter**（`meowKeyFilterStart/Stop`，`input_bridge.c`）在应用内部分发之前**消费并自转发**；否则这些键会走 ArkUI（Tab 的 UP 平台不下发 ⇒ 松手看不见）。释放由 native 的 tracked 表结算（Tab = `OH_Input_GetKeyState` 真值；F 行 = 和弦 deadline），驱动 = 游戏窗既有 16 ms 定时器调 `inputKeyTick`。见 §2.1 |
| 生产者线程 | **不止一个**：窗口级 filter 回调不在 ArkTS 线程上（实测一次会话 5 个 tid）⇒ `meow_ring_push` 用**叶锁**串行化（锁内不取别的锁、不回调）。消费者仍每代唯一 |
| 采集语义 | `critical_send_cursor_pos` 写**最新值槽**（非队列），每帧 `glfwPollEvents` 取一次 |
| IME | 隐形 `TextInput` + 焦点调度，**不参与鼠标路径** |

- **规则：grab 内只有 MOVE 事件可写光标槽** —— 节点接收器 `NODE_ON_MOUSE` 对**非 `MOVE`**（含 DOWN/UP）事件**不得**产出增量；否则按键坐标被抓取差分当成位移 ⇒ **每点一次左键视角漂 1px**（棘轮）。**2026-09-23 已修、用户实测通过**。根因与修法见 [`../launch/决策与不变量.md`](../launch/决策与不变量.md) §23。

- **规则：指针真值只来自用户输入**（不变量）—— 鸿蒙**无 warp / 光标归中 API** ⇒ **游戏发起的指针移动/归中一律 no-op**：`OHOS_WarpMouse` / `glfwSetCursorPos` / `meowGrabReset` **均不写我方光标槽、不发 motion**（**不"假装移动"**）。假实现会把 MC 的指针概念拖到窗口中心 ⇒ **ESC 后按钮不高亮、直接点击猛抬**。**2026-09-23 用户实机确认修复**（鼠标 ESC→返回游戏高亮正确、不猛抬；左键单击不步进；触屏与菜单正常）；接受残留（MC 原版 `accumulatedDX/DY`）见 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) §B7，完整根因见 [`../launch/决策与不变量.md`](../launch/决策与不变量.md) §24。

**已知天花板**：grab 采样 = **显示帧率档位**（动态 60 / 高 90，native 覆盖节点）；非 grab 已直通到 **150–500Hz**。

### 2.1 Tab 与 F 行：由窗口级按键 filter 接管（这两类键的"边沿"都不可信）

平台对这两类键**要么不派发边沿、要么派发的边沿反映的不是用户意图**，而它的**键状态**是准的：`OH_Input_GetKeyState(keyCode)`（`oh_input_manager.h`，API 12，**无需权限**）返回 `KEY_PRESSED / KEY_RELEASED`。这条判据是整个方案的支点 —— **事件只负责触发，状态与 deadline 负责真值**。

#### Tab：UP 从不派发 ⇒ 松手只能"问"

窗口级 filter（位于**应用内部分发之前**）实测：Tab 只有 `DOWN`（约每 52 ms auto-repeat 一次），**一条 `UP` 都没有**；同一接口上 ESC / W / 字母全部成对。而且**把 DOWN 消费掉也换不回 UP**（A/B 已证）⇒ UP 是在系统侧被扣掉的，与 ArkUI 走焦无关。

做法：Tab 由 filter **消费**（顺带使游戏窗内不再发生 ArkUI 走焦）并按 GLFW 语义自转发 `press / repeat`；**`release` 由 `OH_Input_GetKeyState(KEYCODE_TAB)` 判**，由游戏窗既有的 16 ms 定时器经 `inputKeyTick` 驱动 ⇒ 松手后 ≤16 ms 生效，**不需要任何约定值**。

#### F 行：和弦里的"按住"在平台侧不存在 ⇒ 由我们造

本机 F 行是**媒体键语义**，且**按下任第二个 F 键会让固件立刻放掉前一个**（实测；`kc=2092` = F3、`2093` = F4）：

```
16:36:26.932  F3 ↓  state=1     ← 平台知道按着
16:36:26.952  F3 ↑  state=0     ← 发 Up 的同一刻，平台自己的状态已变"松开"
16:36:26.953  F4 ↓  state=1     ← 2–4 ms 后伙伴键按下
（此后 F3 再无任何事件：不 repeat，也永不补发"真 Up"）
```

⇒ ① "**Up 紧跟另一个 F 键的 Down**"（实测 2–4 ms）是这个固件串行化的固定指纹；② 用户手指是否还按着 F3 **不可观测**（事件流与键状态都说"已松开"）—— 所以"按住 F3 才成立"的 MC 组合（1.19+ 的 **F3+F4 游戏模式切换器**）**只能由我们造出按住**。

做法（与 Tab 共用同一套内核：tracked 表 + `inputKeyTick`）：

1. F 行被 filter **消费并转发**；其余键一律 `return false` 走原 ArkUI 路径。
2. `DOWN` 归类：平台**自己发过 `UP` 之后**再来 = **新按下 → GLFW `PRESS`**；否则（平台的 auto-repeat：实测 ~51 ms 一次、**也是 `action=1`**，加上它的重复投递）= **GLFW `REPEAT`** ⇒ "同一次按下触发两遍"的老坑自然消失，不再需要"重复 Down 丢弃"。
3. `UP` **先压 20 ms 看窗口**（`MEOW_FN_UP_LOOKAHEAD_MS`；串行化间隔只有 2–4 ms，纯余量）：窗口内出现另一个 F 行键的 `DOWN` ⇒ 认作**和弦**，把前者**继续保持按下**；否则到点释放。
4. **和弦保持**由**任何 F 行事件**续期，**F 行静默 400 ms**（`MEOW_FN_CHORD_HOLD_MS`）后补发 `RELEASE`。语义 = "你还在动 F 行 = 我还按着 F3；停手 0.4 s = 你松手了"。
5. 尚未收到 `UP` 的 F 键由**系统键状态**兜底结算（与 Tab 同一判据）。
6. 和弦只在"**第二个 F 键出现**"时成立 ⇒ **F3 单键**（开关 debug 屏）与 **F3+字母/数字**（字母不在 F 行、不续期）这类点按型组合**完全不受影响**。

**唯一的约定值 = `MEOW_FN_CHORD_HOLD_MS`（400 ms）**，因为真松手不可观测；它失效的唯一前提是"第二个 F 键"这个指纹不成立。**把 F 行切成真功能键（Fn-Lock）后固件串行化消失、和弦路径根本不会触发，行为与桌面逐位一致。** 平台事实登记见 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) §A5 / §A9。

### 2.2 按键绑定看不到字母/数字/符号：用 `onKeyPreIme` 在输入法之前转发

**现象**：MC 菜单（含**按键绑定**界面）按字母/数字/符号无反应（方向/F 键正常）；游戏内打字正常。

**根因（官方机制）**：ArkUI 按键派发顺序 = ① `onKeyPreIme` / 页面快捷键 → ② **输入法（消费）** → ③ `onKeyEventDispatch` / `onKeyEvent` / 走焦。
菜单态我们**自动激活隐形 IME**（`pollGrabbing` → `scheduleImeForMenu`）⇒ 有输入框获焦、输入法打开 ⇒ **大多数按键（字母/数字/符号/空格）被输入法消费** ⇒ 既到不了 `onKeyEvent`（`handleImeKey` 收不到），也**在 native 窗口 filter 之下**（实测 `OH_NativeWindowManager_RegisterKeyEventFilter` 从未被调用）⇒ 任何"事后"转发都拿不到这些键。

**修法**：给隐形 TextInput 挂 **`onKeyPreIme`**（第 ① 步，输入法之前）——把 `toGlfwKey(kc) ∈ [32,126]` 且**无 Ctrl/Alt/Super** 的键 `sendKey` 转发给 MC，并 **返回 `false`**（不消费，输入法照常收字符做文本合成）⇒ **按键绑定与中文 IME 兼得**。
其余键（F/方向/编辑键/Esc/Enter）与组合键仍走原 `handleImeKey`/`handleKey`，**不双发**（`handleImeKey` 对可打印键仍按"纯文本"抑制）。

**规则（勿重蹈）**：
1. 在 `handleImeKey` 里"不再抑制可打印键"**无效** —— 键根本没到 ArkUI ✗。
2. **native 窗口级按键过滤**（`oh_window_event_filter.h`）**从未被调用**（字母/数字都看不到）⇒ 已删除 ✗。
3. 只有 **`onKeyPreIme`**（输入法之前）能拿到这些键；它逐个上报字母/数字/修饰/F 键（含 auto-repeat）。

**结果**：菜单中按键绑定 / 聊天 / 中文 IME 三者均正常。

### 2.3 触屏当鼠标（窗口级 touch filter，2026-09-21）

与已用的 mouse filter **同族**的窗口级 touch filter；开关 = 应用级设置 `touchAsMouse`（默认 **开**）。

| 手势 | 行为 |
|---|---|
| 单指按下 | 光标**跳到触点** + 左键按下 |
| 拖动 | 光标**跟随** |
| 抬起 | 左键释放 |
| 游戏内（grab）单指 | **故意不发左键**（那里拖动 = 转视角，发了会"一转就挖"） |

- **右键（使用/交互）**：**仅由虚拟按键覆盖层的「交互」键提供**；**`touchAsMouse` 开 + 覆盖层关时游戏内没有右键途径**（触屏手势不产生右键）。
- **多指同时在场：只认第一指驱动光标，其余手指忽略** —— 第一指按下即登记，在其抬起前任何后续落下的手指都不改光标 / 不产生位移 / 不发鼠标键；第一指抬起即注销，其余仍在场的手指**不接管**（要重新驱动须再按一次）。排除区手指（虚拟按键）不算「第一指」，故「按住方向键 + 另一指转视角」两指各司其职。实现见 `input_bridge.c` 的 `g_tDrivingFinger`（`meow_touch_filter`）。
- 实现：native `input_bridge.c` 的 `meow_touch_filter` / `meowTouchFilterStart` / `meowTouchFilterStop`；ArkTS `GameInputController.handleTouchMap` / `ensureTouchFilter`。
- **注册时机 = 桥就绪契约**：启动注册经 `whenBridgeSelected()` 等桥选定（**不读 `currentBridge()` 当前值判空**）；窗口 id 由 `ensureWindowId()` **统一懒解析**（鼠标 filter / 触屏 filter / `lockCursor` 同一份，**不再从鼠标事件派生**）；注册以 `touchFilterWinId` **幂等**（窗口/表面变化 `invalidateWindowId()` 清门后可重注册）。**旧写法**（读当前值 ⇒ 未选定即静默跳过 + 窗口 id 等鼠标 `Move` 才补）在**纯触屏设备上鼠标不动即触屏全废**（2026-09-29 修复）；契约与根因见 [`../../90-archive/多JRE共存-方案.md`](../../90-archive/多JRE共存-方案.md) §4 修订 2。
- **两条渲染链都支持**（26.3 Vulkan/SDL 与 26.2 GL/GLFW）。
- **游戏内破坏/攻击**：**单指手势不承担**（有意不发左键 ⇒ **转视角永不误挖**）⇒ **要挖请按覆盖层的「攻击」键**（走鼠标左键 0，实机可用）；**只有"触屏当鼠标开、覆盖层关"时游戏内没有挖的途径**。**手势方案（长按 / 按住不动 / 只靠按钮）尚未选**。
- **已定案暂缓**：触屏点「回到游戏」后视角朝点击侧瞬移一下 —— 机制与三条已试无效的修法见 [`已知限制与待解.md`](../../00-current/已知限制与待解.md) **§G2**（此处不复述细节）。

### 2.4 虚拟按键覆盖层（独立开关，2026-09-21）

开关 = 应用级设置 `touchControls`（默认 **关**）；独立于触屏当鼠标。

- **布局**：左下 **8 向方向键**（3×3、中心空）；右下 **3×3 缺左上两格** = 攻击 / 交互 / 跳 / 蹲 + 包(物品栏) + 左/右(物品栏前后切换 = 鼠标滚轮等价)；顶部 = ESC / 输入 / TAB；**按下高亮**（「输入」键语义见本节末尾）。
- **方向键语义**：网格内**按格判**；**网格外按"中心→手指"的极角量化到 8 向**（45° 扇区、5° 滞回）；中心格/无效 ⇒ **保持**当前方向；**仅 UP/CANCEL 释放** ⇒ 手指可按住在格间游走、也可滑出网格继续走。
- **虚拟按键不被当鼠标用**：覆盖层把按钮矩形（display px，**数据驱动**、随布局/缩放/边距自动跟随）上报给 native，touch filter 对**起手落在矩形内**的手指**整段手势跳过**（多指不串）。
- **尺寸**：单键边长与间隔各**一个常量**（`TOUCH_CONTROL_BUTTON_SIZE` / `TOUCH_CONTROL_GAP`）× 缩放百分比；四边距独立可调；**固定 vp + 分区锚定** ⇒ 抗窗口 resize / 折叠屏切换。
- **按键走既有桥原语**（`meowSendKey` / `meowSendMouseButton` / `meowSendScroll`），与物理输入同一套。
- 实现：`components/TouchControlsView.ets`（覆盖层）、`pages/GameWindow.ets`（挂载 + `.onTouch`）、`GameInputController.pressVirtual` / `scrollVirtual` / `setTouchExcludeRects`。
- **仅 grab 显示**：左下方向键簇与右下动作/物品栏簇**仅 grab（游戏内锁视角）时渲染**；顶部 ESC / 输入 / TAB **始终渲染**（不在门控内）。grab 状态传递链（**未新开定时器**）：控制器既有 `pollGrabbing` → `grabNative` → 新增公开 `isGrabbing()` → `GameWindow` 既有 100ms 定时器内 `syncGrabActive()` → `@Local grabActive` → 覆盖层 `@Param grabbing` → `@Monitor('grabbing')` 触发 `syncGatedRegionVisibility()`。
- **门控区的排除区**：共 **5** 个 region（0 方向键网格 / 1 右下簇 / 2 ESC / 3 输入 / 4 TAB）；被门控的两簇（0/1）**不可见时必须立即置 `valid=false` 并重报** ✓，否则会排除一片没有按钮的区域 ✗（菜单下半屏点不动 ✗）。
- **陷阱（卸载前必先释放按键）**：**摘除被门控的簇之前必须先释放所有按住的虚拟键** ✗ —— 否则 ① 节点消失后 `Up` 不再回来 ⇒ **原生键卡死**（角色一直朝那个方向走 ✗）；② `scheduleReport` 的"手势中延后"守卫（`dirFingerId >= 0 || pressedCodes.length > 0`）**永远为真** ⇒ **重报永不发出** ⇒ 刚失效的 region **永不重报** ⇒ **菜单下半屏持续被排除** ✗✗。⇒ 正确顺序：**先 `releaseAll()` → 再置 `valid=false` → 再 `scheduleReport()`** ✓（顺序不可换：不先释放，守卫就不放行）。另：同一处补了 `glfwToHmKey` 的 **258（TAB）** ⇒ 让 `releaseAllKeysUp()` 能兜住被按住的 TAB ✓。
- **补发释放必须带"各码自己的"原语（2026-09-28 修）**：`releaseAll()` 原先一律按 `isMouse=false` 补发 ⇒ `pressedCodes` 里混着的鼠标码（攻击 / 交互 = `GLFW_MOUSE_BUTTON_1/2` = 0/1）被当成**键盘**键发出 ⇒ **漏掉 mouse-up**、MC 侧那个鼠标键一直"按着"（离开 grab 收起动作簇 / 关窗时最容易撞上）。现由 `pressedMouseCodes`（`setPressed(code, isMouse, down)` 登记）逐码判原语；该数组**只**服务 `releaseAll()`，不参与渲染。
- **顶部「输入」键：非 grab 时拉起软键盘（2026-09-28，用户真机验证通过）**：语义**按 grab 分岔** ——
  - **grab（游戏内）**：发一次 `T`（`GLFW_KEY_T`），让 MC 自己开聊天框；MC 随即释放 grab ⇒ 既有轮询自动激活 IME。**与改动前行为一致**。
  - **非 grab（主菜单 / 服务器列表等任何 MC GUI）**：MC 不认 `T`，也**不会**自己弹软键盘 —— 它只把字符喂给自己画的 `EditBox`：`EditBox.setFocused → Minecraft.onTextInputFocusChange → TextInputManager.startTextInput → SDL_StartTextInput`，而我们的 SDL `ohos` 驱动侧**没有** `StartTextInput` / `SetTextInputArea` 入口（2026-09-28 核对：`tools/sdl/src/video/ohos/` 下零命中）⇒ 请求被丢掉；MC ≤26.2（GLFW）连这个请求都没有。⇒ 改由覆盖层**把隐形 IME 客户端拉起来**：`GameInputController.requestSoftKeyboard() → showSoftKeyboard()`，焦点落到 `ime-input` ⇒ 系统弹软键盘 ⇒ 打字经 `syncImeText` 进 MC 当前聚焦的输入框。
    - **焦点是唯一可用开关**：官方 FAQ「如何主动拉起软键盘」= `focusControl.requestFocus` 让输入框获焦、键盘自动弹起；而 `inputMethod` 的 `showSoftKeyboard()` 要系统级权限 `ohos.permission.CONNECT_IME_ABILITY`（三方应用拿不到）⇒ 走不通。
    - **焦点没有变化时系统不会重新绑定输入法**：菜单态 `imeActive` 往往已是 true（轮询自动激活过）⇒ 先 `focus('game-xc')`、下一个任务（10ms，`IME_REFOCUS_AFTER_CLICK_MS`）再 `focus('ime-input')`，制造一次真正的焦点变化；`imeActive === false` 时焦点必在 XComponent（`deactivateIme()` 末尾就把焦点还给它、开窗初值是 `defaultFocus`）⇒ 直接 `activateIme()` 即可。
    - **点击是"当刻"动作**：分支判定**现读 native grab 位**（`isGrabbingNow()`），不用 16ms 轮询缓存（否则刚进 / 刚出 grab 那一帧会走错分支、白点一次）；并**统一清掉 Esc 冷却**（冷却只为挡轮询抢焦点，不该挡用户显式动作）。
    - **自证行**（tag `GameInput`）：`soft keyboard: activate` / `soft keyboard: refocus`，以及页面 `ime-input` 的 `ime-input focus` / `ime-input blur`（`FocusController.requestFocus(key)` 在 SDK 里返回 **`void`**，无法用返回值判成败，只能靠 onFocus/onBlur 观测焦点是否真落地）。**只有前者、没有 `ime-input focus` = 焦点请求被系统拒了** ⇒ 键盘不会弹。
    - 该键**不再发键**：高亮态独立（`softKeyboardDown`），不放进 `pressedCodes` —— 否则 `releaseAll()` 会补发一个凭空的多余键 UP。region 仍是 index 3，排除区逻辑不变。

- **系统返回 ⇒ ESC（游戏窗内）**：「返回」等效按一次 **ESC** —— 对本工程 MC，ESC 语义天然统一（grab 里 = 开菜单、菜单里 = 关菜单）。实现（均**加法式**，未新增桥 / pipeline）：`pages/GameWindow.ets`（`@Entry` 页面）新增 `onBackPress(): boolean` ⇒ 调 `this.input?.sendEscapeTap()` ⇒ **返回 `true`**（消费系统返回、应用不退出）；`common/input/GameInputController.ets` 新增公开 `sendEscapeTap()` ⇒ 内部 `pressVirtual(256, false, true)` 紧接 `pressVirtual(256, false, false)`（与顶部虚拟 ESC 键**同一条路**；256 = `GLFW_KEY_ESCAPE`）。**返回手势在 grab 与菜单里都发 ESC**（**不加 grab 门控**，有意）。未动：顶部 ESC 按钮 / native / 设置层。
- **平台事实**：**OHOS 全屏游戏窗口下，系统的「边缘返回手势」确实会派发到 `@Entry` 页面的 `onBackPress()`** —— 返回 `true` = 页面自处理、消费掉、应用不退出。官方 FAQ `faqs-arkui-531` / `faqs-arkui-553` 佐证「仅 `@Entry` 组件生效；返回 true = 页面自处理、不路由」⇒ 全屏应用要拦返回有据可依。

### 2.5 本轮踩坑（勿重蹈）

1. **网关接线**：新增桥方法要**六处齐全**（native 实现 / NAPI `desc[]` / `.d.ts` / `Index.ets` 导出 / `JvmLauncher.ets` 类型 / 调用点）；漏 `Index.ets` 导出 ⇒ 运行期 `?.` **静默失效**（日志里"一条都没有"）。
2. **高频/手势中途路径收拾状态**：`touchFilterStart` 会被 ArkTS **每次触摸**调用（刷新原点/缩放/灵敏度）；把"复位手势状态"放进去 ⇒ 手势进行中每 ~100ms 清零 ⇒ **划视角乱飞 + 按虚拟键同时动视角**。同理"重设排除区时清手指表"也会中途解封按住的手指。**治本** = 复位只在会话边界；排除区快照不碰手指表。
3. **公式因子**：把转视角的系数从"`g_touchSens × g_grabSensitivity`"改成只留前者 ⇒ 手感突变。**两个因子都要留。**
4. **用闸门挡真输入**：曾用 `onTouch` 计数去屏蔽 `onMouse` ⇒ 真鼠标左键全失效（官方文档：单指可响应的触摸事件**均可由鼠标左键操作响应** ⇒ 鼠标点击也会触发 `onTouch`，无法据此区分）。

## 3. 量化对比（为什么"同为 60fps 更不跟手"）

| 段 | 我们 | 桌面 |
|---|---|---|
| 输入投递 | 非 grab **1–2ms**（filter）；grab **= 显示帧间隔**（60Hz≈16.7ms / 90Hz≈11.1ms，native 节点） | ~1–8ms（raw input） |
| 帧内取用 | ≤1 帧（每帧取一次最新值） | ≤1 帧 |
| 渲染 | **Zink（GL→Vulkan 翻译层）**，偶发 20–70ms 尖刺 | 原生 GL 驱动 |
| 上屏/合成 | 浮动窗合成，queue 容量 5（swap 不阻塞：avg 0.5–11ms） | flip / 独占可省 1 帧 |
| **合计粗估** | **~70–90ms** | **~45–60ms** |

**60fps 上限 = 系统刷新率档位**（"动态" = 60；系统设"高" = 90 时 MC FPS>60），**不是 MC 侧自限**（强制 60→90 实验无变化，已证伪）；
`eglSwapBuffers` 不阻塞 ⇒ 也不是合成器背压。详见 [`输入延迟调查证据.md`](../../90-archive/输入延迟调查证据.md) §7.13/§7.14。

### 4.2 鼠标滚轮归一化

- **现象**：游戏里滚一格"飞很远"（菜单瞬间滚没）。
- **根因**：ArkUI `AxisEvent.getVerticalAxisValue()` 单位是 **vp**（一格远大于 1），原样转发（且 native ring 为 `int`、`(int)yoffset` 会截断小数）⇒ 一次轴事件在 MC 里 = 一大截滚动。
- **修**：`GameInputController.handleAxis` 除以常量 `SCROLL_VP_PER_NOTCH`（`common/constants/Constants.ets`，**15**）归一化到 GLFW/桌面约定，**再乘"滚轮速度"倍率**；因 native ring 为 `int`，用 `pushScroll` **累计成整数"格"**再下发（小数留在累加器）。手感：`15` 刚好。
- **可调**：高级选项「滚轮速度 (%)」= 全局设置 `global.launcher.scrollSpeed`（应用沙箱 `app-settings.json`；默认 **100** = 1.0×；主进程写、游戏进程读，**开窗生效**；见 [`../launch/实例设置存储-方案.md`](../launch/实例设置存储-方案.md) §3.2）。

# 下载器可靠性方案（下载原语收尾 + 批量中断 + 零拷贝写盘）

> 触发：PR #1（`1d4f8df`）把 `streamToFile()` 改成「`dataEnd` + 状态码回调都到齐才 resolve」，并加了 1 MiB 攒批写盘、并发 6→16。
> 该 PR 修掉了「404 错误页被当 jar 落盘」，但引入/暴露了三类问题。本文给**可实施、可验收**的修复方案。
> 范围：`entry/src/main/ets/common/data/Downloader.ets`、`VersionInstaller.ets`（`runDownloads` 及其上游）、`DownloadContract.ets`。
> 不在范围：`tools/jre25`（已废弃，走 jre26）、UI 取消按钮的交互设计、镜像选择策略。

## 0. 事实基线（先说清楚哪些是查证过的）

| 问题 | 结论 | 证据等级 |
|---|---|---|
| `requestInStream` 回调返回什么 | 只返回响应码（`number`），不返回 body | 文档明确 |
| 回调何时触发 | 隐含在「拿到状态/响应头之后、body 结束之前」 | **推断**（文档没写时序） |
| 回调是否恰好一次 / 是否可能在 `dataEnd` 之后 | 未定义 | **未知** |
| `dataEnd` 对**零长度 body** 是否一定触发 | 无保证（当前挂起现象即为反证） | **未知**（文档只说「数据接收完毕」） |
| `dataEnd` 是否在错误状态码时触发 | 无定义；描述是「body 接收完毕」而非状态相关 | **未知** |
| `destroy()` 在回调内调用 | 文档示例就在 `dataEnd` 里 destroy；但 destroy 是否可能同步再触发一次回调、是否可能抛 | 半文档/未知 |
| `readTimeout` 语义 | API 参考写「读取超时」，开发指南写「从请求开始到结束的总时间」 | **自相矛盾** |
| `writeSync` 签名 | `writeSync(fd, buffer: ArrayBuffer \| string, options?: WriteOptions): number`，返回**实际写入字节数** | 文档明确 |
| `WriteOptions.offset` | 「期望写入文件位置」= **绝对文件位置**（`pwrite` 语义），不是 buffer 内偏移 | 文档 + 6.1 源码（`write_core.cpp` → `uv_fs_write`）+ FAQ 三者一致；SDK d.ts 注释「filePointer plus offset」与实现不符，**以实现为准** |
| 不传 `offset` 时是否推进 fd 位置 | 会（`offset = -1` → `write(2)`，当前位置写并推进） | 文档 + 源码；且现网已用该路径并通过 sha1 校验（经验证） |
| `writeSync` 是否接受 `Uint8Array` | 否，只接受 `ArrayBuffer`/`string`，否则 `EINVAL` | 文档 + 实现 |

**由此得到两条硬约束**（后文方案必须满足）：

1. **不能用 `{ offset: 0, length: n }` 做「零拷贝」** —— offset 是绝对文件位置，每次 flush 都会写回文件头，且 fd 位置不推进，文件必然被覆盖损坏，而 `writeSync` 还返回成功。
2. **零长度 2xx 不能靠等 `dataEnd`** —— 等不到就是永久挂起。

## 1. 缺陷清单（已核验，含 file:line）

### 1.1 下载原语（`Downloader.ets`）

| ID | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| D1 | 2xx + 无 body（204 / 205 / `Content-Length: 0`）走 `finalize`，但 `streamEnded` 永远为 false → 永不 settle | `131-134`、`227-234` | **永久挂起**：文件不关、请求不销毁、worker 不返回、`installingId` 永不清空；`readTimeout` 不可靠（语义矛盾 + 无 pending 读时可能不触发） |
| D2 | 写失败只 `return`，不 `destroy()`、不 settle，仍等 `dataEnd`+状态码 | `164-166`、`132` | 磁盘满时把整个 body 传完才报错；若无 `dataEnd` 则挂起 |
| D3 | 写失败后 `finalize` 仍会再 `flush()` 一次 | `136`、`103-115` | 重复失败写；`pendingLen` 在失败时未清零 |
| D4 | `writeSync` 返回值被忽略，成功后无条件 `pendingLen = 0` | `111-112` | **短写静默丢数据**（文件尾丢失，仅靠 sha1 事后发现；空 sha1 的安装器直接接受损坏文件） |
| D5 | `closeSync` 异常被吞 | `120-123` | 关文件失败仍报成功（ENOSPC 常在 close 才暴露） |
| D6 | `requestInStream` 同步抛未包 try | `213`、`155` | 已 open 的 fd 泄漏、请求不销毁 |
| D7 | 无「已收字节 vs 声明长度」账目 | `163-193` | 截断响应（传输层给 `dataEnd`）会被当成功；空 sha1 调用点（`VI:1151/2259/2517`）尤其危险 |
| D8 | `dataReceiveProgress` 无终态守卫；`totalSize<=0` 时完全绕过节流 | `196-206` | settle 后仍回调 UI；无 Content-Length 时回调风暴 |
| D9 | `cleanup()` 里 `request.destroy()` 无 try | `127` | destroy 抛异常时（`finished` 已置 true）既不 resolve 也不 reject → 挂起 |
| D10 | 失败路径把**本地 I/O 错误**当远端错误，继续试下一个候选地址 | `268-272` | 磁盘满时把整套镜像都试一遍 |
| D11 | 每次 `streamToFile` 无条件分配 1 MiB staging（含 404/空响应） | `98` | 16 并发常驻 16 MiB；3000 个小资源产生 ~3 GiB 分配churn |
| D12 | `flush()` 为裁剪尾部，每次 `new ArrayBuffer(pendingLen)` + `set()` 全量复制 | `108-109` | 100 MiB 文件复制 100 MiB；16 并发 = 1.6 GiB 纯搬运 + 1.6 GiB 零填充 |

> 说明：**D1 只影响成功路径**。非 2xx 与 `err` 回调是立即 reject 的（`219-232`），不需要等 `dataEnd` —— 这点 PR 做对了。

### 1.2 批量下载（`VersionInstaller.ets` `runDownloads`）

| ID | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| R1 | `Promise.all(workers)` 一失败即 reject，其余 worker 不中断，继续领新任务、继续建目录、继续写盘 | `582-610` | 失败后仍有最长全量剩余的下载在跑；16 并发下最多 15 个请求/句柄常驻 |

| R3 | 计数只有 `done++`，失败时无终态通知；孤儿 worker 继续 `onCount` | `601-602`、`610` | 失败后进度仍在涨，可覆盖**下一次安装**的进度（同一 `InstallerState` 字段） |

| R7 | 直接 `downloadFile`（安装器 jar）与 `fetchText` 不在 `runDownloads` 里 | `VI:1151/2259/2517`、`DL:50-78` | 取消/中断若只做在 worker 池里，这些阶段免疫 |

## 2. 目标与不变量

### 2.1 目标
1. 任何一次下载**有界时间内恰好 settle 一次**（成功或失败），不存在「永久 pending」。
2. 非 2xx 永不被当成功（PR 的收益必须保留）。
3. 本地 I/O 错误**立即失败**并释放资源，不浪费带宽。
4. 一次批量失败后，**不再产生任何目的路径写入**。
5. 写盘不做无谓的全量复制。

### 2.2 不变量（验收时逐条对照）

| ID | 不变量 |
|---|---|
| I1 | 每次下载恰好 settle 一次 |
| I2 | settle 前文件必已关闭；close 失败不得报成功 |
| I3 | settle 后不再有任何写；成功路径不残留未落盘字节 |
| I4 | 失败路径不留 `.part` |
| I5 | 成功必须「最终状态码 2xx」且「body 完成已证明」；两者不可互相替代 |
| I6 | body 完成只由三件事证明：204/205、已知长度已收满、`dataEnd`；**静默不算完成** |
| I7 | 每次下载有上界（总时限 + 空闲时限） |
| I8 | settle 后不再回调进度；`totalSize<=0` 视为未知，不算百分比 |
| I9 | 本地 I/O 错误终止候选列表，不跨镜像重试 |
| I10 | 所有终态路径都销毁请求并摘掉回调 |
| I11 | 收到的每个字节都落盘，或明确失败 |
| I12 | rename 前完整性策略（sha1/大小/类型）已满足 |

## 3. 方案 A：下载原语状态机（对应 D1–D10）

### 3.1 状态

`OPENING` → `AWAITING_STATUS` → `AWAITING_BODY` → `BODY_COMPLETE` → `CLOSING` → `SETTLED_OK | SETTLED_FAIL`

终态 `SETTLED_*` 之后所有事件只记 debug 日志。

### 3.2 关键守卫

- **状态码守卫**：最终码 ∈ [200, 300)。**先判状态码，再判 body** —— 这一条保证 404 页永不被接受。
- **零 body 守卫**：码为 204/205，或已知声明长度为 0 ⇒ **body 视为已完成**，立刻进 `BODY_COMPLETE`，不等 `dataEnd`。
- **长度守卫**：已知声明长度 > 0 时，收满即 `BODY_COMPLETE`（不强行等 `dataEnd`）；`dataEnd` 时若已收 < 声明长度 ⇒ 长度不符失败。
- **写健康守卫**：`writeError` 置位即进 `CLOSING`，不等 body/状态。
- **终态守卫**：`finished` 同时门控 `dataReceive` / `dataEnd` / 进度 / 状态回调。

### 3.3 三个必须回答的边界

| 场景 | 现状 | 目标行为 |
|---|---|---|
| 204 / `Content-Length: 0` | 挂起或产出 0 字节文件 | 立即 `BODY_COMPLETE` → 走**空产物策略**（见 §3.4）→ 拒绝 |
| 200 chunked 但终止块永不发 | 挂起 | 空闲看门狗到期 → 失败（**不猜成功**） |
| 302 未跟随 / 304 | 非 2xx → 失败 | 不变（=正确） |

### 3.4 空产物策略（需拍板，见 §8 D1）

当前所有调用方（jar / library / asset）**都不可能合法地是 0 字节**。建议：`downloadFile` 在 rename 前断言「文件非空」，否则按失败处理并试下一个候选。这样 204 既不会挂起，也不会产出空 jar。

### 3.5 写失败快速失败（对应 D2/D3/D4/D5/D9）

首个写失败时的**严格顺序**：
1. latch `writeError`（此刻起丢弃所有后续字节，不再尝试写）；
2. 置 `finished`（所有回调变 no-op）；
3. 摘回调（尽力）；
4. `destroy()`（尽力，包 try）；
5. `closeSync`（尽力，包 try；失败只记日志，不覆盖主错误）；
6. 立即 reject —— **不等** `dataEnd` / 状态码。

短写：比较 `writeSync` 返回值与请求长度；不等则按写失败处理（`WriteOptions` 没有 buffer 偏移，无法安全续写同一 buffer 的后半段）。

`requestInStream` 同步抛：走同一套 `CLOSING` 收尾（关 fd、destroy、reject），不得泄漏。

### 3.6 错误分类与重试策略（对应 D10）

| 类别 | 例 | 试下一个候选？ |
|---|---|---|
| 远端状态 | 非 2xx / 最终 3xx | 是 |
| 远端传输 | 回调 `err`、连接重置、超时 | 是 |
| 远端完整性 | sha1 不符、长度不符、空产物 | 是 |
| **本地 I/O** | open/write/close 失败、ENOSPC、EACCES | **否**（终止候选列表） |
| 调用方契约 | 非法路径、非法期望哈希 | 否 |

### 3.7 时序兜底

不要只依赖 `readTimeout`（语义矛盾）。建议加**应用层双时限**：总时限（按文件大小估算 + 余量）+ 空闲时限（每次收到字节重置）。到期 → `CLOSING` → 失败。具体数值走**需拍板**（§8 D5）。

### 3.8 日志（16 并发下必须能定位到文件）

每行至少含：关联 id（可用 `destPath` 的短哈希）、目的路径、候选序号、状态码、声明长度（已知/未知）、已收字节、已落盘字节、pending 字节、耗时、错误码/消息。
每个下载**恰好一条结算行**（成功 xor 失败），且不得因日志抛异常影响结算。

## 4. 方案 B：批量中断与计数（对应 R1–R7）

### 4.1 取消令牌模型

- **一个 `InstallSession` 一次安装**，由 `InstallerState` 持有；内含：令牌、会话代号（generation）、逐项状态表、首个错误、终态通知闩、计数。
- 令牌是一次性的三态：`active / aborting / settled`；**首个原因不可变**（用户取消 / 首个 worker 失败 / 被新会话顶替）。
- 令牌**跨阶段存活**（元数据 → 安装器 jar → 库批 → 资源批 → processor 阶段），不是每个 `runDownloads` 一个。
- **退出时机关**：令牌只有在「所有 worker/阶段 settle + 清理完成 + 终态通知已发 + 锁已释放」之后才退休。用户点取消**不立即释放 `installingId`**，先进入「取消中」。
- **代号过滤**：所有进度回调带会话代号，非当前代号的回调直接丢弃 —— 这是防止「旧会话写坏新会话进度」的唯一可靠手段（复用现有 `fabricLoaderSeq` 那套模式）。

### 4.2 传播点（缺一不可）

| 层 | 检查点 |
|---|---|
| 安装入口 | 开跑前；各阶段之间 |
| `runDownloads` | 生成 worker 前、worker 入口、**领 index 前**、每次 await 后、报完成前 |
| `downloadFile` | 每个候选前、`hash` 前后、**删除 dest 之前**、`rename` 之前 |
| `streamToFile` | 注册 abort 监听：置 `finished` → close fd → `destroy()` → reject（走同一套 CLOSING） |
| 直接下载（安装器 jar） | `VI:1151 / 2259 / 2517` 必须也带令牌 |
| `fetchText` | 至少阶段边界可控（其内部不可中断，超时兜底） |
| processor 循环 | 每步前检查；子进程（`:neoinstall`）需 kill/等待 |

### 4.3 语义决定

| 事件 | 调度 | 在飞行 | 对外错误 | 计数 |
|---|---|---|---|---|
| 首个 worker 失败 | 立刻停止领新任务 | **立刻中止**（不「让它下完」） | 首个错误 + 条目标签 | failed=1，claimed 未提交计入 aborted |
| 用户取消 | 立刻停止领新任务 | 立刻中止 | 取消原因（无下载错误） | 已完成保留，未提交计 aborted |
| 取消后再出错 | 已停 | 已中止 | 取消仍为终态，晚到错误只记日志 | 不改写原因 |

**为什么在飞行任务要中止而不是「让它下完」**：`downloadFile` 没有 Range/续传能力（`DL:248-253`），放行只能多救一个文件，却要一直占着 fd/socket 到 120 s 读超时，而且它可能在失败上报之后仍 rename —— 直接违反 I「上报后不再写目的路径」。

### 4.4 收尾顺序（这是 R2 的根因修复）

必需顺序：

1. 令牌 → `aborting`，记录首个原因；
2. worker 停止领新 index；
3. abort 监听关闭 fd、销毁请求；
4. 每个 `downloadFile` 在删 dest / rename 前**最后一次**检查令牌；
5. **等待所有 worker settle**（`allSettled`，不是 `Promise.all`）；
6. 清理不完整实例 / `.part`；
7. 发终态通知；
8. 上报失败/取消，释放锁。

> 第 5 步之前**绝不能**调 `removeIncompleteInstance` —— 这正是 R2。

### 4.5 `.part` 与已完成文件

- **`.part` 一律删除**（无续传能力，留着只会被下一次或并发会话截断）；删除范围限定本会话拥有的项，不做全局扫描。
- **已完成的目的文件保留**：资源是内容寻址、库是 Maven 寻址，`isDownloaded` 会跳过，重试成本最低。
- `cacheDir` 里的安装器 staging **保留**（下次会重新校验/解压，`CC` 可手动清）。

### 4.6 计数与进度契约（对应 R3）

终态必须满足：
- **恰好一次**终态通知（在全部 settle + 清理之后）；
- `done` = 已提交项（安装前就存在 + 成功 rename），**不含** aborted；
- 另给 `aborted` 计数；
- 终态原因：`completed / failed / canceled`；
- `current` 清空、字节进度归零；
- 不伪造 100%。

### 4.7 与 16 并发的关系

一个布尔量「循环顶部检查」不够：它只阻止**新**任务，已经建起的 16 个请求会活到超时。中止必须**主动** destroy/close，并且要在释放安装锁之前等它们全部 settle，否则重试会再加 16 个句柄（`VI:543-545` 已记录 fd 耗尽风险）。

## 5. 方案 C：零拷贝写盘（对应 D11/D12）

### 5.1 结论

**可行，但不是 `{ offset: 0 }`。**

| 方案 | 安全性 | 复制 | 判定 |
|---|---|---|---|
| 现状（复制到新 buffer） | 安全 | 全量 | 可接受但浪费 |
| `{ offset: 0, length: n }` | **会毁文件** | 0 | **禁止** |
| `{ length: n }`（不带 offset） | 安全 | **0** | **推荐** |
| 缩小 buffer（256 KiB） | 安全 | 总量不变 | 仅降内存，系统调用 ×4 |
| 清零 buffer | 无意义 | 0 | 否决 |
| staging 懒分配 | 安全 | 无收益（首个分片即分配） | 可叠加，省空响应的 1 MiB |

### 5.2 推荐做法

- 保留 `staging: ArrayBuffer` 与 `pending = new Uint8Array(staging)` 两个变量分开持有（`pending.buffer` 只在 view 的 `byteOffset === 0` 时才等价，显式分开可避免以后踩坑）。
- flush 时：`fileIo.writeSync(fd, staging, { length: pendingLen })` —— 无 `offset` ⇒ 走 `write(2)` 当前位置写并推进 ⇒ 连续 flush 自然追加。
- 检查返回值：`written !== pendingLen` ⇒ 按写失败处理。
- `staging` 懒分配（首个 `dataReceive` 才分配），顺带省掉空响应/404 的 16 MiB 常驻。
- `flush()` 入口加 `writeError !== null` 守卫（顺手修掉 D3）。

### 5.3 收益（100 MiB × 16 并发估算）

| 指标 | 现状 | 改后 |
|---|---|---|
| flush 次数 | 100/文件，1600 总计 | 同 |
| 临时 buffer 分配 | 100/文件（+200 view） | 0 |
| 纯搬运复制 | **1.6 GiB** | 0 |
| 零填充 | ~1.6 GiB | 0 |
| 常驻内存 | ~32 MiB | ~16 MiB（叠加懒分配后，全 404 场景为 0） |

### 5.4 上线前必须实测（禁止纸上结论）

1. 连续多次 `{ length }` 写入后 sha1 匹配，**特别是最后一次部分 flush**；
2. 第二次 flush 确实紧跟第一次（验证没有变成 pwrite）；
3. **负向验证**：`{ offset: 0 }` 在真机上确实覆盖文件头（证明语义判断正确）；
4. `writeSync` 接受 `ArrayBuffer` 并返回 `pendingLen`；直接传 `Uint8Array` 应 `EINVAL`；
5. 注入短写/ENOSPC，确认被当作失败而不是静默接受；
6. `length > buffer.byteLength` 应 `EINVAL`；`length = 0` 应为 no-op；
7. 16 并发 100 MiB 对比峰值 RSS 与耗时；
8. `2in1 / tablet / phone` 三类设备各跑一遍（ANI 实现可能不同）。

## 8. 需拍板的决策点

| # | 决策 | 结论 |
|---|---|---|
| D1 | 空产物（0 字节）是否一律拒绝 | **已定：拒绝**（本产品不存在合法的 0 字节下载物）。不加 `allowEmpty` 参数，不为不存在的需求留分支 |

## 9. 残余风险（无法完全消除，只能缓解）

| 风险 | 缓解 |
|---|---|
| 回调/`dataEnd` 时序未文档化，可能随 API 版本变化 | 所有终态路径打日志；测试矩阵覆盖；看门狗不依赖库事件 |
| 看门狗误杀慢速网络 | 空闲时限按"收到字节即重置" + 独立总时限；日志记"距上次收到字节的时长" |
| `readTimeout` 语义矛盾 | 不把它当唯一活性保障，显式设置并叠加应用层时限 |
| `destroy()` 重入/抛异常未文档化 | 先 latch 终态再 destroy；destroy 包 try；所有 handler 加守卫 |
| 镜像返回 200 + 错误页 | 强制 sha1 或期望大小；安装器额外校验 ZIP 魔数/结构 |
| 长度被服务端欺骗 | 收满或超出声明长度即判失败；最终以 sha1/大小为准 |
| close 不保证落物理盘（无 fsync API） | 依赖 size/sha1 校验；进程被杀由下次启动清 `.part` |
| 进程被杀留下 `.part`/fd | 每次尝试前先删 `.part`（已有）；启动时清理 |

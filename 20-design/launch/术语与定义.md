# 术语与定义：启动链 / 安装链

> **用途**：本目录（`20-design/launch/`）里出现的**专业名词**的**唯一权威定义**。凡总览 / 环境 / 决策档用到某名词，都在这里定义一次；别处一律"见 [`术语与定义.md`](术语与定义.md) §x"——**不在别处重复定义**。
> **边界**：只定义**启动链 / 安装链**用到、且能在**代码或日志**里找到落点的名词。渲染数值 / 性能 / 输入等其它主题的术语见各自目录。
> **代码路径相对 `Harmomeow-Craft-Launcher/entry/src/main/ets/`；只引符号名（文件 / 函数 / 常量），不写行号。**
> **读法**：每个词条固定六段 —— **定义**（一句话、精确到可判定）→ **形式化**（字面形态 / 集合 / 判据 / 真值表）→ **如何观测**（确切日志串或命令）→ **为什么这样**（设计动机）→ **易混点** → **落点**（`文件 + 函数/常量名`）。部分词条另附 **例** —— **真实材料逐字引用 + 出处**（长串用 `…` 截断但保留首尾关键项），只服务理解、**不作定义**。术语可互相引用（`见 §A.3`），但**不循环定义**；实例级三形态对照见 §G。

## §0 记号约定

- `-cp` / `-p` 等以 `-` 开头者 = JVM 命令行选项的**字面形态**。
- 形式化里 `X ⇒ Y` 读作"X 成立时判为 Y"；`⇔` 读作"当且仅当"。
- `A ∩ B` / `A ∪ B` 是**集合**意义的交 / 并；`|S|` = 集合 S 的基数。
- `<…>` 是**占位**（替换为实际值）；`"…"` 内为**字符串字面量**，须逐字匹配。
- 真值表列出的每一行都互斥且穷尽（MECE）。
- `例` 块里的路径以**工作区根**为基准：设备日志 `Harmomeow-Craft-Launcher/.logs/<文件>`、测试实例 `stuffs/test-forge/…` 或 `stuffs/test-fabric/…`、证据件 `stuffs/research/forge-support/evidence/…`、源码 `Harmomeow-Craft-Launcher/entry/src/main/ets/…`；`<cacheDir>` = 设备应用缓存 `/data/storage/el2/base/haps/entry/cache`。

## §A classpath 三态与形态

### A.1 classpath（classpath / `-cp`）

**定义**：JVM 启动时查找**用户类**（`java.class.path`）的**条目集合**；条目之间用 `:` 分隔，条目是"jar 文件 / 目录 / 含通配符的目录"。

**形式化**：`-cp` 的**值**是单个字符串 `v`；`v.split(":")` 得到条目列表。合法条目 = ① jar / 目录的绝对路径；② 以 `/*` 结尾的目录通配（§A.2）；③（本工程不用）相对路径。**"形态"由条目列表的字面形状判定**（见 §A.10）。

**如何观测**：日志 `classpath mode=<real-tree|ordered|flat> (entries=N, bytes=M)`（真树 / 有序形态）与 `classpath mode=flat`（平铺形态）；`entries` = `v.split(":").length`，`bytes` = `v` 的 UTF-8 字节数。

**为什么这样**：鸿蒙的 JLI 移植对**超长 `-cp`** 有上限（数千字符以上会失效），故"条目多"时不能逐条展开（见 §A.3）；而加载器的"能不能按自身位置反推库根"又要求逐条真实路径（见 §A.6）——两种诉求并存，正是**三态**存在的根本原因。

**易混点**：与 `-p`（module path，§C.1）是**两套独立的查找路径**，不可混用：`-cp` 承载用户类，`-p` 承载命名模块。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`、`assembleRealTreeClasspath`、`assembleClasspath`。

### A.2 通配展开语义（wildcard expansion）

**定义**：`-cp` 条目里的 `<dir>/*`（"目录通配"）由 JVM 在**启动时**展开为 `<dir>` 下**所有 `.jar` 的绝对路径**；**展开结果的顺序由文件系统决定，与 classpath 串里书写的顺序无关**。

**形式化**：`<dir>/*` ⇒ `{ p | p ∈ listdir(<dir>) ∧ p 以 ".jar" 结尾 }`。JDK 8 的实现（`FileList_expandWildcards`）**逐条目原地插入、不排序** ⇒ 顺序 = 目录项枚举序（`readdir`）⇒ 同一 `<dir>` 在同一文件系统上的顺序可复现，但**不跨设备、不跨重装保证，且不同名 jar 之间没有任何"声明顺序"语义**。

**如何观测**：无法从命令行直接打印展开结果；但**后果**可见：① `classpath mode=flat` 说明走了通配；② 同名类被 ≥2 个 jar 提供时，日志 `classpath duplicate class: <类> provided by <jarA> + <jarB> (first in classpath wins)`——`first` 即**枚举序的首个**，而非清单里靠前的那个。

**例**（`1.12.2-Forge-OptiFine` 的**平铺**期）：`-cp` 只是一个通配条目

`-cp /data/storage/el2/base/haps/entry/cache/mc-cp/1.12.2-Forge-OptiFine/*`

（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790788363-hilog.txt` 的 `CMD:` 行，配套 `classpath mode=flat`）。该实例的 Forge 与 OptiFine **都**提供 `net/minecraftforge/common/model/TRSRTransformation.class`，于是日志出现：

`W classpath duplicate class: net/minecraftforge/common/model/TRSRTransformation.class provided by forge-1.12.2-14.23.5.2864.jar + OptiFine-1.12.2_HD_U_G6_pre1.jar (first in classpath wins)`

（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790831197-hilog.txt` 的 `classpath duplicate class:` 行）。
**从这个例子里应当看出**：`*` 展开后谁先命中**不写在 `-cp` 里**，而由目录枚举序决定——所以"两个 jar 抢同一个类"在这种写法下没有可复现的胜者（这正是 §A.5 改显式有序列表要解决的事）。

**复现/观测**：`grep -F "mc-cp/1.12.2-Forge-OptiFine/*" Harmomeow-Craft-Launcher/.logs/*.txt`；`grep -F "classpath duplicate class" Harmomeow-Craft-Launcher/.logs/*.txt`。

**为什么这样**：这是 JDK 的既定行为。它带来的**不确定性**直接催生了 §A.5（launchwrapper 形态改显式有序列表）与 §A.6（真树形态必须逐条绝对路径）：只要"谁提供同名类"依赖枚举序，行为就不可复现。

**易混点**：通配**只匹配一层**（`<dir>/*` ≠ 递归），子目录里的 jar 不被匹配（这正是 §A.4 把随包 ASM 放进子目录的原因）。与"`-cp` 里写多条目"不是一回事：多条目顺序**是确定的**（按书写顺序），通配展开顺序**是不确定的**。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`、`assembleRealTreeClasspath`；`common/data/ClasspathStager.ets` 的 `classpathUsesWildcard`。

### A.3 `flat`（平铺）

**定义**：classpath 三态之一：`-cp` 的**值**是**单个通配条目** `<staging 目录>/*`（§A.8），指向把该版本全部声明库"平铺"拷贝成一层 `.jar` 的那个目录。

**形式化**：判为 `flat` ⇔ `-cp` 值 `v` 满足 `|v.split(":")| == 1 ∧ v.endsWith("/*")`；等价的形态判据 = 启动形态主类既不在"真树主类集合"（§A.10）里，也不是 launchwrapper 主类，且 `loader ≠ neoforge`。适用 loader：**vanilla / Fabric**。

**如何观测**：日志 `classpath mode=flat`（无 `entries/bytes` 后缀——只有一个条目）。

**例**（Fabric `1.18.2`，主类 `net.fabricmc.loader.impl.launch.knot.KnotClient`）：`-cp` 的**完整真值**就是一个通配条目

`-cp /data/storage/el2/base/haps/entry/cache/mc-cp/1.18.2/*`

（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790788691-hilog.txt` 的 `CMD:` 行；同文件 `classpath mode=flat`，实例目录 `stuffs/test-fabric/versions/1.18.2/`）。配套 staging 读数（`Harmomeow-Craft-Launcher/.logs/This PC-1790831580-hilog.txt`）：

`stage 1.18.2: mode=flat sources=39` 与 `stage 1.18.2: gen=3.4.3 keep=lwjgl-3.4.3.jar(12953332) checked=39 copied=1`

**从这个例子里应当看出**：`-cp` 字符串**短到只有一条**（因而不打 `entries/bytes` 后缀），39 个声明库全被 `*` 兜住、逐条不写进命令行——这就是 `flat` 判据（`|v.split(":")| == 1 ∧ v.endsWith("/*")`）的字面样子。

**复现/观测**：`grep -F "classpath mode=flat"` 打 `Harmomeow-Craft-Launcher/.logs/This PC-1790788691-hilog.txt`；`grep -F "mc-cp/1.18.2/*"` 打 `Harmomeow-Craft-Launcher/.logs/*.txt`。

**为什么这样**：vanilla / Fabric 不做"按自身 jar 位置反推 maven 根"（§A.6 的机制只属 Forge ≥1.13 族），classpath 上有没有平铺目录都无所谓；而平铺 + 通配能用**一个条目**承载任意多 jar，规避超长 `-cp`（§A.1）。故对它俩，平铺是"零功能损失的省事写法"。

**易混点**：`flat` 是**启动侧**（`-cp` 字面）的形态名；**staging 侧**与之配套的物化意图**同名**（§A.11 的 `mode=flat`，即"该版本声明的整份库都平铺进去"，§A.3 例里的 `stage … mode=flat sources=39`）——两者是**同一次分流的两个投影**。（与之相对，§A.4 `slim` 配的是 `ordered` / `real-tree`。）

**落点**：`common/data/MinecraftLauncher.ets` 的 `CLASSPATH_MODE_FLAT`、`buildLaunchArgv`。

### A.4 `slim`（staging 形态）

**定义**：`ClasspathStager` 的**物化意图**之一：平铺目录里**只放"随包件 + oshi 补丁件"**，不把该版本声明的整份库拷进去；因为该实例的 `-cp` 是**逐条绝对路径列表**（§A.5 / §A.6），不消费平铺库。

**形式化**：物化目标集 = `{ 随包 LWJGL3 jar } ∪ { 随包 ASM 子目录 } ∪ { oshi 清单点名 ∩ 本版本声明的 oshi 件 }`；`-cp` 是不是通配由 `classpathUsesWildcard` 判定，为 false 即 `slim`。

**如何观测**：日志 `stage <key>-<id>: mode=slim sources=N`；`sources` = 本次**有资格被物化**的件数（`slim` = 清单点名的 oshi 件数）。

**例**（`1.19.4-forge-install-test`）：同一实例，staging 说 `slim`、`-cp` 说"逐条绝对路径"

- staging 读数（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790837446-hilog.txt`）：`stage 1.19.4-forge-install-test: mode=slim sources=1`、`stage 1.19.4-forge-install-test: gen=3.4.3 keep=lwjgl-3.4.3.jar(12953332) checked=1 copied=1`——`checked=copied=1` 说明平铺目录里**只物化了 1 件**（点名的 oshi 补丁件），不是整份 79 条声明库。
- 该件正是 `-cp` 的**第一条**（同文件 `CMD:` 行）：`-cp /data/storage/el2/base/haps/entry/cache/mc-cp/1.19.4-forge-install-test/oshi-core-6.2.2.jar:…`——其余条目全是真库树绝对路径（§A.6）。

**从这个例子里应当看出**：`slim` 不是"少放几个库"的模糊说法，而是"平铺目录**只放随包件 + oshi 补丁件**"；因为该实例的 `-cp` 逐条指向真树，多铺声明库纯属无用 I/O（§A.4 定义）。它与启动侧形态（这里是 `real-tree`）是**同一次分流的两个投影**。

**复现/观测**：`grep -F "stage 1.19.4-forge-install-test: mode=slim" Harmomeow-Craft-Launcher/.logs/*.txt`。

**为什么这样**：把整套声明库平铺拷进去、而最终 `-cp` 却逐条指向真库树 ⇒ 拷贝纯属无用 I/O（`slim` 与 `flat` 的唯一行为差异 = **不再多铺无用的库**）。

**易混点**：`slim` 是 **staging 侧**名；对应**启动侧**的 `-cp` 形态**同时**覆盖 §A.5 `ordered` 与 §A.6 `real-tree`（两者都是"逐条绝对路径列表"）。

**落点**：`common/data/ClasspathStager.ets` 的 `STAGE_SLIM`、`stageClasspathDir`、`classpathUsesWildcard`、`slimDeclaredSources`。

### A.5 `ordered`（显式有序列表）

**定义**：classpath 三态之一：`-cp` 的**值**是"**按清单顺序**逐条绝对路径 + 实例 jar"的列表，**顺序即语义**；用于 launchwrapper 形态（主类 = `net.minecraft.launchwrapper.Launch`，§B.4）。

**形式化**：条目序列 = `[ 真库树里规则命中且本地存在的库（按 libraries[] 声明顺序）… , <gameRoot>/versions/<id>/<id>.jar ]`，再做两处整理（对齐 HMCL `DefaultLauncher.getClasspath()`）：① `optifine:OptiFine*` 移到**最末**；② `optifine:launchwrapper-of*` **整条丢弃**。**不含**随包 LWJGL3（该形态用 MC 自带的 LWJGL2）。

**如何观测**：日志 `classpath mode=ordered (entries=N, bytes=M)`；若发生整理，另有 `classpath ordered: optifine last (moved=M), dropped launchwrapper-of=D (HMCL getClasspath parity: keeps forge before optifine, Launch single-sourced)`。

**例**（`1.12.2-Forge-OptiFine`，主类 `net.minecraft.launchwrapper.Launch`）：**同一个实例**现在走 `ordered`

- 形态与整理读数（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790831197-hilog.txt`）：
  - `classpath mode=ordered (entries=52, bytes=9717)`
  - `classpath ordered: optifine last (moved=1), dropped launchwrapper-of=1 (HMCL getClasspath parity: keeps forge before optifine, Launch single-sourced)`
- `-cp` **首 3 条**（同文件 `CMD:` 行，逐字、UTF-8 长串用 `…` 略去公共前缀 `<workspace>/`）：
  1. `/data/storage/el2/base/haps/entry/cache/mc-cp/1.12.2-Forge-OptiFine/oshi-core-1.1.jar`（staging 的 `slim` 件）
  2. `…/stuffs/test-forge/libraries/com/mojang/patchy/1.3.9/patchy-1.3.9.jar`
  3. `…/stuffs/test-forge/libraries/net/java/dev/jna/jna/4.4.0/jna-4.4.0.jar`
- `-cp` 的**末条**（按 §A.5 定义恒为实例 jar；本机可验它存在）：`…/stuffs/test-forge/versions/1.12.2-Forge-OptiFine/1.12.2-Forge-OptiFine.jar`。（`-cp` 的**末 3 条**在日志里取不到——见本页 §A.10 例表下方"日志截断"说明，故不列。）
- 顺序**真的决定胜负**（同文件）：`W classpath duplicate class: net/minecraftforge/common/model/TRSRTransformation.class provided by forge-1.12.2-14.23.5.2864.jar + OptiFine-1.12.2_HD_U_G6_pre1.jar (first in classpath wins)`——因为 Forge 本体**恒排在** OptiFine 之前（`optifine last`），胜者确定。
- 游戏参数里的 tweak 顺序（同文件 `CMD_TAIL:` 行）：`net.minecraft.launchwrapper.Launch --tweakClass net.minecraftforge.fml.common.launcher.FMLTweaker --tweakClass optifine.OptiFineForgeTweaker …`。

**从这个例子里应当看出**：`ordered` 的两条"整理"规则（OptiFine 置末、丢 `launchwrapper-of`）不是文案——同一条命令里既有 `optifine last (moved=1)` 的自证、又有"胜者 = Forge"的体检行；而且**同一实例**此前是 `flat`（`Harmomeow-Craft-Launcher/.logs/This PC-1790788363-hilog.txt`：`-cp …/mc-cp/1.12.2-Forge-OptiFine/*` + `classpath mode=flat`），改判据后变为 `ordered`——这就是"`flat` → `ordered`"的落地样子。

**复现/观测**：`grep -F "classpath mode=ordered" Harmomeow-Craft-Launcher/.logs/*.txt`；`grep -F "classpath ordered: optifine last" Harmomeow-Craft-Launcher/.logs/*.txt`；`ls -1 stuffs/test-forge/versions/1.12.2-Forge-OptiFine/1.12.2-Forge-OptiFine.jar`。

**为什么这样**：`flat` 的通配展开序不确定（§A.2）⇒ OptiFine 1.12.2 里那份 920 B 的 `TRSRTransformation` 空壳可能**先于** Forge 本体命中 ⇒ `IModel.getDefaultState()` 调 `identity()` 抛 `NoSuchMethodError`。改成清单顺序后，`net.minecraftforge:forge` 恒在 OptiFine 之前，同名类归属**确定**。

**易混点**：与 §A.6 `real-tree` **共用同一种 `-cp` 字面**（都是逐条绝对路径列表），差别在**内容策略**：`ordered` 额外做 OptiFine 排位 + 不含随包 LWJGL3。两者由**启动形态主类**区分（`Launch` → `ordered`；真树族主类 → `real-tree`）。

**落点**：`common/data/MinecraftLauncher.ets` 的 `CLASSPATH_MODE_ORDERED`、`isLaunchWrapperMain`、`launchWrapperOptifineOrder`、`assembleRealTreeClasspath`。

### A.6 `real-tree`（真 maven 树）

**定义**：classpath 三态之一：`-cp` 的**值**是"**真库树（§A.7）里逐条绝对路径** + 实例 jar"的列表；用于按"自身 jar 物理位置"反推 `libraries` 根的加载器族（Forge ≥1.13 三代 + NeoForge，§B.2）。

**形式化**：判为 `real-tree` ⇔ 主类 ∈ `REAL_CLASSPATH_MAIN_CLASSES`（= {`cpw.mods.modlauncher.Launcher`, `cpw.mods.bootstraplauncher.BootstrapLauncher`, `net.minecraftforge.bootstrap.ForgeBootstrap`, `net.neoforged.fml.startup.Client`}）**或** `loader == "neoforge"`（兜底）。条目序列 = 真库树里 `libraries[]` 声明顺序的逐条绝对路径 + 实例 jar（+ 继承式实例的基座 client jar + `-DmergeModules` 点名件的绝对路径 + 随包 LWJGL3 jar），按绝对路径**保序去重**（§A.9）。

**如何观测**：日志 `classpath mode=real-tree (entries=N, bytes=M)`；另有 ASM 自证行 `classpath real-tree: asm=<path> (in-libraries=yes|no)`。

**例**（`1.19.4-forge-install-test`，主类 `cpw.mods.bootstraplauncher.BootstrapLauncher`）：`-cp` 是"真库树逐条绝对路径"

- 形态读数（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790837446-hilog.txt`）：`classpath mode=real-tree (entries=67, bytes=12052)`。
- `-cp` **首 3 条**（同文件 `CMD:` 行，逐字；公共前缀 `…/<workspace>/` 用 `…` 略）：
  1. `/data/storage/el2/base/haps/entry/cache/mc-cp/1.19.4-forge-install-test/oshi-core-6.2.2.jar`（staging 的 `slim` 件）
  2. `…/stuffs/test-forge/libraries/com/google/code/gson/gson/2.10/gson-2.10.jar`
  3. `…/stuffs/test-forge/libraries/com/google/guava/failureaccess/1.0.1/failureaccess-1.0.1.jar`
  跟着的还有 `…/libraries/com/google/guava/guava/31.1-jre/guava-31.1-jre.jar`——这些坐标的**声明路径**都能在 `stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json` 里查到（顶层 `libraries[]` 与 `patches[]`；其中 `patches[game]` 头部正是 `…/com/github/oshi/oshi-core/6.2.2/oshi-core-6.2.2.jar`、`…/com/google/code/gson/gson/2.10/gson-2.10.jar`，与 `-cp` 头部一致）。
- `-cp` 的**末条**恒为实例 jar（§A.6 定义；本机可验）：`…/stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.jar`。（**末 3 条**取不到，见 §A.10 例表下方"日志截断"说明。）
- ASM 落在**真树**里（同文件）：`classpath real-tree: asm=…/stuffs/test-forge/libraries/org/ow2/asm/asm/9.6/asm-9.6.jar (in-libraries=yes)`（这是 **1.16.5** 那条的读数；`1.19.4-…` 因触发 §E.8 覆盖而变成 `…/cache/mc-cp/1.19.4-forge-install-test/asm9/asm-9.9.1.jar (in-libraries=no)`）。

**从这个例子里应当看出**：`real-tree` 的条目**就是 maven 树的绝对路径**（`libraries/<group>/<artifact>/<ver>/<artifact>-<ver>.jar`，§A.7），条数等于"规则命中且本地存在的声明库"——这里的 `entries=67` 就是可判定的量（可与 §A.10 例表逐实例比对）。

**复现/观测**：`grep -F "classpath mode=real-tree" Harmomeow-Craft-Launcher/.logs/*.txt`；`grep -F "classpath real-tree: asm=" Harmomeow-Craft-Launcher/.logs/*.txt`；`ls -1 stuffs/test-forge/libraries/org/ow2/asm/asm/*/*/`。

**为什么这样**：**充要**——Forge ≤1.16.x 的 FML 用 `ClassLoader.getResource("org/objectweb/asm/Opcodes.class")` 取到 **ASM jar 的路径**后连续 `getParent()` **×6** 当作 `libraries` 根，再拼 `…/forge-<ver>-universal.jar` 只做 `Files.exists` 校验；ASM 在真树里恰是 `libraries/org/ow2/asm/asm/<v>/asm-<v>.jar`（上溯 6 级 = `libraries`），而平铺目录里 ASM 落在任意深度 ⇒ 上溯 6 级落到**别的目录** ⇒ fatal `Missing forge!`（jar 其实在盘上）。FML 不读任何 `-D`，也不扫 `java.class.path` ⇒ 换任何深度的平铺都只会错成另一个值，**只有真树能修**。

**易混点**：① 与 §A.5 `ordered` 共用同一种字面（见 §A.5 易混点）；② "真树"指**库文件的物理布局真的是 maven 布局**（§A.7），不是"路径字符串里含 `libraries`"；③ NeoForge 的兜底独立于主类清单——NeoForge 演进快、主类会改，classpath 形态不得掉回平铺。

**落点**：`common/data/MinecraftLauncher.ets` 的 `CLASSPATH_MODE_REAL_TREE`、`needsRealClasspath`、`assembleRealTreeClasspath`、`logAsmProvider`；`common/constants/LaunchContract.ets` 的 `REAL_CLASSPATH_MAIN_CLASSES`。

### A.7 maven 树布局

**定义**：把库按**坐标** `group:artifact:version[:classifier][@ext]` 映射成的**物理目录结构**：`<库根>/<group 的 . 换 />/<artifact>/<version>/<artifact>-<version>[-classifier].<ext>`。

**形式化**：给定坐标 `g:a:v[:c][@e]`，路径 = `g 换斜杠 + "/" + a + "/" + v + "/" + a + "-" + v + (c ? "-"+c : "") + "." + (e ?: "jar")`。**`<库根>` 在本工程恒为 `<gameRoot>/libraries`。**

**如何观测**：文件系统直接可验，例如 `libraries/org/ow2/asm/asm/9.6/asm-9.6.jar`；启动宏 `${library_directory}` 即 `<gameRoot>/libraries`（§C.5）。

**例**（`stuffs/test-forge/libraries/` 的真实片段，逐字取自 `ls -1 stuffs/test-forge/libraries/org/ow2/asm/*/*/`）：

```
stuffs/test-forge/libraries/org/ow2/asm/      ← group=org.ow2.asm 的“.”换成“/”
├── asm/
│   ├── 6.2/asm-6.2.jar                        ← artifact=asm, version=6.2
│   ├── 9.1/asm-9.1.jar
│   ├── 9.6/asm-9.6.jar                        ← ① 代每条启动都指这里（§A.6 / §E.8）
│   ├── 9.7.1/asm-9.7.1.jar
│   └── 9.9.1/asm-9.9.1.jar
├── asm-commons/
│   ├── 9.6/asm-commons-9.6.jar
│   └── 9.7.1/asm-commons-9.7.1.jar
└── asm-tree/9.6/asm-tree-9.6.jar
```

**从这个例子里应当看出**：坐标 `org.ow2.asm:asm:9.6` 到路径 `org/ow2/asm/asm/9.6/asm-9.6.jar` 是**纯机械映射**（group 点换斜杠、末段 = `<artifact>-<version>.jar`）；也正因为 `asm/9.6/` 距 `libraries` 恰好 5 层，FML 的 `getParent()`×6 才落到 `libraries`（§A.6 的"充要"）。

**复现/观测**：`ls -1 stuffs/test-forge/libraries/org/ow2/asm/*/*/`。

**为什么这样**：这是 Maven 仓库的既有约定，也是 FML"上溯 6 级反推库根"（§A.6）能成立的**前提**——`org/ow2/asm/asm/<v>/` 恰好 5 层，`getParent()` 6 次正好落到 `libraries`。

**易混点**：`<artifact>-<version>` 里的连字符**同时**是 artifact 与版本的候选分隔符，从字符串无法唯一切分（如 `guava-25.1-jre`）；本工程按"首个以数字开头的段作版本起点"切分。

**落点**：`common/data/MinecraftLauncher.ets` 的 `mavenPathFromName`；`common/data/VersionInstaller.ets` 的 `mavenPath`；`common/data/NeoForgeInstaller.ets` 的 `splitArtifactVersion`。

### A.8 平铺 staging 目录

**定义**：`ClasspathStager` 落盘的物化目录 `<cacheDir>/mc-cp/<key>-<id>/`——把"该实例要用的 jar"**平铺成一层**（无子目录）的沙箱缓存目录。

**形式化**：路径 = `<cacheDir>/mc-cp/<key>-<id>`（`cacheDir` = `UIAbilityContext.cacheDir`）。内容 = `flat` 时的整份声明库，或 `slim` 时的"随包件 + oshi 补丁件"（§A.4）；外加子目录 `asm9/`（随包 ASM，**不平铺**）。

> 本节**例**里的 `mc-cp/<id>` 是加 key 前的**历史读数**（现行目录名带 `gameRoot` 短哈希前缀，见 §E.9 与 [`环境与载体.md`](环境与载体.md) §7.1）。

**如何观测**：文件系统 `<cacheDir>/mc-cp/<key>-<id>/`；日志 `stage <key>-<id>: gen=<gen> keep=<jar>(N) checked=C copied=C`。

**例**（`1.18.2` 的平铺目录）：`-cp` 指向它、ASM 子目录也在它下面

- 平铺目录（单层）——路径取自日志 `-cp` 与 staging 行（`<cacheDir>` = `/data/storage/el2/base/haps/entry/cache`）：
  ```
  /data/storage/el2/base/haps/entry/cache/mc-cp/1.18.2/
  ├── <该实例声明的整份库，平铺一层>.jar     ← flat 时在此（§A.3；本次 sources=39）
  ├── oshi-core-5.8.5.jar                    ← oshi 补丁件覆写后的名字（日志 `override oshi-core-5.8.5.jar <- oshi-overrides/oshi-core-5.8.5-meow.jar`）
  └── asm9/                                   ← 随包 ASM 子目录，不参与一层通配（§A.8 / §E.8）
  ```
- 指向它的 `-cp`（`Harmomeow-Craft-Launcher/.logs/This PC-1790788691-hilog.txt`）：`-cp /data/storage/el2/base/haps/entry/cache/mc-cp/1.18.2/*`。
- `asm9/` 子目录的真身（`Harmomeow-Craft-Launcher/.logs/This PC-1790837446-hilog.txt`，同形状）：`asm override: bundled ASM 9.9.1 (5 jars) staged at /data/storage/el2/base/haps/entry/cache/mc-cp/1.19.4-forge-install-test/asm9; …`。
- **边界**：该目录在**设备应用缓存**里，**本机不可读**（本工作区无 `/data/storage/el2/…`）⇒ 上面"目录结构"由代码常量 `Paths.MC_CP_DIR`（= `'mc-cp'`）+ 日志里的真实路径**合成**，非本机 `ls` 所得。

**从这个例子里应当看出**：`staging` 是**写盘物化**（§A.11），目录名恒为 `<cacheDir>/mc-cp/<key>-<id>/`；"平铺一层"是为了让 §A.3 的 `<dir>/*` 一步拿到全部 jar，而 ASM **必须**退到子目录 `asm9/`（一层通配不递归）。

**复现/观测**：`grep -F "mc-cp/1.18.2/*" Harmomeow-Craft-Launcher/.logs/*.txt`；`grep -F "mc-cp/1.19.4-forge-install-test/asm9" Harmomeow-Craft-Launcher/.logs/*.txt`。

**为什么这样**：鸿蒙无 `/tmp`、随包区（HSP el1）只读 ⇒ 运行期要用的 jar 必须落到**可写的沙箱缓存**；平铺一层是为了让 §A.3 的 `<dir>/*` 通配**一步**拿到全部 jar。

**易混点**：**随包 ASM 必须放子目录 `asm9/`**——平铺通配**不递归**（§A.2），平铺进去会混进 `flat` 形态的 `-cp`、可能与 Fabric 自带的 ASM 互相遮蔽。

**落点**：`common/constants/Paths.ets` 的 `MC_CP_DIR`；`common/data/ClasspathStager.ets` 的 `stageClasspathDir`；`common/constants/LaunchDefaults.ets` 的 `ASM_STAGE_SUBDIR`。

### A.9 保序去重

**定义**：把 classpath 条目序列里**完全相同的绝对路径**去掉、只保留**首次出现**，且**不改变其余条目的相对顺序**。

**形式化**：`dedup([x₁…xₙ])` = 保留满足 `xᵢ ∉ {x₁…xᵢ₋₁}` 的项。**判据 = 字符串（绝对路径）相等**，**不是** artifact 名相等。

**如何观测**：日志 `classpath mode=real-tree (entries=N)` 的 `N` 比"声明库数 + 1"小即说明发生了去重；反例日志 `Duplicate key …/failureaccess-1.0.1.jar`（NeoForge）说明**该去重没生效**。

**为什么这样**：NeoForge 清单与 vanilla 清单会声明**同一个库**（guava / failureaccess / gson 等），同路径出现两次会让 `bootstraplauncher` 的合并阶段抛 `IllegalStateException: Duplicate key`。**不能按 artifact 名去重**——bootstraplauncher 的模块合并本来就靠"同名不同版本的 jar 合并成同一模块"，按名去重会破坏它。

**易混点**：与"库表去重"（`VersionResolver.dedupLibraries`：按 `group:artifact` 留最高版本、位置保持首次出现、**同坐标的 natives / classifier 变体保留**）是**两层不同的去重**：前者作用在**绝对路径串**，后者作用在**库声明表**。

**落点**：`common/data/MinecraftLauncher.ets` 的 `assembleRealTreeClasspath`（`unique` / `seen` 循环）；对比 `common/data/VersionResolver.ets` 的 `dedupLibraries`。

### A.11 staging 模式

**定义**：把某实例的运行 jar **物化到平铺 staging 目录**（§A.8）的那一步；其"意图"（`flat` / `slim`）由 §A.4 的判据决定。

**形式化**：日志 `stage <key>-<id>: mode=<flat|slim> sources=<N>`，其中 `sources` = 本次**有资格被物化**的件数（`flat` = 整份声明库；`slim` = 清单点名的 oshi 件）。同一步还写"是否重新解包随包 tar"的 done 标记：内容 = `${EXTRAS_VERSION}|<随包 tar 的字节数>`（**双条件**）。

**如何观测**：日志 `stage <key>-<id>: mode=flat|slim sources=N`、`stage <key>-<id>: gen=… keep=…(N) checked=C copied=C`、`extras <key>-<id>: stamp=… reextract=yes|no`。`stageClasspathDir` 返回**空串**即中止启动（形态断言失败）。

**为什么这样**：超长 `-cp` 在本 JLI 移植会失效（§A.1）⇒ 启动前必须把 jar 物化到沙箱；物化必须**幂等 + 可自愈**（`copied` 只在尺寸不符时才 +1；done 标记挡住重复解包；tar 字节数让"换了 tar 却忘升令牌"也自动重抽）。

**易混点**：`stage` 是**物化**（写盘）动作，不是"启动"；`mode=` 是物化意图，不等于启动侧的 `classpath mode=`。

**落点**：`common/data/ClasspathStager.ets` 的 `stageClasspathDir`、`STAGE_FLAT`、`STAGE_SLIM`、`stagedBundleComplete`；`common/constants/LaunchDefaults.ets` 的 `EXTRAS_VERSION`。

## §B 加载器与启动形态

### B.1 loader（加载器）

**定义**：在 MC 之上接管"类加载 / mod 发现 / 启动分流"的**那一层**；本工程只识别四族：vanilla（无加载器）、Forge、NeoForge、Fabric（含 Legacy Fabric）。

**形式化**：`loader ∈ {"", "fabric", "legacy_fabric", "forge", "neoforge"}`。判据（`detectLoader`）：查补丁 id（`patches[].id`）与库坐标（`net.fabricmc:fabric-loader` / `net.legacyfabric:` / `net.minecraftforge:forge|fmlloader` / `net.neoforged.fancymodloader:`）；**判定顺序 Forge → NeoForge → Fabric**。

**如何观测**：版本卡片被识别为 `forge` / `neoforge` / `fabric` / 未知；`ResolvedVersion.loader` 即该判定产出。

**为什么这样**：classpath 形态（§A.10）、tweak 修复（§B.11）需要"知道这是哪族"；但**形态判据又刻意不依赖 loader 名**（loader 名不可靠：薄 `inheritsFrom` 认不出）⇒ loader 只作辅助与兜底，主判据一律用主类。Forge 先于 NeoForge 判：Forge 47.x 的库表**同时**含 `net.minecraftforge:*` 与 `net.neoforged.fancymodloader:*`，先判后者会把 Forge 误判成 NeoForge。

**易混点**：与"主类 / 启动形态（§B.3）"是**两套判据**：loader 可能识别失败（返回 `""`），主类却始终稳定——这正是 §A.10 按主类判的原因。

**落点**：`common/data/VersionResolver.ets` 的 `detectLoader`、`LOADER_FABRIC`、`LOADER_LEGACY_FABRIC`、`LOADER_FORGE`、`LOADER_NEO_FORGE`。

### B.2 世代（Forge 四代 ①/②/③）

**定义**：Forge 随 MC 版本演进出的**四代启动机制**（legacy + ① + ② + ③），每代有**不同的主类**与**不同的 classpath / 参数契约**。

**形式化（真值表）**：

| 世代 | MC 段 | 主类 | 是否需要真树（§A.6） | `-p`（module path） |
|---|---|---|---|---|
| legacy | ≤1.12.2 | `net.minecraft.launchwrapper.Launch` | 否（走 §A.5 `ordered`） | 无 |
| ① | 1.13–1.16.5 | `cpw.mods.modlauncher.Launcher` | **是** | 无 |
| ② | 1.17.1–1.20.1 | `cpw.mods.bootstraplauncher.BootstrapLauncher` | **是** | 有 |
| ③ | ≥1.20.3 | `net.minecraftforge.bootstrap.ForgeBootstrap` | **是** | 无（责任收回加载器） |

（世代 ②→③ 切点 = **1.20.2 → 1.20.3**：1.20.2 的主类是 `net.minecraftforge.bootstrap.BootstrapLauncher`，与 ③ 代不同名、也**不在** `REAL_CLASSPATH_MAIN_CLASSES` 里。）判据一律 = **主类字符串**，MC 版本号**不参与**判型。

**如何观测**：日志 `classpath mode=real-tree …` 与主类名；`GameVersionsView` 的 `FORGE_MIN_MC` / `FORGE_MAX_MC`。

**为什么这样**：四代主类不同 ⇒ "该走哪条路"的判据要落在主类上；世代名（①/②/③）只是**给这三代起的简称**，便于对照，不是代码里的枚举。

**易混点**：① 世代名（①/②/③）与"安装形态"（`legacy` / `spec-no-processor` / `spec-processors`，§D.11）**正交**：前者按**主类**分、后者按**`install_profile.json` 的键**分；② "legacy Forge" 与"legacy LWJGL2"（§E.1）都叫 legacy，含义不同。

**落点**：`common/constants/LaunchContract.ets` 的 `REAL_CLASSPATH_MAIN_CLASSES`；`common/data/MinecraftLauncher.ets` 的 `needsRealClasspath`。

### B.3 主类 / 启动形态（mainClass / launch shape）

**定义**：**主类** = 版本 json 的 `mainClass` 字段（JVM 启动后第一个被加载并执行 `main` 的类）；**启动形态** = 由主类字符串**归类**出的"这一类实例怎么启"的类别（本工程用它当 §A.10 / §B.11 的判据）。

**形式化**：`mainClass` 是 json 的**字符串字段**；启动形态 = `classify(mainClass)`，取值 {vanilla, fabric, launchwrapper, modlauncher, bootstraplauncher, forgebootstrap, neoforge-client}。本工程**一律直启 `json.mainClass`**（`buildLaunchArgv` 把它原样推进 argv 的主类位），不反射、不替换。

**如何观测**：`GameLauncher CMD:` 起的完整 argv 里，`-cp` 串之后那个 token 即主类；`classpath mode=` 行即形态分类的产出。

**为什么这样**：主类比"loader 名"或"MC 版本号"都**稳定**（薄 `inheritsFrom`、被人工改写的清单都改不动它）⇒ 用它当判据可避免"同一判据散成两处布尔"。

**易混点**：主类 ≠ 实例名 / 目录名 ≠ json 内部 `id`（Fabric 实例的 `id` 形如 `fabric-loader-0.15.11-1.20.1`，**不是** MC 版本号）。真 MC 版本号另由 `readVersionId`（解析继承 / 补丁后的 `mcVersion`）给出。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`、`readVersionId`；`common/data/VersionResolver.ets` 的 `ResolvedVersion.mcVersion`。

### B.4 LaunchWrapper

**定义**：legacy（≤1.12.2）的 MC / Forge / LiteLoader / OptiFine 共用的**老式类加载框架**，主类 `net.minecraft.launchwrapper.Launch`；它靠 `--tweakClass` 挂载各家的 tweaker（§B.11）。

**形式化**：主类字符串 `== "net.minecraft.launchwrapper.Launch"` 即 launchwrapper 形态。其构造里有 `(URLClassLoader) getClassLoader()` 强转 ⇒ 要求当前 app classloader 是 `URLClassLoader`。

**如何观测**：日志 `classpath mode=ordered …`（形态判据命中）；argv 里出现 `--tweakClass …`。

**为什么这样**：`Launch.<init>` 的强转只在 **Java 8 档**出现（§B.9），而 JDK 8 的 app classloader 本身就是 `URLClassLoader` 子类 ⇒ 强转原生成立 ⇒ **不需要**换系统 CL；`LaunchClassLoader` 的委派父指向"定义 `Launch` 的那个 CL" ⇒ tweaker 实现类与 `net.minecraft.launchwrapper.ITweaker` 同源 ⇒ 单一 CL 下无 CCE / 无 CNFE。

**易混点**：`LaunchWrapper`（框架名）≠ `launchwrapper-of`（OptiFine 自带的同名 fork，§A.5 里要丢弃的那条）。

**落点**：`common/data/MinecraftLauncher.ets` 的 `LAUNCHWRAPPER_MAIN`、`isLaunchWrapperMain`。

### B.5 ModLauncher

**定义**：Forge **① 代**（1.13–1.16.5）的加载器主类 `cpw.mods.modlauncher.Launcher`。

**形式化**：主类 `== "cpw.mods.modlauncher.Launcher"` ⇒ 真树形态（§A.10）、无 `-p`。

**如何观测**：日志 `classpath mode=real-tree …`；ASM 自证行 `classpath real-tree: asm=<path> (in-libraries=yes)`（① 代的不变量：ASM 必须落在真树 `libraries/org/ow2/asm/`）。

**为什么这样**：① 代 FML 用"ASM jar 上溯 6 级"反推库根（§A.6）⇒ 必须真树；该代 json 无 module path（§B.2）。

**易混点**：`ModLauncher` 是**主类名 / 框架名**；ASM 覆盖判据里的 `modlauncher ≥ 10`（§E.8）指的是**库 `cpw.mods:modlauncher` 的版本**，不是这里的"代"。

**落点**：`common/constants/LaunchContract.ets` 的 `REAL_CLASSPATH_MAIN_CLASSES`。

### B.6 BootstrapLauncher

**定义**：Forge **② 代**（1.17.1–1.20.1）与 **NeoForge 1.20.2+** 共用的加载器主类 `cpw.mods.bootstraplauncher.BootstrapLauncher`。

**形式化**：主类 `== "cpw.mods.bootstraplauncher.BootstrapLauncher"` ⇒ 真树形态 + 有 `-p` / `-DignoreList` / `-DmergeModules`（② 代）。

**如何观测**：日志 `classpath mode=real-tree …`；argv 里 `-p` 与 `-DignoreList` / `-DmergeModules` / `-DlibraryDirectory` 齐。

**为什么这样**：老 `bootstraplauncher`（0.1.17 / 1.0.0）的 `module-info` 一个包都不导出 ⇒ 从无名模块反射调用会被 Java 9+ 模块系统拒（`IllegalAccessException … does not export … to unnamed module`）⇒ **直启**（§B.9）。② 代的 `-p` / `-DignoreList` 需要真实、稳定、有序的 classpath 条目集合 ⇒ 真树。

**易混点**：Forge ② 与 NeoForge 1.20.2+ **同主类、同 classpath 形态**，但**安装链**与"是否 ASM 替换"是分开的（见 §D / §E.8）。

**落点**：`common/constants/LaunchContract.ets` 的 `REAL_CLASSPATH_MAIN_CLASSES`。

### B.7 ForgeBootstrap

**定义**：Forge **③ 代**（≥1.20.3）的加载器主类 `net.minecraftforge.bootstrap.ForgeBootstrap`。

**形式化**：主类 `== "net.minecraftforge.bootstrap.ForgeBootstrap"` ⇒ 真树形态；json 里 `-p` / `-DignoreList` / `-DlibraryDirectory` **全无**（库发现责任收回加载器自己）。

**如何观测**：日志 `classpath mode=real-tree …`。

**为什么这样**：③ 代把 classpath 分区的责任收回加载器 ⇒ 它必须能枚举 classpath 条目 ⇒ 仍需真树。应用内安装未适配（③ 代另有 `hideExtract` / `serverJarPath` / `path` 带 `:shim` 三项形态差异）。

**易混点**：1.20.2 的主类是 `net.minecraftforge.bootstrap.BootstrapLauncher`（**不在** `REAL_CLASSPATH_MAIN_CLASSES`），与 ③ 代的 `ForgeBootstrap` 不是同一个类名。

**落点**：`common/constants/LaunchContract.ets` 的 `REAL_CLASSPATH_MAIN_CLASSES`。

### B.8 KnotClient

**定义**：Fabric 的加载器主类 `net.fabricmc.loader.impl.launch.knot.KnotClient`（来自 Fabric meta `launcherMeta.mainClass.client`）。

**形式化**：主类 `== "net.fabricmc.loader.impl.launch.knot.KnotClient"` ⇒ 平铺形态（§A.10）。

**如何观测**：日志 `classpath mode=flat`；版本卡片识别为 `fabric` / `legacy_fabric`。

**为什么这样**：Knot 要求 loader 类由**父加载器**持有；自设 system CL 会破坏该契约（§B.9）。Fabric 的 loader 自行处理 classpath 追加 ⇒ 平铺自足。

**易混点**：`KnotClient`（客户端）≠ 服务端的 `KnotServer`；Fabric meta 的 `mainClass` 是对象 `{client, server}`，本工程取 `client`。

**落点**：`common/data/VersionInstaller.ets` 的 `fabricMainClass`。

### B.9 system class loader 与 `-Djava.system.class.loader`

**定义**：`-Djava.system.class.loader=<类名>` 让 JVM 用指定类当**系统类加载器**（替代默认 `AppClassLoader`）。

**形式化**：本工程的**不变量**：**恒不设**该属性；`buildLaunchArgv` 的 argv 里**不含** `-Djava.system.class.loader`。等价表述：启动主类恒 = `json.mainClass`，**无主类分叉**。

**如何观测**：`GameLauncher CMD:` 的完整 argv 里搜不到 `java.system.class.loader`。

**为什么这样**：① 自研 system CL 会与加载器自带的类加载体系冲突（Forge ≥1.13 / NeoForge 设它会在 JVM 启动期 `Class.forName` 直接 `ClassNotFound`）；② launchwrapper 的强转（§B.4）只在 Java 8 档出现，而 JDK 8 的 app CL 本就是 `URLClassLoader` 子类 ⇒ 强转原生成立、**不需要**换 CL；③ vanilla 的平铺 classpath 自足。

**易混点**：与"app classloader / `AppClassLoader`"是同一件事的不同叫法；"系统类加载器"（system CL）≠ "引导类加载器"（bootstrap CL，加载 `java.base` 的那个）。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`（"固定 JVM 参数"段与顶部定案的注释）。

### B.10 启动器族（loader family）—— 历史术语

**定义**：**历史术语**：指"由某个加载器引入、且必须与加载器本体同源加载的一组 jar"（launchwrapper / FML 本体 / OptiFine）。

**形式化（历史）**：曾用常量 `LOADER_FAMILY_PATH_SEGMENTS` + 判据 `isLoaderFamilyJar` 把这些 jar 摘出平铺目录、交给自研 system CL；**该整套机制已随 `MeowLauncher`（§B.12）退役而废除**——理由是"老 Forge 只走 Java 8 档"（§B.9），JDK 8 的 app CL 本就是 `URLClassLoader`，无需摘族。

**如何观测**：现役代码里**搜不到** `LOADER_FAMILY_PATH_SEGMENTS` / `isLoaderFamilyJar`（仅在注释里作为历史说明出现）。

**为什么这样**：见 §B.9 的定案。

**易混点**：与 `loader`（§B.1）不同：`loader` 是**加载器种类**（forge/neoforge/fabric），"启动器族"是**一组 jar**。

**落点**：**历史 / 归档** —— 归档指针 [`../../90-archive/launcher净室-设计.md`](../../90-archive/launcher净室-设计.md)（净室 classpath 跳过表 / 桩类规划）；现役仅剩注释 `common/data/MinecraftLauncher.ets`。

### B.11 tweak class / `--tweakClass`

**定义**：launchwrapper 的**扩展点**：`--tweakClass <类>` 告诉 `Launch` 去加载并初始化一个 `ITweaker`（Forge / LiteLoader / OptiFine 各有一个），用来在游戏启动前改类加载 / 参数表。

**形式化**：argv 里一对相邻 token `["--tweakClass", <类名>]`。本工程对 launchwrapper 形态**重排**这些对（照抄 HMCL `repairLaunchWrapper` 的三段规则），净效果头部 = **Forge → OptiFine → LiteLoader**；规则 = 每段"先删净所有 `--tweakClass <target>` 相邻对，再把 `<replacement>` 前插到最前"。

**如何观测**：argv 里 `--tweakClass` 的相邻类名顺序。

**例**（`1.12.2-Forge-OptiFine`，主类 `net.minecraft.launchwrapper.Launch`）：一条真实 `CMD_TAIL:`（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790831197-hilog.txt`）

```
… /data/…/mc-run-1.12.2-Forge-OptiFine/natives net.minecraft.launchwrapper.Launch
   --tweakClass net.minecraftforge.fml.common.launcher.FMLTweaker
   --tweakClass optifine.OptiFineForgeTweaker
   --username <player> --version 1.12.2-Forge-OptiFine --gameDir … --assetsDir … --assetIndex 1.12 …
```

**从这个例子里应当看出**：`--tweakClass` 是**主类之后**的成对游戏参数，这里是"Forge → OptiFine"两段、顺序已确定（HMCL `repairLaunchWrapper` 的净效果）；它和 §A.5 的 `classpath ordered: optifine last` 是同一实例的两处投影。

**复现/观测**：`grep -F "CMD_TAIL:"` 打 `Harmomeow-Craft-Launcher/.logs/This PC-1790831197-hilog.txt`。

**为什么这样**：装上 Forge 常会**整段替换**游戏参数表，把 LiteLoader / OptiFine 的 `--tweakClass` 挤掉或打乱顺序；launchwrapper 对 tweak 的加载顺序敏感（后者可覆盖前者的 transformer 注册）⇒ 启动前必须把顺序修成确定性形式。**Forge 的 tweaker 缺失时不补**（HMCL 只对已存在的 Forge tweaker 重排；LiteLoader / OptiFine 才在组件存在时"补一份"）。

**易混点**：`--tweakClass` 是**游戏参数**（在主类之后），不是 JVM 选项；只在 launchwrapper 形态出现，ModLauncher 世代用 json 里的 `arguments` 取代它。

**落点**：`common/data/MinecraftLauncher.ets` 的 `FORGE_TWEAKERS`、`LITELOADER_TWEAKER`、`OPTIFINE_TWEAKER_PLAIN`、`OPTIFINE_TWEAKER_FORGE`、`hasTweak`、`reorderTweak`、`reorderLaunchWrapperTweaks`。

### B.12 MeowLauncher —— 历史术语

**定义**：**历史术语**：本工程早期自研的 Java 层启动器入口（配合净室 `MeowClassLoader` 当 system CL），曾用于 vanilla 的"运行期 `addURL`"与 Forge 的反射顶替。

**形式化（历史）**：曾以"设 `-Djava.system.class.loader=MeowClassLoader` + 主类改为 `meow.launcher.MeowLauncher`"的方式启动；**已退役**（主类分叉一并取消）⇒ 现役**一律直启 `json.mainClass`**（§B.9）。

**如何观测**：现役 argv / 代码里**搜不到** `MeowLauncher` / `MeowClassLoader`（仅注释里作历史说明）；随包 tar 里的 `launcher.jar` 与 `gson-for-launcher.jar` 桩件已摘除。

**为什么这样**：老 Forge 定口径"只走 Java 8 档"（§B.9）后，整套"换系统 CL + 摘启动器族"机制不再需要；vanilla 的平铺 classpath 自足（§A.3）。

**易混点**：与"启动器（launcher）"（本 App 本身）不同——`MeowLauncher` 是**被从游戏进程内调用的 Java 入口**，不是桌面 App。

**落点**：**历史 / 归档** —— 归档指针 [`../../90-archive/launcher净室-设计.md`](../../90-archive/launcher净室-设计.md)、`stuffs/research/launchwrapper-study/REPORT.md`；现役仅剩注释 `common/data/MinecraftLauncher.ets`、`common/constants/LaunchDefaults.ets`。

## §C 启动参数机制

### C.1 module path（`-p`）

**定义**：Java 9+ 的**模块查找路径**：JVM 从此路径上的**命名模块**（能提供 module descriptor 的 jar / 目录）中解析模块。

**形式化**：字面形态 `-p <列表>`（别名 `--module-path <列表>`），`<列表>` 是 `:` 分隔的**绝对路径**列表。本工程该选项**由版本 json 的 `arguments.jvm` 给出**（如 `-p ${library_directory}/…`），`buildLaunchArgv` 只做宏替换 + 规则过滤、**不自造**。

**如何观测**：`GameLauncher CMD:` 的 argv 里 `-p` 之后那一串；② 代（Forge 1.17.1–1.20.1）必有。

**例**（`1.19.4-forge-install-test`）：`-p` 的**真值在版本 json 里**（来源：`stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json` 的 `arguments.jvm`，逐字；`${classpath_separator}` 是宏，行内用 `⋮` 略）

```
-p ${library_directory}/cpw/mods/bootstraplauncher/1.1.2/bootstraplauncher-1.1.2.jar⋮
   ${library_directory}/cpw/mods/securejarhandler/2.1.6/securejarhandler-2.1.6.jar⋮
   ${library_directory}/org/ow2/asm/asm-commons/9.7.1/asm-commons-9.7.1.jar⋮
   …⋮ ${library_directory}/org/ow2/asm/asm/9.7.1/asm-9.7.1.jar⋮
   ${library_directory}/net/minecraftforge/JarJarFileSystems/0.3.19/JarJarFileSystems-0.3.19.jar
```

共 **8** 条（`${classpath_separator}` 出现 7 次）。注意 ASM 的 5 件（`asm` / `asm-commons` / `asm-tree` / `asm-util` / `asm-analysis`）**同时出现在 `-p` 与 `-cp` 两处**（§E.8）。`-p` 之后紧跟 json 里的 `--add-modules ALL-MODULE-PATH`（§C.2）。

**从这个例子里应当看出**：`-p` 与 `-cp` 是**两套独立列表**，且这里 `-p` 装的是**命名模块**（bootstraplauncher / securejarhandler / ASM / JarJar 文件系统）——所以 ASM 覆盖必须**同时改写两处**才不会留旧件（§E.8）。该值由 json 给出、`buildLaunchArgv` 只做宏替换，所以**版本 json 是 `-p` 的权威出处**（`CMD:` 行因截断看不到它）。

**复现/观测**：`python3 -c "import json;d=json.load(open('stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json'));print(d['arguments']['jvm'][13], d['arguments']['jvm'][14])"`。

**为什么这样**：② 代的 FML / bootstraplauncher 用模块系统加载；它需要真实、稳定、有序的条目集合 ⇒ 与真树形态（§A.6）绑定。

**易混点**：与 `-cp`（§A.1）是**两套独立路径**：`-cp` 找用户类（无名模块），`-p` 找命名模块；**同一个 jar 可以同时在两者里**（ASM 就是——见 §E.8，故 ASM 覆盖须同时改写 `-cp` 与 `-p`）。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`（`-p` / `--module-path` 分流与 `rewriteNextAsModulePath`）。

### C.2 `--add-modules ALL-MODULE-PATH`

**定义**：告诉模块系统"把 `--module-path` 上的**全部**模块都加入根模块集（root modules）"。

**形式化**：字面常量 `ALL-MODULE-PATH`；本工程该选项**由版本 json 给出、原样透传**。

**如何观测**：`GameLauncher CMD:` argv 里 `--add-modules ALL-MODULE-PATH`。

**为什么这样**：② 代要显式把 module path 上的模块都解析进 boot layer；这也是 ASM 经 `-p` + `--add-modules ALL-MODULE-PATH` 加载的由来（§E.8）。

**易混点**：`--add-modules` 是**JVM 选项**（在 `-cp` 之前的选项区），不是游戏参数。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`（json jvm 参数透传）。

### C.3 `-DignoreList`

**定义**：Forge ② 代 bootstraplauncher 的**属性**：按**文件名（子串）**点名一批 jar，让它在 classpath 扫描 / 模块解析时**忽略**它们。

**形式化**：`-DignoreList=<逗号分隔的文件名 / 子串>`；由 json `arguments.jvm` 给出、原样透传。**判据是文件名子串匹配**（如 `asm-9.5.jar,…`）。

**如何观测**：`GameLauncher CMD:` argv 里的 `-DignoreList=…`。

**例**（`1.19.4-forge-install-test`，来源：`stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json` 的 `arguments.jvm`，逐字）

```
-DignoreList=bootstraplauncher,securejarhandler,asm-commons,asm-util,asm-analysis,asm-tree,asm,JarJarFileSystems,client-extra,fmlcore,javafmllanguage,lowcodelanguage,mclanguage,forge-,${version_name}.jar
```

**从这个例子里应当看出**：`ignoreList` 按**带版本的文件名 / 子串**点名（如 `asm-commons`、`asm`、`forge-`），与 §C.1 的 `-p` 里那批 `…/9.7.1/asm-commons-9.7.1.jar` **一一对应**——正因为它"只认名字子串"，一旦把 ASM 改名成随包版本就**静默脱靶**（§C.3 为什么这样 / §E.8 为何 NeoForge 不覆盖）。

**复现/观测**：`grep -o '"\-DignoreList=[^"]*"' stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json`。

**为什么这样**：② 代用它剔除会撞包的重复提供者。**它按带版本的文件名点名** ⇒ 改名会**静默脱靶**——这正是 NeoForge 刻意**不**做 ASM 覆盖的原因（§E.8）。

**易混点**：与 `-DmergeModules`（§C.4）不同：`ignoreList` 是"忽略这些 jar"，`mergeModules` 是"把这些 jar 合并进模块"。

**落点**：`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`、`needsAsmOverride`（注释）。

### C.4 `-DmergeModules`

**定义**：bootstraplauncher 的**属性**：按**文件名**在 classpath 里查一批 jar，把它们**合并成同一个模块**（union filesystem）。

**形式化**：`-DmergeModules=<逗号分隔的文件名>`（如 `jna-5.10.0.jar,jna-platform-5.10.0.jar`）；加载器按**文件名查表**，查不到就拿空集去 union 合并 ⇒ 读 `/META-INF/versions` 抛 `UnionFileSystem$NoSuchFileException` / `Duplicate key`。

**如何观测**：`GameLauncher CMD:` argv 里的 `-DmergeModules=…`；启动侧对"点名件在真树里不存在"打 warn `mergeModules: <fileName> declared by loader but absent from real tree (<relPath>); declared-vs-tree mismatch -> name lookup will fail`。

**例**（点名值来自 json，脱靶 warn 来自日志）：

- json 里那一条（来源：`stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json`，逐字）：`-DmergeModules=jna-5.12.1.jar,jna-platform-5.12.1.jar`。
- 当**真树里没有**同名的 `jna-5.10.0.jar` 时（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790752847-hilog.txt`）：
  `W mergeModules: jna-5.10.0.jar declared by loader but absent from real tree (net/java/dev/jna/jna/5.10.0/jna-5.10.0.jar); declared-vs-tree mismatch -> name lookup will fail`

**从这个例子里应当看出**：`mergeModules` 按**文件名**查表（`jna-5.10.0.jar`），查不到就拿空集去 union 合并 —— 于是 `-cp` 里必须**由启动/安装期按名补进**真正的 `jna-5.10.0.jar`（§C.4 为什么这样）；warn 行把"点名 vs 真树缺件"当场暴露。

**复现/观测**：`grep -F "mergeModules:" Harmomeow-Craft-Launcher/.logs/*.txt`；`grep -o '"\-DmergeModules=[^"]*"' stuffs/test-forge/versions/1.19.4-forge-install-test/1.19.4-forge-install-test.json`。

**为什么这样**：它要的 jar（如 `jna-5.10.0.jar`）**不在任何清单里**（vanilla 只声明另一个版本）⇒ 必须由安装期按名补下 + 启动期按名补进 classpath（`assembleRealTreeClasspath` 会解析 `-DmergeModules` 值并补进去）。

**易混点**：见 §C.3 易混点。另：NeoForge **安装链**会按名补下这些 jar，而 Forge 安装链不补 ⇒ Forge 实例真缺点名件时只能在启动期 warn（登记为条目 ID，见 §F.1）。

**落点**：`common/data/NeoForgeInstaller.ets` 的 `mergeModuleNames`、`resolveMergeModuleEntries`、`libraryNames`；`common/data/MinecraftLauncher.ets` 的 `assembleRealTreeClasspath`。

### C.5 `-DlibraryDirectory`

**定义**：Forge ② 代用于告诉加载器"库根目录在哪"的属性。

**形式化**：`-DlibraryDirectory=<gameRoot>/libraries`；由 json `arguments.jvm` 给出（经宏 `${library_directory}` 展开）、原样透传。

**如何观测**：`GameLauncher CMD:` argv 里的 `-DlibraryDirectory=…`。

**为什么这样**：加载器要按 maven 布局在库根下找件；本工程宏 `library_directory` = `<gameRoot>/libraries`（**不随版本隔离移动**，与 assets 一样是共享池）。

**易混点**：与 `${library_directory}`（**宏**）是一个值的两个写法：json 写宏，argv 里是展开后的绝对路径。与 `-DmergeModules`（按名合并模块）作用不同。

**落点**：`common/data/MinecraftLauncher.ets` 的 `makeMacros`（`library_directory`）、`buildLaunchArgv`（json 透传）。

### C.6 `inheritsFrom`

**定义**：版本 json 的**继承**字段：`<id>` 指向父版本，子版本只写差异、其余靠继承合并。

**形式化**：json 含**非空字符串** `inheritsFrom` ⇒ 形态 ①（`VERSION_FORM_INHERITS`）；解析器**递归**解析父实例并合并（**子覆盖父**；`libraries` 子在前父在后；`arguments` 基座在前、子追加）。父缺失 / 成环 ⇒ 退化为原版叶子。

**如何观测**：版本 json 里的 `inheritsFrom` 字段；`ResolvedVersion.form == "inherits"`。

**为什么这样**：官方安装器与外部导入的实例用这种"薄叶子"布局（如官方 Forge 安装器：`inheritsFrom = <MC 版本>`）。

**易混点**：与 §C.7 `patches[]`（HMCL 补丁式）**互斥**——判定顺序：有 `inheritsFrom` 优先判 ①，否则有含 `id == "game"` 的 `patches` 判 ②，否则原版。混合形态（继承之上再叠自身 `patches`）少见但支持。

**落点**：`common/data/VersionResolver.ets` 的 `detectVersionForm`、`resolveEffective`、`mergeInherit`、`VERSION_FORM_INHERITS`。

### C.7 `patches[]`

**定义**：HMCL 自装实例的**补丁式**布局：顶层是原版全字段的扁平化结果，`patches[]` 保留各层（`game` / `forge` / `fabric` / `neoforge`）供折叠。

**形式化**：json 含 `patches` 且其中**至少一条 `id == "game"`** ⇒ 形态 ②（`VERSION_FORM_PATCHES`）；解析器从**空清单**起，按 `priority` **升序**逐条折叠（缺省 priority 排最前）。

**如何观测**：版本 json 里的 `patches[]` 与其 `id` / `priority`；`ResolvedVersion.form == "patches"`。

**为什么这样**：Java 侧只读顶层字段 ⇒ `patches` 必须与顶层自洽（顶层 = patches 的折叠结果）；这也是安装链"顶层扁平 + `patches[game, 加载器]`"写盘格式的依据（`game` priority 0 / 加载器 patch priority 30000）。

**易混点**：`patches[]`（HMCL **版本清单**布局）≠ `install_profile.json` 的 `processors`（安装期工具链，§D.1）——都叫"补丁 / 处理"，但一个是版本清单的层、一个是安装的步骤。

**落点**：`common/data/VersionResolver.ets` 的 `hasGamePatch`、`sortedPatches`、`mergePatch`、`VERSION_FORM_PATCHES`；`common/data/VersionInstaller.ets` 的 `composeFabricManifest` / `composeForgeManifest` / `composeNeoForgeManifest`。

### C.8 `rules`

**定义**：MC 清单里用来**门控**某条参数 / 库"在当前平台是否生效"的规则数组。

**形式化**：判据（`ruleAllows`）：`rules` 未定义或空 ⇒ **允许**；否则**必须**存在一条 `action == "allow"` 且其 `os` 命中当前平台（`name` / `arch` 匹配）才放行；**带非空 `features` 的规则一律视为不匹配**（本工程不向 JVM 声明任何 feature）。平台取值 = `os.name == "linux"`、`os.arch == "aarch64"`。

**如何观测**：无独立日志；后果 = 某些带 `features` 的门控参数（如 `--width ${resolution_width}`）**不进** argv，避免被 Forge 的 joptsimple 解析失败（`NumberFormatException`）。

**为什么这样**：清单里的规则是**跨平台**的，本工程视鸿蒙为 `linux + aarch64`（`RULE_OS_NAME` / `RULE_OS_ARCH`）；`features` 门控必须显式不命中，否则会把带**未展开宏**的参数发出去。

**易混点**：库的 `rules` 过滤（`collectFromJson`）与参数的 `rules` 过滤（`collectArgs` / `ruleAllows`）是**同一判据的两处消费**；`features: {}`（空对象）等价于"无特性要求"、**照常命中**，只有**非空** `features` 才不命中。

**落点**：`common/data/MinecraftLauncher.ets` 的 `ruleAllows`；`common/data/VersionInstaller.ets` 的 `rulesAllow`；`common/constants/LaunchDefaults.ets` 的 `RULE_OS_NAME`、`RULE_OS_ARCH`。

### C.9 `natives`

**定义**：库的**原生载荷**（`.so` / `.dll` / `.dylib`）：清单里带 `natives` 映射（`os → classifier`）或 `downloads.classifiers` 的库条目。

**形式化**：库条目满足"`name` 带 classifier（`parts.length ≥ 4`）**或** `natives != undefined` **或** `downloads.classifiers != undefined`" ⇒ 是 natives 件。**本工程的 natives 不进 `-cp`**；原生库靠**随包同名库顶替**（§E.6）。

**如何观测**：库声明里的 `natives` / `classifiers`；启动 argv 里 `-Dorg.lwjgl.librarypath=<el1 目录>` 与 `-Dorg.lwjgl.system.bundledLibrary.nameMapper=…`。

**为什么这样**：见 §E.6（随包顶替 + nameMapper）。**同坐标的"普通 jar"与"natives 包"是两条不同的库**：Mojang 清单里同名条目会出现两次，只按 `name` 判等会把 natives 包当重复合并掉 ⇒ 本工程的库去重把"原生载荷不同"计入不相等判据。

**易混点**：`natives`（库字段）≠ `natives 目录`（`-Djava.library.path` / `${natives_directory}` 指向的**可写沙箱目录**，只作 JNA / LWJGL 的**解压工作目录**，真 native 从 el1 按名加载）。

**落点**：`common/data/VersionResolver.ets` 的 `VersionLibrary.natives`、`sameNative`；`common/data/MinecraftLauncher.ets` 的 `collectFromJson`（跳过 `org/lwjgl/*`）；`common/constants/Paths.ets` 的 `NATIVES_DIR`。

### C.10 平台伪装

**定义**：把本机真实 `os.name`（`HarmonyOS`）伪装成 `os.name=Linux` + `os.version=6.6` 的一对 `-D` 属性；**一切"另起 JVM"的路径都必须带它**。

**形式化**：常量 `TOOL_JVM_PLATFORM_SPOOF_ARGS = ["-Dos.name=Linux", "-Dos.version=6.6"]`（值取自 `SPOOF_OS_NAME` / `SPOOF_OS_VERSION`）；在 argv 里紧跟在可执行文件 `java` 之后、其余 `-D` 之前。**判据（不变量）**：任何 argv 若以 `java` 起头，第二个 token 必须（以）`-Dos.name=Linux` 开头。

**如何观测**：工具 JVM 的 job argv（`[java, -Dos.name=Linux, -Dos.version=6.6, -Djava.io.tmpdir=…, -cp, …, <主类>, …]`，见 `ForgeProcessorJob` / `NeoForgeProcessorJob`）；游戏侧在 `GameLauncher CMD:` 的"固定 JVM 参数"段。

**例**（游戏侧，来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790831197-hilog.txt` 的 `CMD:` 行）：整条命令以 `java` 起头，**第二个 token 就是**平台伪装

```
I CMD: /data/storage/el2/base/haps/entry/files/meow-jres/meow_jre_legacy/bin/java
        -Dos.name=Linux -Dos.version=6.6 -Dmeow.cpu.chip=KirinX90 -Duser.dir=… 
```

（安装期工具 JVM 的 argv 落在 `…/cache/forge-installer/official/<ver>/job-0.json`，见同页 §D.1 的 `job=` 路径；该文件在设备上、**本机不可读**，故此处只给游戏侧这一处真实读数。）

**从这个例子里应当看出**：伪装是 **argv 里真写出来的 `-D`**（`-Dos.name=Linux` 紧跟 `java`），而不是清单 `rules` 的匹配值（§C.10 易混点）；"任何以 `java` 起头的 argv 第二 token 必是 `-Dos.name=Linux`"这条不变量，直接在这行上可核对。

**复现/观测**：`grep -oE "bin/java -Dos\.name=Linux -Dos\.version=6\.6" Harmomeow-Craft-Launcher/.logs/*.txt | head`。

**为什么这样**：JDK 8 的 `sun.nio.fs.DefaultFileSystemProvider.create()` 按 `os.name` **精确匹配**（`Linux` / `SunOS` / `Darwin` / …），本机真 `os.name` 是 `HarmonyOS` ⇒ 匹配不上直接 `AssertionError: Platform not recognized`（发生在**类初始化期**，连主类都加载不到，`JLI` 退 1）。现代套 26 对未知 `os.name` 宽容回退 ⇒ **不可依赖"在 26 上没炸"**。

**易混点**：游戏参数的**平台规则过滤**用的也是同一对值（视鸿蒙为 `linux` / `aarch64`，§C.8），但那是**清单 `rules` 的匹配值**、不写进 argv；平台伪装是**写进 argv 的 `-D`**。两者同源、用途不同。

**落点**：`common/constants/LaunchDefaults.ets` 的 `TOOL_JVM_PLATFORM_SPOOF_ARGS`、`SPOOF_OS_NAME`、`SPOOF_OS_VERSION`；`common/data/VersionInstaller.ets` 的 `toolJvmArgv`；`common/data/MinecraftLauncher.ets` 的 `buildLaunchArgv`。

## §D 安装链

### D.1 processor

**定义**：`install_profile.json` 里的一条**安装期处理器**：以一个工具 jar 为单位、带 classpath / args /（可选）outputs，按 profile 顺序执行；Forge ≥1.13 / NeoForge 靠它产出打补丁后的 client jar。

**形式化**：`processors[]` 的每条 = `{sides?, jar, classpath?, args?, outputs?}`；`sides` 缺省 = 双端。**"安装要不要 JVM" 只由 client 侧 processor 数决定**：`forgeClientProcessorCount > 0` ⇒ 需 JVM。执行时**参数原样来自 profile、只做占位符替换**（§D.4）。

**如何观测**：安装进度的 `onCurrent(label)`（标签 = `<artifact>[:<--task 值>]`，如 `installertools:MCP_DATA`）；日志 `processor <label> handshake returned code=N`；失败消息 `processor failed (<label>) exit=N log=<路径> job=<路径>`。

**例**（`1.16.5-36.2.42` 的 `install_profile.json`，逐字；配合真实安装日志）：

- profile 里 4 条 processor（来源：`stuffs/research/forge-support/evidence/1.16.5-36.2.42/install_profile.json`）：`net.minecraftforge:installertools:1.3.0`（`--task MCP_DATA`）→ `net.minecraftforge:jarsplitter:1.1.4` → `net.md-5:SpecialSource:1.8.5` → `net.minecraftforge:binarypatcher:1.0.12`。
- 它们跑起来时的日志（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790837336-hilog.txt`）：
  `forge spec+processors form (client=4); delegating to new chain`，
  `forge processor installertools:MCP_DATA handshake returned code=0 elapsedMs=1002`，
  `forge processor jarsplitter handshake returned code=0 elapsedMs=7014`，
  `forge processor binarypatcher handshake returned code=0 elapsedMs=6015`。
- 失败时的形状（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790767330-hilog.txt`）：
  `E forge processor installertools:MCP_DATA exit=1 tool-stdio=/data/storage/el2/base/haps/entry/cache/forge-installer/official/36.2.42/logs/1-installertools_MCP_DATA.log job=/data/storage/el2/base/haps/entry/cache/forge-installer/official/36.2.42/job-0.json`

**从这个例子里应当看出**：label 就是 `<artifact>`（`jarsplitter` / `binarypatcher`）或 `<artifact>:<--task 值>`（`installertools:MCP_DATA`，§D.2）；"client 侧 processor 数"（这里 `client=4`）正是 §D.1 判据里"要不要 JVM"的那个数，也是 §D.11 的 `spec-processors` 判据。

**复现/观测**：`grep -F "forge processor" Harmomeow-Craft-Launcher/.logs/*.txt`；`python3 -c "import json;print([p['jar'] for p in json.load(open('stuffs/research/forge-support/evidence/1.16.5-36.2.42/install_profile.json'))['processors']])"`。

**为什么这样**：工具会 fail-open（参数错也退 0）⇒ **不信退出码，断言产物**（§D.5 / §D.6）。

**易混点**：`processor`（安装期工具）≠ `tweak class`（启动期扩展点，§B.11）——一个在**安装时**跑、一个在**启动时**跑。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `buildForgeProcessorPlans`；`common/data/NeoForgeInstaller.ets` 的 `buildNeoForgeProcessorPlans`；`common/data/VersionInstaller.ets` 的 `runForgeProcessors` / `runNeoForgeProcessors` / `forgeClientProcessorCount`。

### D.2 installertools

**定义**：Forge 安装链里出现频率最高的一支**工具 jar**（artifact 名 `installertools`），其不同**子任务**由 `--task <值>` 指定。

**形式化**：label 形如 `installertools:<--task 的值>`；② 代（1.17.1+）client 侧有 **3 个子任务**：`MCP_DATA` / `DOWNLOAD_MOJMAPS` / `MERGE_MAPPING`。**判据**：`--task <T>` 的相邻对 ⇒ `label = "installertools:" + T`。

**如何观测**：安装进度里的标签（带子任务名）；工具输出归档 `<workDir>/logs/<序号>-<label>.log`。

**为什么这样**：只用 artifact 名时，失败日志 `processor failed (installertools)` **分不清是哪个子任务**（诊断要求）；故 label 必须带 task。

**易混点**：`installertools`（Forge 工具集）≠ 其它工具 jar（`jarsplitter` / `SpecialSource` / `binarypatcher` / `mcp_config`）——它们同为"安装期工具"，但 artifact 名不同。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `forgeProcessorLabel`。

### D.3 `:neoinstall` 载体

**定义**：安装期工具 JVM 的**宿主**：一个**独立进程**的无窗 `UIAbility`（进程名 `:neoinstall`），负责跑一次工具 JVM 并写出退出码。

**形式化**：ability 名 = `NeoInstallAbility`，进程后缀 = `:neoinstall`（静态 `process: ":neoinstall"`）。启动参数 = `StartOptions{processMode: NEW_PROCESS_ATTACH_TO_PARENT, startupVisibility: STARTUP_HIDE}`（**二者必须成对**，仅 2in1 / Tablet 支持）⇒ 窗口不显示、dock 无图标、`onForeground` 不回调。每次 processor 起**一次**进程（JVM 一进程一 VM）。

**如何观测**：`startAbility` 传 `parameters.job=<job 文件路径>`；job 文件 = JSON `{argv, rootUri, jreId}`；退出码经桥 headless 写 `<filesDir>/meow-neo-jvm-result.txt`，握手串 `JLI_BEGIN args=N` / `JLI_RETURNED code=N`；可重试错误码 `16000068` / `16000050`。

**为什么这样**：JVM 硬绑**进程**（HotSpot 一进程一 VM，二次 `JLI_Launch` 必败），而桥在 `JLI_Launch` 返回后**无条件 `_exit`** ⇒ 安装 JVM **必须放独立进程**（否则 `_exit` 带走整个 App）。**为什么不能 exec**：JRE 数据在 el2（禁执行）、el1 无可执行的 `java`。

**易混点**：`:neoinstall` 是**进程名**（安装期），`:game` 是游戏进程名（启动期）；载体名叫 "neoinstall" 但**两条链共用它**（Forge ≥1.13 与 NeoForge 都经 `runToolJvmOnce` 起它）——名字是历史包袱，不是"只服务 NeoForge"。

**落点**：`common/constants/LaunchContract.ets` 的 `NEO_INSTALL_ABILITY`、`NEO_INSTALL_PROCESS_SUFFIX`；`common/data/VersionInstaller.ets` 的 `startToolJvmAbility`、`runToolJvmOnce`、`toolJvmArgv`；`common/constants/Paths.ets` 的 `NEO_JVM_RESULT`、`NEO_JVM_TOOL_LOG`。

### D.4 占位符展开

**定义**：把 `install_profile.json` 里 processor 参数 / `data` 值中的**三种形态**替换成**绝对路径 / 字面量**的那一步。

**形式化（三形态 + 内建变量）**：

| 形态 | 字面 | 展开为 |
|---|---|---|
| 字面量 | `'text'`（单引号包裹） | `text`（去引号） |
| 坐标 | `[g:a:v[:classifier][@ext]]` | `<libraryDir>/<maven 路径>`（§A.7） |
| 变量 | 其它，含 `{KEY}` | 值 = `vars[KEY]`；**未定义 ⇒ 抛错** `unresolved placeholder {KEY}` |

另：`data` 值若以 `/` 开头（如 `/data/client.lzma`）= installer 包内路径 ⇒ 展开为 `<unzipDir>+<原串>`。**内建变量**（恒注入）：`SIDE=client` / `MINECRAFT_JAR` / `MINECRAFT_VERSION` / `ROOT` / `INSTALLER` / `LIBRARY_DIR`。

**如何观测**：job 文件里的 `argv`（已展开为绝对路径）；失败消息 `unresolved placeholder {KEY}`。

**例**（`1.16.5-36.2.42` 的 `data`，来源：`stuffs/research/forge-support/evidence/1.16.5-36.2.42/install_profile.json`，逐字）：三种形态在同一份 profile 里各出现一次

| 形态 | 原文（`data[KEY].client`） | 展开为 |
|---|---|---|
| 坐标 `[…]` | `PATCHED` = `[net.minecraftforge:forge:1.16.5-36.2.42:client]` | `<libraryDir>/net/minecraftforge/forge/1.16.5-36.2.42/forge-1.16.5-36.2.42-client.jar`（§A.7） |
| 变量 `{…}` | `MC_SLIM` = `{MC_SLIM}` 作为 processor arg 出现，值来自 `data` | 由 `data` 逐层解析 |
| 字面量 `'…'` | `MC_SLIM_SHA` = `'045d6edac8fe1b004e159c49704b5b729f551079'` | 去引号后的 sha1 字面量 |
| 包内路径 `/…` | `BINPATCH` = `/data/client.lzma` | `<unzipDir>/data/client.lzma`（installer 包内） |

processor 的 `args` 也原样引用这些键，如 `net.minecraftforge:jarsplitter:1.1.4` 的 `["--input","{MINECRAFT_JAR}","--slim","{MC_SLIM}","--extra","{MC_EXTRA}","--srg","{MAPPINGS}"]`。

**从这个例子里应当看出**：`{…}` 由 `data` 提供（`MC_SLIM` / `PATCHED` …），`[…]` 是坐标、`'…'` 是字面量、`/…` 是包内路径——三者**各按各的规则展开**，`buildForgeProcessorPlans` 只做替换、不解析语义；展开结果就是 job 文件里 `argv` 的绝对路径。

**复现/观测**：`python3 -c "import json;d=json.load(open('stuffs/research/forge-support/evidence/1.16.5-36.2.42/install_profile.json'))['data'];print({k:v['client'] for k,v in d.items()})"`。

**为什么这样**：**参数原样来自 profile**，只做替换 ⇒ 不必理解 `--task MCP_DATA` 之类语义，也不随 `InstallerTools` 的 CLI 版本漂移。

**易混点**：与启动期的 `${…}` 宏替换（`MinecraftLauncher.expand`）**不是同一套**：安装期用 `{KEY}`（单花括号、值来自 `data`），启动期用 `${name}`（美元 + 花括号、值来自 `makeMacros`）。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `expandForgeValue`、`buildForgeProcessorPlans`；`common/data/NeoForgeInstaller.ets` 的 `expandValue`。

### D.5 `outputs` 幂等

**定义**：processor 声明的**产物集**（`{路径占位键: sha1 占位值}`），用于"已装过就跳过、没装对就重来"。

**形式化**：`outputs` 是**对象**（不是数组）；展开后 = 一组 `(路径, sha1)`。**预检**（`forgeOutputsAllMatch`）：`outputs ≠ ∅ ∧ 每项文件存在 ∧ sha1 相符` ⇒ 整条 processor **跳过**。否则：先删不符 / 为空的陈旧产物（`forgeRemoveStaleOutputs`）→ 执行工具 → **执行后校验**（`forgeVerifyOutputsOrThrow`）：sha1 为主判据，**仅 `.jar`** 不符时降级为 ZIP 结构校验（§D.8），仍不符 ⇒ **先删产物再抛**。

**如何观测**：日志 `forge processor <label> skipped (outputs already match)`；失败消息 `processor output rejected (<label>): <路径> expected-sha1=… actual-sha1=… reason=<sha1-mismatch|missing|sha1-mismatch+zip-invalid>`。

**例**（`1.16.5-36.2.42` 的 `processors[].outputs`，来源：`stuffs/research/forge-support/evidence/1.16.5-36.2.42/install_profile.json`，逐字）：`outputs` 是**对象**（`{路径占位键: sha1 占位值}`）

```
jarsplitter      outputs = { "{MC_SLIM}": "{MC_SLIM_SHA}", "{MC_EXTRA}": "{MC_EXTRA_SHA}" }
binarypatcher    outputs = { "{PATCHED}": "{PATCHED_SHA}" }
installertools   （无 outputs）
SpecialSource    （无 outputs）
```

把键值一起展开后即一组 `(路径, sha1)`（如 `{PATCHED:…-client.jar} : 427f13ce6f486c182c9693e94e907e2eb049773f`）——`forgeOutputsAllMatch` 正是逐个比对这个 sha1。

**从这个例子里应当看出**：`outputs` 不是"又一份文件清单"，而是"**产物 + 期望 sha1**"的对象；有 `outputs` 的两条（`jarsplitter` / `binarypatcher`）恰是**动态生成 jar** 的两条——这正是 §D.8 ZIP 结构降级只发生在它们产出的 `.jar` 上的原因。**注意**：本批留存日志里**没有**出现 `skipped (outputs already match)` / `output rejected` 字符串，故此处**只用 profile 真值**、不引日志。

**复现/观测**：`python3 -c "import json;print([{'jar':p['jar'],'outputs':p.get('outputs')} for p in json.load(open('stuffs/research/forge-support/evidence/1.16.5-36.2.42/install_profile.json'))['processors']])"`。

**为什么这样**：工具多数"先删后写"、非原子 ⇒ 中断可能留下半成品；幂等预检让"重入 / 重试不重跑工具"，产物校验把"工具退 0 但产物不对"也挡住。

**易混点**：**预检只看 sha1**（对齐 HMCL 的 ProcessorTask 预检），ZIP 结构降级**只属执行后校验**——这样"预检认为命中"与"执行后接受"两个判据不互相冲突。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `forgeOutputsAllMatch`、`forgeRemoveStaleOutputs`、`forgeVerifyOutputsOrThrow`、`ForgeOutputTarget`；编排侧 `common/data/VersionInstaller.ets` 的 `runForgeProcessors`。

### D.6 PATCHED 断言

**定义**：安装成功的**唯一硬判据**：processor 链跑完后，"打补丁后的 client jar"（profile `data` 里键名为 `PATCHED` 的那件）必须存在。

**形式化**：`vars.get("PATCHED")` = 展开后的绝对路径（§D.4）；`ForgeProcessorSet.patchedPath`（= 同一值）。**断言**：`patchedPath ≠ "" ∧ exists(patchedPath)`，否则抛 `forge patched client jar missing after processors`（NeoForge 侧文案 `neoforge patched client jar missing after processors`）。

**如何观测**：失败消息 `… patched client jar missing after processors`；成功 = 该文件在 `<gameRoot>/libraries/…` 下存在。

**为什么这样**：工具 fail-open（参数错也退 0）⇒ 不能只信退出码；`PATCHED` 存在 = "字节码重命名真跑完了"的可判定证据。

**易混点**：`PATCHED` 是 `data` 的一个**键**（值 = 产物绝对路径）；不同世代的 profile 键集不同，本工程的断言是**存在性**（`PATCHED`），逐 sha1 校验由 §D.5 的 `outputs` 承担。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `ForgeProcessorSet.patchedPath`、`buildForgeProcessorPlans`；`common/data/NeoForgeInstaller.ets` 的 `NeoForgeProcessorSet.patchedPath`；`common/data/VersionInstaller.ets` 的 `installForgeNewVersion` / `installNeoForgeVersion`。

### D.7 内嵌 `maven/`

**定义**：installer jar 内部自带的一份 **maven 布局目录** `maven/**`（§A.7），用于兜住"清单里 `url` 为空"的件。

**形式化**：`<unzipDir>/maven/<maven 相对路径>`；**命中即拷贝**到 `<gameRoot>/libraries/<同路径>`。**必须在库下载之前**做，靠下载的"目标已存在即跳过"语义接住。① 代（1.13–1.16.5）恒 7 条 = 5 目录项 + 主制品 `forge:<ver>` + `:universal`。

**如何观测**：文件系统 `<unzipDir>/maven/…`；拷贝后 `<gameRoot>/libraries/…` 存在。

**例**（`1.13.2-25.0.223` 的 installer.jar，来源：`stuffs/research/forge-support/evidence/1.13.2-25.0.223/maven-list.txt`，即 installer.jar 的 ZIP 条目列表，逐字）：

```
maven/
maven/net/
maven/net/minecraftforge/
maven/net/minecraftforge/forge/
maven/net/minecraftforge/forge/1.13.2-25.0.223/
maven/net/minecraftforge/forge/1.13.2-25.0.223/forge-1.13.2-25.0.223-universal.jar   (2385532 B)
maven/net/minecraftforge/forge/1.13.2-25.0.223/forge-1.13.2-25.0.223.jar               ( 159947 B)
```

（同形状见 `stuffs/research/forge-support/evidence/1.16.5-36.2.42/maven-list.txt`。）这 **7** 条 = 5 目录项（`maven/`+`net/`+`minecraftforge/`+`forge/`+`<ver>/`）+ 主制品 `forge-<ver>.jar` + `:universal`。

**从这个例子里应当看出**：内嵌 `maven/` 的路径就是**真 maven 布局**（§A.7），解包后原样拷进 `<gameRoot>/libraries/` 即可命中"目标已存在即跳过"的下载语义；它兜住的正是 ① 代那两件 `url` 为空的 `forge:<ver>` / `:universal`（§D.7 为什么这样）。

**复现/观测**：`unzip -l stuffs/research/forge-support/evidence/1.13.2-25.0.223/installer.jar | grep -F "maven/net/minecraftforge/forge/"`（`maven-list.txt` 是该命令的落盘结果）。

**为什么这样**：① 代的主制品 `net.minecraftforge:forge:<ver>` 与 `:universal` 的库 `url` 是**空串** ⇒ 下载会穿透到缺省库仓（`libraries.minecraft.net`）生成 404；只有从内嵌 `maven/` 取。

**易混点**：`内嵌 maven/`（**installer jar 里的**一份）≠ §A.7 的"真 maven 树"（**游戏根 `libraries/` 里的**真布局）——前者是"取件的来源"，后者是"classpath 指向的落点"。

**落点**：`common/data/VersionInstaller.ets` 的 `installForgeVersion`（新形态 0 processor 分支）、`installForgeNewVersion`（内嵌 `maven/**` 解包段）；`common/data/ForgeNewInstaller.ets` 的 `ForgeExpandContext.unzipDir`。

### D.8 ZIP 结构降级

**定义**：`outputs` 执行后校验里，"sha1 不符"的**唯一**豁免：**仅 `.jar`** 输出，若"ZIP 结构可读 + 条目能完整解出"则接受。

**形式化**：`sha1(actual) ≠ expected ∧ path.toLowerCase().endsWith(".jar") ∧ zipStructurallyValid(path)` ⇒ 接受并打 warn（**不伪造 sha1、不写"已核对"**）；非 `.jar`、或 `.jar` 但结构也不合法 ⇒ 先删产物再抛。

**如何观测**：warn `output sha1 mismatch but ZIP structure is valid; accepting (zlib-downgrade) label=<label> file=<path> expected=<sha1> actual=<sha1>`。

**为什么这样**：Forge 的 processor 在安装期**动态生成** jar（`jarsplitter` 的 `MC_SLIM` / `MC_EXTRA`、`binarypatcher` 的 `PATCHED`）；若设备沙箱的 deflate 实现与官方"参考 zlib"逐字节不同，官方 `install_profile.json` 记录的 sha1 **必然不符** ⇒ 不做降级会让安装**必然失败**。**NeoForge 侧没有这个降级**（正是"Forge / NeoForge 两条链分开实现"的收益之一）。

**易混点**：降级**只**发生在**执行后校验**（§D.5 易混点），不在**预检**；且**只**对 `.jar`。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `forgeZipStructurallyValid`、`isJarOutput`、`forgeVerifyOutputsOrThrow`。

### D.9 installer 缓存自愈

**定义**：installer jar 被跨实例缓存（"按路径命中即跳过"）时，**复用前先解一次**以证明它可用；解不开即判坏、删除、重下。

**形式化**：判据 = `extractArchive()` 能否解出**下游真正要用的东西**（`install_profile.json` + `spec` 形态的内嵌启动清单）；缺任一 ⇒ 打 warn `cached <loader> installer unusable, re-downloading: <路径> (<错误>)` ⇒ `unlink` 坏件 ⇒ 重下再解。workDir 按**下载源 + loader 版本**隔离（`<cache>/<loader>-installer/<源>/<版本>/`）。

**如何观测**：warn 串（上）；workDir 路径。

**为什么这样**：官方源元数据**没有 installer 的 sha1** ⇒ 不做哈希校验；而"命中即跳过"会把半截 / 被破坏的文件**永久复用** ⇒ 必须靠"复用前先解一次"当自愈。

**易混点**：与 §D.5 的 `outputs` 幂等是**不同层的幂等**：这个防"输入件坏"，那个防"输出件缺 / 错"。

**落点**：`common/data/VersionInstaller.ets` 的 `installForgeVersion`（`extractArchive` / 自愈分支）、`installForgeNewVersion`（`extractNewArchive`）、`installNeoForgeVersion`（`extractArchive`）。

### D.10 DOWNLOAD_MOJMAPS

**定义**：Forge ② 代 client 侧 processor 里的一个 `installertools --task DOWNLOAD_MOJMAPS` 子任务，用来下载官方的 Mojang 混淆映射。

**形式化**：label = `installertools:DOWNLOAD_MOJMAPS`（§D.2 的 label 取法）。该工具**硬编码 `launchermeta.mojang.com`、在工具内自建 HTTP** ⇒ 本工程的镜像 / 源切换对它**无效**（不可镜像）。本工程按 processor **原样执行**（起工具 JVM）。

**如何观测**：安装进度标签 `installertools:DOWNLOAD_MOJMAPS`；工具输出归档。

**为什么这样**：只命中 ② 代；降级为"健壮性改进"（设备网络可达该域名）。可选修法 = 仿 HMCL 特判为"可镜像的纯下载、不起 JVM"。

**易混点**：与 §D.2 的其它两个子任务（`MCP_DATA` / `MERGE_MAPPING`）不同：那两个是本地处理，这个是**网络下载**（故有"可镜像 / 可特判"的话题）。

**落点**：`common/data/ForgeNewInstaller.ets` 的 `forgeProcessorLabel`；编排侧 `common/data/VersionInstaller.ets` 的 `runForgeProcessors`（**无特判 = 原样执行**）。

### D.11 spec

**定义**：`install_profile.json` 的**形态键** `spec`：它的**有无**区分"Forge 新格式安装器"与"老格式安装器"。

**形式化**：`spec != undefined` ⇒ 新格式；此时再看 **client 侧 processor 数**：`> 0` ⇒ `spec-processors`（需外部 JVM，1.13–1.20.1）；`= 0` ⇒ `spec-no-processor`（零 JVM，1.12.2）。`spec == undefined ∧ install != undefined ∧ versionInfo != undefined` ⇒ `legacy`（零 JVM，≤1.8.9）。两键皆无 ⇒ `unsupported`（明确拒绝）。**判据 = 键的存在性 + processor 数，不是 `spec` 的具体值、也不是 MC 版本号。**

**如何观测**：日志 `forge spec+processors form (client=N); delegating to new chain`；错误 `forge install unsupported: unknown install_profile.json format`。

**例**（`stuffs/research/forge-support/evidence/*/install_profile.json` 的真实键集，逐条核对）：

| 版本目录 | `spec` | `processors` 数 | `install` / `versionInfo` | 形态判定 |
|---|---|---|---|---|
| `1.7.10-10.13.4.1614-1.7.10` | 无 | 0 | 有 / 有 | `legacy`（零 JVM） |
| `1.8.9-11.15.1.2318-1.8.9` | 无 | 0 | 有 / 有 | `legacy`（零 JVM） |
| `1.12.2-14.23.5.2864` | `0` | 0 | 无 / 无 | `spec-no-processor`（零 JVM） |
| `1.13.2-25.0.223` | `0` | 5 | 无 / 无 | `spec-processors`（需 JVM） |
| `1.16.5-36.2.42` | `0` | 4 | 无 / 无 | `spec-processors`（需 JVM） |

配套日志（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790765950-hilog.txt`）：`forge spec+processors form (client=4); delegating to new chain`。

**从这个例子里应当看出**：`spec` 的**有无**分"新 / 老格式"，`processors` 数分"要不要 JVM"——**同是 `spec:0`，`1.12.2`（0 条）零 JVM、`1.16.5`（4 条）要 JVM**；`1.7.10 / 1.8.9` 两键都没有 `spec`、只有 `install`/`versionInfo` ⇒ `legacy`（§D.11 判据 = 键的存在性 + processor 数）。

**复现/观测**：`for d in stuffs/research/forge-support/evidence/*/; do python3 -c "import json,sys;j=json.load(open('$d/install_profile.json'));print('$d', 'spec='+str(j.get('spec')), 'proc='+str(len(j.get('processors',[]))))"; done`。

**为什么这样**："要不要 JVM"由 processor 数决定（`spec:0` 的 1.12.2 恰是 `processors: []`）⇒ 这就是 §D.1 判据的由来；`spec` 只是"新格式"的形态标签。

**易混点**：`spec`（**安装器**形态键）≠ §B.2 的"世代 ①/②/③"（**启动**形态）——同一"代"既有 `spec:0` 又有 `spec:1`，两者**正交**。

**落点**：`common/data/VersionInstaller.ets` 的 `classifyForgeProfile`、`FORGE_FORM_LEGACY`、`FORGE_FORM_SPEC_NO_PROCESSOR`、`FORGE_FORM_SPEC_PROCESSORS`、`FORGE_FORM_UNSUPPORTED`、`forgeClientProcessorCount`。

## §E 渲染 / 环境 / JRE

### E.1 LWJGL 单代

**定义**：本工程对**现代** MC（≥1.13）只随包**一代** LWJGL3（3.4.3）；更老的 LWJGL3 声明（3.1.x / 3.2.x / 3.3.x）一律**就近归并**到它。

**形式化**：`LWJGL_GEN_TABLE = [{minMajor:3, minMinor:4, gen:"3.4.3"}]`；择代判据 `lwjglGeneration` = 取"声明 `org.lwjgl:lwjgl:<ver>` 的 `(major,minor)` ≥ 门槛"的**最高**代，未命中任何门槛也落到表末（地板）。**legacy（≤1.12.2）不走此表**——用 MC 自带的 LWJGL2 + 自编 `liblwjgl.so`。

**如何观测**：`-Dmeow.lwjgl.gen=<tag>`（如 `3.4.3`）；`-Dorg.lwjgl.system.bundledLibrary.nameMapper=org.lwjgl.system.MeowBundledNameMapper`；平铺目录里 `lwjgl-<gen>.jar`；日志 `stage <key>-<id>: gen=<gen> keep=<jar>(N)`。

**为什么这样**：现代只剩一代 ⇒ staging **不再"选代"**；某版本真缺 API ⇒ 运行期显式 `NoSuchMethodError`（= "该加一代"的信号）。3.4.3 能服务 1.13–1.21.x，靠 overlay 里的 **3.4.x 兼容 shim**。

**易混点**：**legacy LWJGL2**（`isLegacyLwjgl`，声明 `org.lwjgl.lwjgl:*`）与 **LWJGL3** 都定义 `org.lwjgl` 包 ⇒ 同时进 classpath 会 `sealing violation`（故 legacy 实例不得混入随包 LWJGL3）。

**落点**：`common/data/MinecraftLauncher.ets` 的 `LWJGL_GEN_TABLE`、`lwjglGeneration`、`isLegacyLwjgl`；`common/constants/LaunchDefaults.ets` 的 `LWJGL_GEN_343`、`LWJGL_GEN_JARS`、`LWJGL_NAME_MAPPER`。

### E.2 gl4es FPE

**定义**：**固定管线（FPE = Fixed-Pipeline Emulation）**渲染路径：用自编 `gl4es` 把桌面固定管线 GL 调用**翻译**到原生 GLES（因为 GLES 无固定管线）。

**形式化**：判据 = MC 版本 **< 1.17**（`isLegacyVersion`）⇒ 走 gl4es；`RendererChoice.lib = "libgl4es.so"`、`env = "gl4es"`、`glProfile = "compat"`，**不注入** `MEOW_GL3`。适用 MC ≤1.16（含 legacy 1.6.x–1.12.2）。

**如何观测**：`-Dorg.lwjgl.opengl.libname=libgl4es.so`；桥按 `MEOWCRAFT_RENDERER=gl4es` 建 GLES 上下文。

**为什么这样**：GLES 无固定管线，只能用翻译层仿真；gl4es 跑在原生 GLES 上，绕开系统 `libGLv4.so`（Mesa Zink）compat 路径的渲染错乱。

**易混点**：与 §E.3 `gl4es core` 用**同一个 lib / env**（`libgl4es.so` / `gl4es`），区别只在"是否注入 `MEOW_GL3`"——即**按 MC 版本自动分流**（<1.17 → FPE；≥1.17 → core）。

**落点**：`common/data/RendererPolicy.ets` 的 `rendererForVersion`、`isLegacyVersion`；`common/constants/LaunchDefaults.ets` 的 `RENDERER_LIB_GL4ES`、`RENDERER_ENV_GL4ES`。

### E.3 gl4es core（MEOW_GL3）

**定义**：gl4es fork 的**核心档（core-profile）**后端：把 GL 3.2 / 3.3 core 调用翻译到原生 GLES 3.2，用于**无系统桌面 GL** 的设备（如手机）。

**形式化**：判据 = MC 版本 **≥ 1.17** 且设备无桌面 GL（`!isDesktopGlExpected`）⇒ `lib = libgl4es.so`、`env = gl4es`、`glProfile = core`，**额外注入** `MEOW_GL3=1` + `MEOW_STRICT_CAPS=1`。对应 UI「渲染后端」档 = `gl4es3`。

**如何观测**：渲染 env 里的 `MEOW_GL3=1`；桥日志 `created OpenGL ES 3.2 context for gl4es core backend` / `[meowcore] core backend init`。

**为什么这样**：1.17–1.21.x 要 GL 3.2 / 3.3 core（含 UBO / `glMapBufferRange` / fence / instancing）⇒ gl4es FPE 结构性不可用；无桌面 GL 的设备只能走 core → GLES 3.2。`MEOW_STRICT_CAPS=1` 让能力守卫用"公布 + 可解析"的诚实口径。

**易混点**：见 §E.2 易混点。另有"静默 no-op 陷阱"（core 入口面：GL 入口被公布但实际 no-op，登记为条目 ID，见 §F.1）。

**落点**：`common/data/RendererPolicy.ets` 的 `rendererForVersion`、`isDesktopGlExpected`；`common/constants/LaunchDefaults.ets` 的 `RENDERER_BACKEND_GL4ES3`。

### E.4 桌面 GL core

**定义**：**有系统桌面 GL** 的设备（2in1 / tablet）在 ≥1.17 走的渲染路径：经"GL guard"（`libmeowglguard.so`）透传到系统桌面 GL（`libGLv4.so`）。

**形式化**：判据 = MC 版本 **≥ 1.17** 且 `isDesktopGlExpected()`（`deviceInfo.deviceType ∈ {2in1, tablet}`）⇒ `lib = libmeowglguard.so`、`env = openglv4`、`glProfile = core`。guard 对 `glTexSubImage2D` 加后置同步（可选，由 `guardNeedsSync` 定）。

**如何观测**：`-Dorg.lwjgl.opengl.libname=libmeowglguard.so`；env `MEOWCRAFT_RENDERER=openglv4`；桥日志 `created desktop OpenGL …`。

**为什么这样**：桌面 GL 是"真·桌面后端"，性能与兼容性最好；guard 是给少数"客户端内存入口"补同步拷贝、规避 Mesa glthread UAF 的落点。

**易混点**：`libmeowglguard.so`（guard，本工程自研薄透传层）≠ `libGLv4.so`（系统桌面 GL，§E.5）——guard 是**转发到**后者的那一层；回滚 = 把 lib 直接指向 `libGLv4.so`。

**落点**：`common/data/RendererPolicy.ets` 的 `rendererForVersion`、`isDesktopGlExpected`、`guardNeedsSync`；`common/constants/LaunchDefaults.ets` 的 `RENDERER_LIB`、`RENDERER_LIB_REAL_GL`、`RENDERER_ENV`。

### E.5 Zink

**定义**：系统桌面 GL 库 `libGLv4.so` 的**实现身份**：Mesa 的 **Zink**（"GL over Vulkan"）后端——把桌面 GL 调用转译到 Vulkan。

**形式化**：`libGLv4.so` = Mesa Zink（over Vulkan 的 GL 4.2 core / compat）；本工程把它当"系统桌面 GL"用（§E.4 的落点）。

**如何观测**：`/system/lib64/libGLv4.so` 的存在性（`RendererPolicy.isDesktopGlExpected` 的设备门）；GL 后端字符串。

**为什么这样**：这是本机唯一可用的"桌面 GL"；它的转译让"桌面 GL + 后端"这条链在无原生 GL 驱动的鸿蒙上成立。

**易混点**：Zink（GL → Vulkan 的**转译**）≠ §E.2 / §E.3 的 gl4es（GL → GLES 的**转译**）≠ MC 的**原生 Vulkan 后端**（26.2+，走自研 `libmeowvulkan.so` shim）——三条是**不同的翻译 / 后端路线**，别混。

**落点**：`common/constants/LaunchDefaults.ets` 的 `RENDERER_LIB_REAL_GL`（= `libGLv4.so`）；`common/data/RendererPolicy.ets` 的 `isDesktopGlExpected`。

### E.6 natives 顶替

**定义**：本工程**不按清单的 `natives` 规则解压原生库**，而是用**随包同名库**顶替：native 从只读随包区（el1）按名 `dlopen`。

**形式化**：`collectFromJson` **跳过**一切 `org/lwjgl/*`（LWJGL3 由随包 clean-room 合并 jar 替代；legacy 的 LWJGL2 core / util 例外保留）。**命名 / 查名两处锁步**：`tools/lwjgl/install_natives.sh` 按规则铺名（`liblwjgl_<世代号紧跟基名>.so`），`org.lwjgl.system.MeowBundledNameMapper` 按名查。启动设 `-Dorg.lwjgl.system.bundledLibrary.nameMapper=…` + `-Dmeow.lwjgl.gen=<tag>`。

**如何观测**：`-Dorg.lwjgl.librarypath=<el1 目录>`、`-Djava.library.path=<craft>:<el1>:<natives 目录>`、`-Dorg.lwjgl.system.bundledLibrary.nameMapper=…`。

**为什么这样**：平台对**随包 native 打 fs-verity**，运行时写入数据区的文件 `dlopen` 一律 `EINVAL` ⇒ native **必须随包**；且 hvigor 只打包 `libs/<abi>/` **顶层** `.so`（子目录 / 非 `.so` 一律丢弃）⇒ 各代 native **同放一个扁平目录**，靠世代号紧跟基名消歧。

**易混点**：与 §C.9 的 `natives`（**库字段 / 声明**）不同：这个是**实现**（怎么把 .so 拿到手）。另："natives 目录"（可写沙箱，JNA / LWJGL 的解压工作目录）只作工作目录，**真 native 从 el1 按名加载**。

**落点**：`common/data/MinecraftLauncher.ets` 的 `collectFromJson`、`buildLaunchArgv`；`common/constants/LaunchDefaults.ets` 的 `LWJGL_NAME_MAPPER`、`LWJGL_GEN_JARS`。

### E.7 JRE 档（Java 8 / 26）

**定义**：本工程**随包两套 JRE**（档）：现代套 = OpenJDK **26**；legacy 套 = Java **8**。启动时按 (MC 版本 × loader) **择一**。

**形式化**：`BUNDLED_RUNTIMES = [{id:"meow_jre", javaMajor:26}, {id:"meow_jre_legacy", javaMajor:8}]`。选择 = 两张表的 join（`JavaPolicy`）：表 A「(MC 版本段 × loader) → 约束 `min` / `max` / `preferred`」× 表 B「可用 runtime（各带 `javaMajor`）」；求解 = 满足区间 → 取与 preferred 最接近者（同距取更高）。**无规则命中的组合 = "取最新" = 现代套 26**。关键段：Forge ≤1.12.2 → **强制上限 8**；Forge 1.13–1.16.999 → (0,17,8)；Forge 1.17–1.20.4 → (16,0,17)。

**如何观测**：日志 `JRE for <实例>: <id>`；逐段理由（稳定英文诊断串）在日志的 `reasonDiag`。

**为什么这样**：legacy Forge 需 `java.util.jar.Pack200`（JDK 14 删）与可用 `SecurityManager`（JDK 24 禁）⇒ 上限 8；两套 JRE 的 el1 `.so` + 数据**各占一个命名空间**（同名 `.so` 放同一目录会互相污染）。

**易混点**：随包只有 **26** 与 **8** ⇒ Forge 1.17–1.17.1 因 `min 16` 挡下 8、**静默落到 26**（偏离 HMCL 的 `MODLAUNCHER_8`）；**用户可覆盖**（`AUTO` / 指定 id；与规则冲突只记录、不静默改）。

**落点**：`common/data/JavaRuntime.ets` 的 `BUNDLED_RUNTIMES`、`JavaRuntime`；`common/data/JavaPolicy.ets` 的 `requirementFor`、`resolveJavaRuntime`、`autoChoice`、`pickBest`。

### E.8 ASM 覆盖

**定义**：为少数实例把 classpath 上的 **ASM** 换成**随包的一版**（9.9.1），因为实例声明的 ASM 读不懂**当前 JRE** 的类文件。

**形式化**：判据（`needsAsmOverride`）**两条都成立**：① **ModLauncher ≥ 10**（`declaredModLauncherVersion` 解析 `cpw.mods:modlauncher` / `net.minecraftforge:modlauncher`，`compareDottedVersion(ml,"10") ≥ 0`）；② **实例声明的 ASM 能力 < 当前 JRE 的 class major**（`asmMaxClassMajor(declaredAsm) < jreMajor + 44`）。**NeoForge 一律不触发**（`looksLikeNeoForge` ⇒ false）。命中且随包 5 件齐 ⇒ `rewriteAsmList` **同时改写 `-cp` 与 `-p`**、不残留旧套。

**如何观测**：日志 `asm override: bundled ASM 9.9.1 (5 jars) staged at <dir>; dropped declared modlauncher=<ver> asm=<ver> (jre=<26> -> class major <70>); -cp and -p rewritten`；不触发时 `asm override: not needed (modlauncher=<ver> asm=<ver> jre=<n>)`；件缺时 error `bundled ASM missing/incomplete at <dir> -> keeping declared ASM (expect "Unsupported class file major version <n>" on this JRE)`。

**例**（同一 workspace 下三个实例，逐条对读）：

| 实例 | 声明（来自实例 json） | 日志读数（含出处） | 判定 |
|---|---|---|---|
| `1.19.4-forge-install-test` | `modlauncher=10.0.8`，`asm=9.7.1` | `asm override: bundled ASM 9.9.1 (5 jars) staged at /data/storage/el2/base/haps/entry/cache/mc-cp/1.19.4-forge-install-test/asm9; dropped declared modlauncher=10.0.8 asm=9.7.1 (jre=26 -> class major 70); -cp and -p rewritten`（`Harmomeow-Craft-Launcher/.logs/This PC-1790837446-hilog.txt`） | **触发**（ModLauncher ≥10 且 9.7.1 读不懂 JDK 26 的 `major 70`） |
| `1.16.5` | `modlauncher=8.1.3`，`asm=9.6` | `asm override: not needed (modlauncher=8.1.3 asm=9.6 jre=8)`（`Harmomeow-Craft-Launcher/.logs/This PC-1790771715-hilog.txt`） | 不触发（ModLauncher <10） |
| `1.17.1` | `modlauncher=9.0.7`，`asm=9.1` | `asm override: not needed (modlauncher=9.0.7 asm=9.1 jre=26)`（`Harmomeow-Craft-Launcher/.logs/This PC-1790771680-hilog.txt`） | 不触发（ModLauncher <10） |

配套自证：覆盖后（`This PC-1790837446-hilog.txt`）`classpath real-tree: asm=/data/storage/el2/base/haps/entry/cache/mc-cp/1.19.4-forge-install-test/asm9/asm-9.9.1.jar (in-libraries=no)`；未覆盖时（`This PC-1790771715-hilog.txt`，`1.16.5`）`classpath real-tree: asm=/storage/…/stuffs/test-forge/libraries/org/ow2/asm/asm/9.6/asm-9.6.jar (in-libraries=yes)`。`-p` 侧的真值见 §C.1（那 5 件 ASM 也列在 `-p` 里）。

**从这个例子里应当看出**：判据是**两条同时成立**（`modlauncher ≥ 10` **且** 声明 ASM 能力 < 当前 JRE class major）——`1.17.1` 虽是 JRE 26，却因 `modlauncher=9.0.7 < 10` 而**不触发**；覆盖的效果不是"换了个 jar 路径"，而是**同时改 `-cp` 与 `-p`**（`-cp and -p rewritten`），所以 `in-libraries` 由 `yes` 翻成 `no`。

**复现/观测**：`grep -F "asm override" Harmomeow-Craft-Launcher/.logs/*.txt`；`grep -F "classpath real-tree: asm=" Harmomeow-Craft-Launcher/.logs/*.txt`。

**为什么这样**：`org.objectweb.asm` 9.7.1 读不懂 JDK 26 的类文件（`major 70`）⇒ modlauncher 10.0.8 的 `ClassTransformer.transform → computeHierarchyFromFile` 抛 `Unsupported class file major version 70`。分界**不在 ASM 版本算术**，而在"读 JDK 类文件"这件事的**组件版本**：ModLauncher ≥10 才去读 JDK 自己的类文件。

**易混点**：ASM 在两处出现：`-cp` 里有一份（`collectFromJson` 收真树里声明的 ASM）、`-p` 里也有一份（② 代 ASM 正是经 `-p` + §C.2 加载）⇒ **只改一处会留旧件 / 甚至造成同模块两份**。**判据里的 `modlauncher` 是库版本**，不是 §B.2 的"代"。

**落点**：`common/data/MinecraftLauncher.ets` 的 `needsAsmOverride`、`asmMaxClassMajor`、`ASM_CLASS_MAJOR_TABLE`、`rewriteAsmList`、`looksLikeNeoForge`、`logAsmProvider`；`common/constants/LaunchDefaults.ets` 的 `ASM_BUNDLED_VERSION`、`ASM_STAGE_SUBDIR`、`EXPECTED_ASM_JARS`。

### E.9 `mc-cp`（classpath 平铺暂存根）

**定义**：`<cacheDir>` 下与 `mc-run` **对等**的一级目录；其下**每实例一份** `<key>-<id>/`，装该实例 `-cp` 指向的 jar（`flat` = 整份平铺；`slim` = 只随包件 + oshi 补丁件）+ 子目录 `asm9/`（随包 ASM 覆盖件）。

**形式化**：目录常量 `MC_CP_DIR = 'mc-cp'`；实例目录 = `<cacheDir>/mc-cp/<key>-<id>`（`<key>` = `gameRootKey`，命名见 [`环境与载体.md`](环境与载体.md) §7.1；`-cp` 内容 / 三态见 §A.8）。

**如何观测**：`ls -1 <cache>/mc-cp`；日志 `extras <key>-<id>: …` 与 `stage <key>-<id>: mode=<flat|slim> sources=N`。

**落点**：`common/constants/Paths.ets` 的 `MC_CP_DIR`、`instanceCacheName`、`mcCpInstanceDir`。

### E.10 `mc-run`（运行目录根）

**定义**：`<cacheDir>` 下与 `mc-cp` **对等**的一级目录；其下**每实例一份** `<key>-<id>/`，装该实例沙箱运行目录（`java.io.tmpdir`）与子目录 `natives/`（JNA / LWJGL 解压工作目录）、`logs-fallback/`（§E.11）。

**形式化**：目录常量 `MC_RUN_DIR = 'mc-run'`；实例目录 = `<cacheDir>/mc-run/<key>-<id>`（命名同 §E.9）。

**如何观测**：`ls -1 <cache>/mc-run`；日志 `version <id> isolation=on runDir=<cache>/mc-run/<key>-<id>`。

**落点**：`common/constants/Paths.ets` 的 `MC_RUN_DIR`、`mcRunDir`、`NATIVES_DIR`。

### E.11 `logs-fallback`（兜底日志子目录）

**定义**：run 目录内的子目录 `<cacheDir>/mc-run/<key>-<id>/logs-fallback`；**仅当**实例内日志目录 `<gameRoot>/versions/<id>/.hmmcraft/logs` 建不出来 / 不可用时，作 `-XX:ErrorFile` 的**兜底**落点（**首选恒为实例内**）。

**形式化**：子目录常量 `MC_RUN_LOGS_FALLBACK_SUBDIR = 'logs-fallback'`；`mcRunLogsFallbackDir(runDir) = <runDir>/logs-fallback`。

**如何观测**：argv 的 `-XX:ErrorFile=…`——兜底为 `<cache>/mc-run/<key>-<id>/logs-fallback/hs_err_pid%p.log`，首选为 `<gameRoot>/versions/<id>/.hmmcraft/logs/hs_err_pid%p.log`。

**为什么**：`-XX:ErrorFile` 指到**不存在**的路径时，JVM 会**静默**把 hs_err 写回 cwd（= 游戏目录）⇒ 兜底目录必须在 JVM 启动前**确实建出来**；而 `mkdirSync(dir, true)` 对**已存在**的目录也抛 `File exists` ⇒ "建不出来"的判据只能是**目录最终可用**，不是 mkdir 有没有抛错（不变量见 [`决策与不变量.md`](决策与不变量.md) §26）。

**落点**：`common/constants/Paths.ets` 的 `MC_RUN_LOGS_FALLBACK_SUBDIR`、`mcRunLogsFallbackDir`；`common/data/GameLauncher.ets`（`-XX:ErrorFile` 选择）。

### F.2 渲染 / Vulkan shim 的 `F<n>`

| 编号 | 含义 |

| F72 | `vkCmdPushDescriptorSet` → 普通描述符集 |
| F73 / F74 | 默认强制 `preTransform=IDENTITY` |

## §G 实例：同一实例在三种形态下的对照

> **本节是 worked example**，材料**全部真实、逐字引用并标出处**；它只服务理解，**不新增定义**（定义仍在 §A–§E）。`-cp` 的公共前缀 `<workspace>/` 行内以 `…` 略去。

### G.1 三个主角

| 别名 | 实例目录（可本机 `ls`） | 主类（json 的 `mainClass`） | 形态 | loader / 世代 |
|---|---|---|---|---|
| 平铺样板 | `stuffs/test-fabric/versions/1.18.2/` | `net.fabricmc.loader.impl.launch.knot.KnotClient` | `flat` | Fabric |
| 有序样板 | `stuffs/test-forge/versions/1.12.2-Forge-OptiFine/` | `net.minecraft.launchwrapper.Launch` | `ordered`（此实例**曾经**是 `flat`） | legacy Forge + OptiFine |
| 真树样板 | `stuffs/test-forge/versions/1.19.4-forge-install-test/` | `cpw.mods.bootstraplauncher.BootstrapLauncher` | `real-tree`（+ ASM 覆盖） | Forge ② 代 |

三者主类分别来自各自 `versions/<id>/<id>.json`（可 `ls`）；`1.12.2-Forge-OptiFine` 的 json 另有 `patches[]` = `["game","forge","optifine"]`，`1.19.4-forge-install-test` 的 = `["game","forge"]`。

### G.2 逐实例对照

#### G.2.1 `flat` — Fabric `1.18.2`

- **① `-cp` 真值（完整）**：`-cp /data/storage/el2/base/haps/entry/cache/mc-cp/1.18.2/*`（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790788691-hilog.txt` 的 `CMD:` 行；同文件 `classpath mode=flat`）。
- **② 目录结构（示意；设备应用缓存，本机不可读）**：
```
<cacheDir>/mc-cp/1.18.2/        (<cacheDir> = /data/storage/el2/base/haps/entry/cache)
├── <整份声明库，平铺一层>.jar     ← 39 件（stage sources=39）
└── asm9/                         ← 随包 ASM 子目录（不参与一层通配）
```
- **③ staging 读数**（来源：`Harmomeow-Craft-Launcher/.logs/This PC-1790831580-hilog.txt`）：`stage 1.18.2: mode=flat sources=39`、`stage 1.18.2: gen=3.4.3 keep=lwjgl-3.4.3.jar(12953332) checked=39 copied=1`。

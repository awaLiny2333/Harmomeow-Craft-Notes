# 安装进度聚合方案（批量字节 + 进度条）

> 定位：**安装进度的口径与呈现设计**。要解决的是「16 个并发下载线程把读数写进同一组字段」造成的数字错乱。
> 边界：只改**展示层与进度采集**，不动下载/校验/落盘/清理语义；不引入取消按钮；不做跨批次总进度。
> 代码基线：`5c4797e`（主仓 HEAD）。**只引符号名，行号仅作辅助。**
> 同族：[`下载器-可靠性方案.md`](下载器-可靠性方案.md)（下载原语的结算契约）、[`安装链-总览.md`](安装链-总览.md)（四类安装的入口）。

---

## 1. 现状：一条 Text 被 16 个 worker 争用

### 1.1 事实

| 项 | 现状 |
|---|---|
| 并发度 | `DownloadContract.DOWNLOAD_CONCURRENCY = 16` |
| 「当前文件」 | `InstallerState.current`，由 `runDownloads` 的 worker **领任务时**写入（`onCurrent`） |
| 单文件字节 | `InstallerState.fileReceived` / `fileTotal`，由**任意一个**在飞文件写入 |
| 节流 | `Downloader.PROGRESS_INTERVAL_MS = 100`，但 `lastProgressAt` 是 `streamToFile` 的**局部变量** ⇒ 16 份独立节流 |
| 批次边界 | 每批 `runDownloads` 起点 `onCount(0, total)`，但**字节字段不重置** |
| 无 `Content-Length` | `dataReceiveProgress` 不触发（代码注释已声明）⇒ 该文件全程不更新读数 |

### 1.2 症状

1. **名字与数字不同源**：`current` 是"最近被领走的文件"，字节是"最近一次上报的任意文件" ⇒ 常见「`client.jar` + 38 MB / 430 MB」，而 client.jar 只有 30 MB。
2. **数字来回跳**：16 个 worker 交替写同两个 `@Trace` 字段，最后一个写的赢 ⇒ 12% → 88% → 3%，读起来像进度倒退。
3. **批次切换残留**：`files → assets` 时计数回到 `0 / N`，字节行仍是上一批最后一个文件的满格数字；`PHASE_WRITE` 阶段同样残留。
4. **无长度文件读数停住**：回调不触发，UI 一直挂着上一个文件的数字。
5. **已存在文件也闪**：`onCurrent` 在 `isDownloaded` 判断之前。

### 1.3 根因

进度模型是**单文件视角**，而执行模型是**16 并发**。两者不匹配，靠"谁最后写谁生效"掩盖 ⇒ 读数没有物理意义。

## 2. 目标与不变量

### 2.1 目标

1. 读数**单调推进**，与并发数无关。
2. 读数**永远不超过 100%**。
3. 更新频率**全局有界**（≤10 Hz），不再随并发数放大。
4. 批次切换不残留。
5. 不依赖服务端是否给 `Content-Length`。

### 2.2 不变量（实现与验收逐条对照）

| ID | 不变量 |
|---|---|
| I1 | 上报的 `done ≤ total`（聚合路径用 `min` 截断 + 单文件路径由转发 helper clamp + 显示层再 clamp 一次） |
| I2 | 无重试时 `done` 单调不减 |
| I3 | 每批恰好一次起点事件；中间 ≤10 Hz；恰好一次终态事件（单文件路径由下载原语在成功结算时补发终态） |
| I4 | 批次结算后不再上报 |
| I5 | 未知大小项对分子、分母**同增** |
| I6 | 批次未完成且 `total > 0` 时，`total ≥ done + 1`（进度条不到 100%） |
| I7 | 不改下载、校验、`.part` 清理、失败语义 |

## 3. 口径

一批 = 一次 `runDownloads` 调用。对该批去重后的项集合：

```
knownTotal = Σ size            （仅 size > 0 的项）
settled    = Σ size            （已完成 / 装前即存在的已知项）
unknown    = Σ received        （所有 size = 0 项的当前尝试已收字节）
inflight   = Σ min(received, size)   （在飞的已知项）

bytesTotal = knownTotal > 0 ? knownTotal + unknown : 0
bytesDone  = settled + inflight + unknown
```

**为什么不会超分母**：`settled + inflight ≤ knownTotal` 恒成立（每项贡献不超过自己的 size），而 `unknown` 在两侧同时出现 ⇒ `bytesDone − bytesTotal ≤ 0`。

**未知项完成时**：把它的 `received` 留在 `unknown` 里，不转入 `known` 口径 —— 转口径会让分母瞬间改变、读数跳变。代价是「已知项全部完成后，未知项仍在下载时百分比逼近但不到 100%」，由 I6 的 `+1` 兜底。

**全未知批次**：`knownTotal = 0` 时**上报 `0 / 0`**（而不是 `unknown / unknown`）—— 后者会让分子恒等于分母、进度条常驻 100%，没有信息量。UI 据 `bytesTotal <= 0` 整段隐藏，只保留 `N / M`。

**换候选重试**：该项的 `received` 归零（分子、分母同时回落）⇒ 读数会回退一次。这是"剩余工作量"最诚实的表达；不做高水位，否则分母被永久高估。

## 4. 数据流与落点

### 4.1 下载原语（`Downloader.ets`）

现状：只有 `dataReceiveProgress` 上报，且被 100 ms 局部节流。无 `Content-Length` 时它不触发。

改为：

- 把「节流 + 上报」抽成一个内部发射器（守卫 `finished` / `writeError` / `onProgress === undefined`）；
- `dataReceive` 记账后调用同一发射器（`received` 已累计）；
- `dataReceiveProgress` 仍保留，用于记录 `declaredLength`（完整性账目），不再单独承担上报；
- **提交成功后补发一次终态**（不受 100 ms 节流约束）：最后一片常被节流窗口丢掉，不补发则单文件读数会停在 `< total`；
  补发点在 `downloadFile` 的 **sha1 校验 + `rename` 成功之后**（空产物 / 校验失败 / 换候选一律不补发）；
- 节流值保持 100 ms（per-file）。聚合层的全局节流另算。

**不改**：状态机、结算路径、看门狗、写盘。

收益：无论有没有 `Content-Length`，每个在飞文件都以 ≤10 Hz 报「已收字节」。

### 4.2 批量聚合（`VersionInstaller.runDownloads`）

新增一个批次内的聚合器（局部状态，随调用结束销毁）：

| 字段 | 含义 |
|---|---|
| `knownTotal` | 已知大小项之和（去重后） |
| `settled` | 已完成已知项之和 |
| `unknown` | 未知项当前尝试已收字节之和 |
| `inFlight` | `index → received`（每个 worker 只写自己那格） |
| `lastEmitAt` | 全局节流戳 |

事件与动作：

| 事件 | 动作 |
|---|---|
| 批次开始 | 计算 `knownTotal`；发 `(0, knownTotal)` |
| 某文件收到字节 | 更新 `inFlight[index]`；距上次 ≥100 ms 才发 |
| 某文件完成（含装前已存在） | `inFlight.delete(index)`；`settled += size`；走**全局节流**（资产批完成事件可达数百次/秒，不能强制发） |
| 批次结束 | 发终态（含 `total ≥ done + 1` 守卫） |

回调签名：`onFileProgress(received, total)` → **`onBytes(done, total)`**。
`onCount` / `onCurrent` 保持不变（`current` 按用户决定保留；`onCurrent` 挪到 `isDownloaded` 之后）。

单文件路径（Forge / NeoForge 的 installer jar，走裸 `downloadFile`）：
由 `forwardSingleFileBytes` 转发 —— `total > 0` 时上报 `min(received, total) / total`（防超 100%），`total <= 0` 时上报 `0 / 0`（UI 整段隐藏）。`downloadFile` 在校验 + `rename` 成功后补发终态 ⇒ 结束必然满格。

### 4.3 安装状态（`InstallerState.ets`）

| 现状 | 改为 |
|---|---|
| `@Trace fileReceived` | `@Trace bytesDone` |
| `@Trace fileTotal` | `@Trace bytesTotal` |
| `current` | **保留**（用户决定） |

- 四个安装入口（`install` / `installFabric` / `installNeoForge` / `installForge`）的回调一并改名；
- 安装开始时清零；
- `PHASE_WRITE` / `PHASE_PROCESS` 时清零（这两个阶段没有下载字节，不留上一批的残留）。

### 4.4 UI（`GameVersionsView.ets`）

保持极简，三段：

```
[阶段文案]                       phaseText()
[N / M]                          download_progress
[38.2 MB / 430.1 MB]             download_file_progress（bytesTotal > 0 时）
[=======------------]            Progress（线性；bytesTotal > 0 时）
[当前文件]                       current（保留）
```

- `Progress({ value: bytesDone, total: bytesTotal, type: ProgressType.Linear })`，默认样式，不加自定义颜色/圆角；
- 值取 `Math.min(bytesDone, bytesTotal)`；
- `bytesTotal <= 0` 时整段（字节行 + 进度条）不渲染；
- 复用现有 `fmtSize`；
- 不新增文案资源（`download_file_progress` 已有）。若后续加"本批"前缀，再新增 1 条。

## 5. 边界与失败语义

| 场景 | 行为 |
|---|---|
| 幂等重装（全部命中） | 每个命中项立即 `settled += size`；批次终态直接报满，不出现 0 → 满的假动画 |
| 首个 worker 失败 | 停止领新任务；在飞项收尾（期间仍可能有节流上报）；批次终态发一次，随后 UI 由错误分支接管 |
| 本地 I/O 失败 | 同上；UI 在 `installingId` 清空后回到空闲 |
| 换镜像重试 | 该项读数归零一次，随后继续单调 |
| 声明 size 与实际不符 | `min(received, size)` 保证不超；完成时以 `size` 入账 |
| processor 阶段（`:neoinstall`） | 无字节事件，`bytesTotal = 0` ⇒ 只显示阶段与计数 |
| 归档/删除/清理 | 不涉及 |

## 7. 改动面 / 回滚 / 非目标

| 文件 | 改动 |
|---|---|
| `common/data/Downloader.ets` | 抽出进度发射器；`dataReceive` 也上报；**状态机不变** |
| `common/data/VersionInstaller.ets` | `runDownloads` 聚合器；回调改名；4 个安装入口；单文件包装 |
| `common/state/InstallerState.ets` | 2 个字段改名；4 处回调；两处清零 |
| `components/GameVersionsView.ets` | 加 `Progress`；字节行绑新字段 |
| `resources/base/element/string.json` | 不新增（除非给字节行加前缀） |

- **回滚**：四个文件整块 revert；无数据迁移、无对外契约变化。
- **风险**：纯展示与采样层，不进入下载结算；失败路径不受影响。
- **非目标**：用户可见取消按钮、跨批次/整次安装的总进度、单文件读数回归、下载并发度调整、下载器结算语义。

## 1. 两套 JRE 与选择规则

| 套 | id / HSP 模块 | 构成 | 服务对象 |
|---|---|---|---|
| **现代** | `meow_jre` / `meowjre` | 官方 OpenJDK 26.0.2.1（glibc）件原地改 `.dynstr` + 自编 `libc6.so` / `libjli` / `libjvm`（打 `OHOS_DL_DIR` / `OHOS_JAVA_HOME` 分体 patch） | 默认（无约束段） |
| **legacy** | `meow_jre_legacy` / `meowjrelegacy` | Eclipse Adoptium Temurin 8（aarch64/glibc）数据件 + 自编 `libjvm.so`（musl，源码 `ref/jdk8u`）与 `libc6.so` / `libjli.so` 等桥接件 | 需要 Java 8 的实例 |

- **两套都必须**：`libjli` 含 `OHOS_DL_DIR` / `OHOS_JAVA_HOME`（分体启动）；HSP 模块名与 id **版本中性**（版本由**数据令牌**承载，见 §2）。
- **选择规则 = 两张表的 join**（`common/data/JavaPolicy.ets`）：表 A「(MC 版本段 × loader) → 约束 `min/max/preferred` + 依据」× 表 B「可用 runtime（各带 `javaMajor`）」。
  - 香草最低：`≥1.13→8`、`≥1.17→16`、`≥1.18→17`、`≥1.20.5→21`、`≥26.1→25`。
  - **Forge**：`≤1.12.2→强制上限 8`（`java.util.jar.Pack200` 已在 JDK 14 删除、`SecurityManager` 已在 JDK 24 禁用）；`1.13–1.16.999→(0,17,8)`（preferred 8）；`1.17–1.20.4→(16,0,17)`（preferred 17）。
  - **无规则命中的组合一律「取最新」= 现代套 26**（默认不改变单 JRE 时代的行为）。
- **已知缺档（登记）**：随包只有 **26** 与 **8** ⇒ Forge **1.17–1.17.1** 落到 Java 26，偏离 HMCL 的 `MODLAUNCHER_8`（要求 ≤17）；决策 = **不加 `max 17` 边界**（8 太老、不满足 `min 16`）；将来若出问题则**补一档 JRE 17**（不是改用 8）。登记见 [`../../00-current/已知限制与待解.md`](../../00-current/已知限制与待解.md) §C14。
- **用户覆盖**：`AUTO / VERSION / DETECTED / CUSTOM`（`AUTO` 交给策略；用户可覆盖，与建议冲突只在理由里记录、不静默改）；**结果（选中的 JRE 主版本）进 UI 与启动日志（同源同一个 `resolveJavaRuntime`）**；逐段 / 逐选择的理由只进日志（`reasonDiag`，稳定英文诊断串）。
- **安装期工具 JVM 与启动 JVM 同源**：`:neoinstall` 的 processor 工具 JVM 用哪套 JRE，由主进程用**与启动路径同一处**的 `JavaPolicy.resolveJavaRuntime` 按 (MC 版本 × loader) 解析出 `id`，经 job（`NeoForgeProcessorJob.jreId`）传到 `NeoInstallAbility` 用**同一个 id** 起 `startJvm`；id 缺失（旧 job）/未知 ⇒ 回退现代套 + warn。

## 2. 多 JRE 布局与令牌门

- **物理上不能"合租"**：`libjli` / HotSpot 用 **`OHOS_DL_DIR` 这个扁平目录 + 裸名**（`$OHOS_DL_DIR/libjvm.so`）定位 JVM 组件，其余 JRE `.so` 靠 `LD_LIBRARY_PATH` **按文件名** dlopen ⇒ 同一个 el1 平铺目录里放两套同名 `.so` 必然互相污染（静默命中一份）。⇒ **两套 JRE 各占一个 el1 目录 / 命名空间**（各一个 `type:shared` + `libIsolation:true` 的 HSP）。
- **一套 JRE = 一个对象**：`common/data/JavaRuntime.ets` 把**必须彼此一致**的四项绑在一起 —— `id` / HSP 模块名 / **数据令牌** / **就绪标记**（现代套 `lib/modules`、legacy 套 `lib/rt.jar`），并自带 `home() / libsDir() / javaBin() / zipfsPatchDir() / readyPath() / tokenPath()`。启动链只认"解析好的那一个" ⇒ 结构上不可能出现"数据用 A、el1 用 B"。
- **桥的模块选择只在一处**：`JvmLauncher.currentBridge()`。每个 HSP **各有一份** `libmeowcraftbridge.so`（带窗口环 / surface / 输入共享状态）⇒ 起 JVM 后**所有**桥调用都必须打到那个模块，否则状态分家。`loadBridge()` 里那个小分支是**唯一**知道模块名的地方。
- **数据落盘与令牌**：`<filesDir>/meow-jres/<id>`（数据 tar）与 HSP 模块的 el1 `.so`。就绪 = 数据布局 + **令牌一致**；改数据必须升令牌（见 [`决策与不变量.md`](决策与不变量.md) §10.2、§18）。
- **清理**：`Install` 扫 `filesDir/meow-jres/` 删**非当前 id** 的兄弟目录（幂等、失败仅告警）。`lib/patch/jdk.zipfs/**` 属现代套专有（见 §6），路径随 `jreHome` 传 ⇒ 换 JRE 自动跟随。
- **加第三套 JRE = 纯数据**：① tools 配方产出；② 新建版本中性 HSP；③ `JavaRuntime` 表加一行 + `Paths.ets` 加字符串 + native `jre_launcher.h::kJreSpecs` 加一行；④ rawfile 放 `<id>.tar.gz`；⑤（需要时）`JavaPolicy` 表加一行；⑥ `loadBridge()` 加一个分支 —— **逻辑代码零改动**（UI 下拉选项也由 `BUNDLED_RUNTIMES` 生成）。
- **代价**：每套 JRE ≈ el1 二十余个 `.so` + 数据 tar（单份 ~50–70 MB）；部署 2 包 → **3 包**（`meowjre` + `meowjrelegacy` HSP + `entry` HAP）；多出来的 HSP **由系统管理、app 删不掉**（弃用只能 `hdc shell bm uninstall -n <bundle> -m <module>`）。

## 3. 平台伪装（另起 JVM 必带）

**契约**：本仓**任何"另起 JVM"的路径**（安装期工具 JVM、各子进程、将来的其它载体）的 argv 都必须带**与游戏同源**的平台伪装 —— 常量 = `common/constants/LaunchDefaults.ets` 的 `TOOL_JVM_PLATFORM_SPOOF_ARGS`（= `-Dos.name=${SPOOF_OS_NAME}` + `-Dos.version=${SPOOF_OS_VERSION}`，紧随 `java`、排在其余 `-D` 之前）。游戏路径同源（`MinecraftLauncher.buildLaunchArgv` 的"固定 JVM 参数"段也 push 同一对）。

- **为什么**：JDK 8 的 `sun.nio.fs.DefaultFileSystemProvider.create()` 按 `os.name` **精确匹配**（`Linux` / `SunOS` / `Darwin` / …），本机真 `os.name` 是 `HarmonyOS` ⇒ 匹配不上直接 `AssertionError: Platform not recognized`（**类初始化期**，连主类都加载不到，`JLI` 退 1）。现代套 26 对未知 `os.name` 宽容回退 ⇒ 同一条链在 26 上此前从未暴露 ⇒ **不可依赖"在 26 上没炸"**。
- **落点**：`runForgeProcessors` / `runNeoForgeProcessors`（两条链的工具 job argv）。完整不变量与取证见 [`决策与不变量.md`](决策与不变量.md) §25。

## 4. 安装期工具 JVM 载体（无窗 `:neoinstall` UIAbility）

**问题**：JVM 硬绑**进程**（HotSpot 一进程一 VM，二次 `JLI_Launch` 必败），而桥在 `JLI_Launch` 返回后**无条件 `_exit`** ⇒ 安装 JVM **必须放独立进程**（否则 `_exit` 带走整个 App）。

- **载体 = 独立进程 UIAbility + `STARTUP_HIDE`（2in1/Tablet 专属）**：静态 `process: ":neoinstall"` 的 UIAbility（**不 `loadContent`**）+ 父进程 `startAbility` 传 `StartOptions{processMode: NEW_PROCESS_ATTACH_TO_PARENT, startupVisibility: STARTUP_HIDE}`（SDK 要求二者成对，@since 12，仅 2in1/Tablet）⇒ **窗口不显示、dock 无图标、`onForeground` 不回调**、进程隔离成立（JVM 的 `_exit` 只结束 `:neoinstall`），且**完整复用 HSP 内 `dlopen` JRE** 的链路（零 lib 解析风险）。
- **语义等价于 HMCL 的"派生 `java` 子进程"**：独立进程、退出码权威、无状态泄漏；代价是 N 次 JVM 冷启动（client 侧 N = 1（26.x）… 6（1.21.x））。**为什么不能 exec**：JRE 数据在 el2（禁执行）、el1 无可执行的 `java`。
- **桥的 headless 模式（沉淀，通用能力）**：`launchJvm` 的 `rendererLib` 传空 ⇒ 跳过渲染器预 `dlopen` / 渲染相关 env / glthread 失效安全；**退出码文件通道** = headless 时把 `JLI_BEGIN` / `JLI_RETURNED code=N` 追加到 `<filesDir>/meow-neo-jvm-result.txt`（补上"native 只有 hilog、主进程拿不到退出码"的洞）。
- **载体机理共享、安装办法分开**：与 loader 无关的载体机理（起无窗 `:neoinstall` 进程、job 文件协议、结果文件**字节偏移式新鲜度基线**、退出码权威、软/硬超时、`16000068` 退避重试、进程探针）抽成一段共享段 `VersionInstaller.ets` 的 `runToolJvmOnce`（两条链共用）；**各存一份**的是 profile 解析 / processor 计划构造 / `outputs` 幂等 / 内嵌 `maven/**` 解包 / 清单组装 / ASM 排除。见 [`安装链-总览.md`](安装链-总览.md) 与 [`决策与不变量.md`](决策与不变量.md) §0.2。
- **保活 / 冻结**：短时任务（`OH_BackgroundTaskManager_RequestSuspendDelay`，单次 ≤3min、连续 ≤3 次）不够一次完整安装；长时任务（`continuous-task`）能到"取消才不挂起"，但**会弹通知栏通知**（代价 = 一条通知）；后台单核占用超阈值会被结束。
- **phone 侧无解（登记）**：手机 `module.json5` 的静态 `process:` **被忽略** ⇒ 所有 ability 同进程；`startupVisibility=STARTUP_HIDE` 与 `childProcessManager` **仅 2in1/Tablet**；`ExtensionAbility` 作宿主"三方 × 按需 × 长时 × 独立进程"四者不可兼得；`Worker`/`TaskPool` 是同进程线程；HotSpot 一进程一 VM ⇒ **phone 端 1.13+ 的 processor 安装失败**（用户裁决：先聚焦 2in1，不做设备门）。**重开条件**：① 实现"进程内单 VM + 装完重启启动器"；或 ② 按版本走"不跑 JVM"的安装路径（**MC 26.x 形态的 client 侧只有 1 个 processor 且不做字节码重命名 ⇒ 可纯 native 重实现**；1.20.1 / 1.20.2–1.21.x 仍各卡 FART / ART 1 个 remapper）。见 [`../../00-current/已知限制与待解.md`](../../00-current/已知限制与待解.md) §E 与 [`NeoForge无JVM安装-可行性与取证.md`](NeoForge无JVM安装-可行性与取证.md)。

## 5. 随包 ASM 覆盖（Forge 1.19.x）

- **判据**（`MinecraftLauncher.needsAsmOverride`）：**modlauncher ≥ 10 且其声明的 ASM 能力 < 当前 JRE class major**。典型 = Forge 1.19.x（ML 10.0.8 + ASM 9.7.1）在 JDK 26 上读不懂类文件 ⇒ `Unsupported class file major version 70`。
- **件与落点**：随包 `asm9/{asm,asm-analysis,asm-commons,asm-tree,asm-util}-9.9.1.jar`（**`asm9/` 子目录**，落 `<cache>/mc-cp/<key>-<id>/asm9/`，见 §7），`rewriteAsmList` **同时改写 `-cp` 与 `-p`** 且不残留旧套。
- **分界**：1.17.1(ML 9.0.7) / 1.18.2(ML 9.1.3) / 1.20.1(ML 10.0.9 但 ASM 9.9.1) 不触发；1.19.4 触发。
- **NeoForge 刻意不替换**：`needsAsmOverride` 对 `looksLikeNeoForge` 一律返回 false（其 `-DignoreList` 按**带版本文件名**点名 ASM ⇒ 改名会静默脱靶）。

## 6. JRE 级 Java 类补丁（`jdk.zipfs` best-effort chmod）

- **要解决的问题**：手机（`HUAWEI Mate XT`）游戏目录在用户存储（FUSE/hmdfs）**拒 chmod** ⇒ Fabric 首次启动的 `tiny-remapper` 经 `jdk.zipfs` 写 `<gameDir>/.fabric/remappedJars/*.jar` 时 `ZipFileSystem.sync()` 无条件 `Files.setPosixFilePermissions` 抛 `Operation not permitted` ⇒ Fabric 崩。
- **修法**：把该 chmod 改成 **best-effort**（失败即忽略，**被写 jar 字节不变**），用 JDK 官方 **`--patch-module`** 投放（`MinecraftLauncher.LaunchOptions.zipfsPatchDir` → `--patch-module jdk.zipfs=<jreHome>/lib/patch/jdk.zipfs`；`GameLauncher` **先做存在性检查**）—— 只覆盖 `jdk.zipfs` 一个模块的类，**不动** `lib/modules`(jimage) / `jmods` / 任何模块哈希，**不 patch `java.base`**。
- **补丁点与构建**：`ref/jdk26u/src/jdk.zipfs/share/classes/jdk/nio/zipfs/ZipFileSystem.java`；补丁本体 / 构建 = 主仓 `tools/jre26/{patches/zipfs_chmod_best_effort.py,linux_build_zipfs_patch.sh}`，`rebuild_for_meowcraft.sh --zipfs-patch <dir>` 放进 `home/lib/patch/jdk.zipfs/`（36 个类，不含 `module-info.class`）。
- **影响面**：2in1（可 chmod）catch 不触发 ⇒ 行为不变；其它 zipfs 使用者仅在 chmod 失败时才改变（只是"少设权限"）。数据 tar 变 ⇒ **数据令牌升**（见 [`决策与不变量.md`](决策与不变量.md) §10.2）。**撤法** = 删 `home/lib/patch/jdk.zipfs`（重打 tar）+ 去掉那条 `--patch-module` argv（+ 令牌回退）。
- 实机结论见 [`../../00-current/现状基线.md`](../../00-current/现状基线.md) §5 第 27 条。

## 7. 缓存与运行目录（沙箱缓存 vs 游戏根）

**契约**：磁盘分**两块**——
- **沙箱缓存** `<cacheDir>`（= `UIAbilityContext.cacheDir`，设备应用缓存）：本工程写出来的**可随时整块重建**的运行期数据；
- **游戏根** `<gameRoot>`（用户的 `.minecraft` 式目录）：版本清单 / 客户端 jar / 共享库 / 资源 / 设置 / 存档——**属游戏与用户，清缓存永不动它**。

两侧按实例配对的目录名一律为 **`<key>-<id>`**（`<key>` = `gameRoot` 短哈希；`<id>` = 实例名），沙箱的 `mc-cp/` 与 `mc-run/` 用**同一**分区规则。

### 7.1 命名规则：`<key>-<id>`

- **`<id>`** = 实例名（版本目录名，即 `<gameRoot>/versions/<id>` 的末段）。
- **`<key>`** = `gameRootKey(gameRoot)` = **SHA-256**(UTF-8(`normalizeGameRoot(gameRoot)`)) 十六进制串**前 8 位**（`GAME_ROOT_KEY_LENGTH`）。
- **规范化**（`normalizeGameRoot`，唯一口径，刻意保守）：① 折叠连续斜杠（`a//b` → `a/b`）；② 去尾部斜杠（保留根 `/` 本身）。**不动大小写**（鸿蒙文件系统一般区分大小写）、**不解析** `.` / `..`、不做 unicode 归一；取字节用 UTF-8 ⇒ 含中文的游戏目录按**字节**哈希。
- **稳定性**：输入只有"规范化路径 + 纯函数哈希"，无时间 / 随机量 ⇒ 同一游戏根的任何一次运行都得**同一个** key（跨进程、跨启动一致）。
- **为什么要有 key**：早期按**裸实例名**命名（`mc-cp/<id>`、`mc-run/<id>`）⇒ **同名而不同游戏根**的两个实例共享同一份 staging / run 目录，互相踩：staging 被对方重铺、`natives/` 混用、`hs_err` 串台。加 `gameRoot` 短哈希前缀即可隔离。
  - **实测**（`Harmomeow-Craft-Launcher/.logs/`）：实例名同为 `26.3`、游戏根 `stuffs/test-fabric` ⇒ key `4857b775`；游戏根 `stuffs/test-neoforge` ⇒ key `3b0db310`。两次运行的 `mc-cp/<key>-26.3`、`mc-run/<key>-26.3` 子目录名**不同**，连 `natives/` 下的世代目录也不同（`3.4.3-snapshot` vs `3.4.3+4`）。

### 7.2 沙箱缓存布局（`<cacheDir>/`，可随时重建）

```
<cacheDir>/                            ← 应用缓存根（cacheDir）
├── mc-cp/                             ← classpath 平铺暂存根（本工程写）
│   └── <key>-<id>/                    ← 每实例一份
│       ├── <平铺 jar…>                ← flat：整份声明库；slim：只随包件 + oshi 补丁件
│       └── asm9/                      ← 随包 ASM 覆盖件（子目录，不参与一层通配）
├── mc-run/                            ← 运行目录根（本工程写；与 mc-cp 对等）
│   └── <key>-<id>/
│       ├── natives/                   ← JNA / LWJGL 解压工作目录（java.io.tmpdir 之下）
│       └── logs-fallback/             ← -XX:ErrorFile 的兜底目录
├── forge-installer/                   ← Forge 安装器解包工作目录（本工程写）
│   └── <源>/<版本>/                   ← 如 official/<ver>/（installer.jar / unzipped / job-*/logs）
├── neo-installer/                     ← NeoForge 安装器解包工作目录（本工程写）
│   └── <源>/<版本>/
└── mc-run-<…> / mc-run-<…>-logs       ← 旧形态孤儿：早期无 key / 前缀式布局残留在顶层的目录
```

### 7.3 游戏根布局（`<gameRoot>/`，清缓存不动）

```
<gameRoot>/                            ← 用户游戏目录（如 stuffs/test-fabric、stuffs/test-neoforge）
├── versions/
│   └── <id>/
│       ├── <id>.json                  ← 版本清单（游戏 / 安装器写）
│       ├── <id>.jar                   ← 客户端 jar（游戏 / 安装器写）
│       └── .hmmcraft/                 ← 实例私有数据（本工程 + JVM 写）
│           ├── instance-settings.json ← 实例设置（本工程写）
│           └── logs/                  ← -XX:ErrorFile 首选落点（JVM 崩溃时写）
├── libraries/
│   └── <group 路径>/<artifact>/<version>/<file>   ← maven 布局共享库（游戏 / 安装器写）
└── assets/
    ├── indexes/
    └── objects/                       ← 内容寻址资源（游戏写）
```

### 7.4 逐目录职责

| 目录 | 是什么 | 谁写 | 生命周期 |
|---|---|---|---|
| `<cacheDir>/mc-cp/<key>-<id>/` | 该实例 `-cp` 指向的 jar 平铺暂存 | 本工程（`ClasspathStager`） | **可随时重建**（清缓存即整树删） |
| `<cacheDir>/mc-cp/<key>-<id>/asm9/` | 随包 ASM 9.9.1 覆盖件（子目录） | 本工程（ASM 覆盖，§5） | **可随时重建** |
| `<cacheDir>/mc-run/<key>-<id>/` | 该实例运行目录（`java.io.tmpdir`） | 本工程 / JVM | **可随时重建** |
| `<cacheDir>/mc-run/<key>-<id>/natives/` | JNA / LWJGL 解压工作目录 | JNA / LWJGL（运行期） | **可随时重建** |
| `<cacheDir>/mc-run/<key>-<id>/logs-fallback/` | `-XX:ErrorFile` 的兜底落点 | JVM（崩溃时） | **兜底诊断**（首选在实例内） |
| `<cacheDir>/forge-installer/<源>/<版本>/` | Forge 安装器解包工作目录 | 本工程（安装期） | **可随时重建** |
| `<cacheDir>/neo-installer/<源>/<版本>/` | NeoForge 安装器解包工作目录 | 本工程（安装期） | **可随时重建** |
| `<gameRoot>/versions/<id>/{<id>.json,<id>.jar}` | 版本清单 / 客户端 jar | 游戏 / 安装器（上游） | 游戏根资产（**不清**） |
| `<gameRoot>/versions/<id>/.hmmcraft/instance-settings.json` | 实例设置 | 本工程 | 游戏根资产（**不清**） |
| `<gameRoot>/versions/<id>/.hmmcraft/logs/` | `-XX:ErrorFile` **首选**落点 | JVM（崩溃时） | **兜底诊断**（**不清**） |
| `<gameRoot>/libraries/<…>` | maven 布局共享库 | 游戏 / 安装器（上游） | 游戏根资产（**不清**） |
| `<gameRoot>/assets/{indexes,objects}` | 内容寻址资源 | 游戏（上游） | 游戏根资产（**不清**） |

**分类口径**：**本工程写** = 我们产出的沙箱暂存 / 设置；**游戏 / 安装器写** = 游戏根里由游戏本体或 loader 安装器落盘的资产；**可随时重建** = 删掉后启动时按需重铺（沙箱缓存）；**兜底诊断** = 只在崩溃时落 `hs_err_pid%p.log`——首选实例内 `.hmmcraft/logs`，建不出时退 `mc-run/<key>-<id>/logs-fallback`。

### 7.5 沙箱里「是谁的件」（随包覆盖件 / 上游拷贝 / staging 记号）

`mc-cp/<key>-<id>/` 里的东西分三类：**① 我们自己的覆盖件**（自编或随包的官方原件，用来**顶替**声明里的同名件）、**② 上游声明库的拷贝**（`flat` 时整份铺进来，内容未改）、**③ 我们自己的 staging 记号**。

| 文件/目录 | 是谁的 | 顶替谁 / 用途 | 生效机制 |
|---|---|---|---|
| `lwjgl-3.4.3.jar` | **我们自编的单代合并 jar**（`tools/lwjgl/build_lwjgl_jar.sh`：官方 12 模块 + `deltas/overlay`(13 件) + `deltas/overlay-3.4.3`(7 件)）。含 `MeowBundledNameMapper`、GLFW 符号由自研桥 `libmeowcraftbridge.so` 提供（**无 `liblwjgl_glfw.so`**）、`GLCapabilities` 由 `gen_glcap.py` 按版本生成（3.4.3 = **2270** 槽）、5 个 3.4.x 兼容 shim、26.x 的 `sdl/vma/spvc/shaderc` | 顶替清单声明的 `org.lwjgl:*` | `collectFromJson` **跳过** `org/lwjgl/*`；我们的 jar 落在平铺目录 ⇒ `flat` 由 `-cp "<dir>/*"` 取件、真树 / `ordered` 由 `assembleRealTreeClasspath` 按**绝对路径**补进 `-cp` |
| `oshi-core-<v>.jar`（= 随包 `oshi-core-<v>-meow.jar` 覆盖后的名字；**10 件**：5.7.4 / 5.7.5 / 5.8.2 / 5.8.5 / 6.2.2 / 6.4.5 / 6.4.10 / 6.6.5 / 6.9.0 + legacy 1.1） | **我们重编的补丁版**（`rawfile/oshi-overrides/` 下的 `manifest.txt`，逐行 `<v>.jar=<v>-meow.jar`；认 `-Dmeow.cpu.chip`） | 顶替声明里的同名 `oshi-core` | **平铺 = 同名覆盖**（`ClasspathStager.applyOshiOverrides` 就地覆写 staged 同名件）；**真树 / ordered = 替换并前置**（`assembleRealTreeClasspath` 先移出上游同名、再把补丁件放首条） |
| `asm9/`（5 件 `9.9.1`） | **随包的官方原件（未改动）** | 覆盖实例声明的旧 ASM（**仅 1.19.x 命中**） | `MinecraftLauncher.needsAsmOverride` 改写 `-cp` **与** `-p` 条目（`rewriteAsmList`），不残留旧套 |
| `meowcraft_extras.done` | **我们自己的 staging 记号** | —— | 内容 = `${EXTRAS_VERSION}|<随包 tar 字节数>`；命中且期望件都在才跳过重抽（幂等重铺的依据） |
| 其余 `<声明库>.jar` | **上游声明库的拷贝**（内容未改） | 供 `flat` 的 `-cp "<dir>/*"` 一步取件 | 仅 `flat` 铺；`slim` 不铺（其 `-cp` 是显式绝对路径列表） |

**`flat` vs `slim`（同一分区名、两种物化意图）**：

- **`slim`**（`-cp` 是显式绝对路径列表：launchwrapper `ordered` / Forge ≥1.13 与 NeoForge `real-tree`）⇒ 平铺目录里**只剩上面①②③里"我们自己的覆盖件"**（`lwjgl-3.4.3.jar` + `asm9/` + 声明的 oshi 补丁件 + `done` 记号）；上游声明库不进任何 classpath，故不铺。
- **`flat`**（vanilla / Fabric 的 `-cp "<dir>/*"`）⇒ **整份声明库 + 我们的覆盖件**（一层平铺）。
- **实测规模**（`stuffs/research/file-structure/cache/mc-cp/`，清缓存前快照）：`slim` 实例 `1.7.10` = **2 顶层项 / 427K**（仅 `asm9/` + `done`）；`slim` 实例 `26.3`（NeoForge）= **4 项 / 14M**（`asm9/` + `lwjgl-3.4.3.jar` + `oshi-core-6.9.0.jar` + `done`）；`flat` 实例 = **57 项 / ~113M**。
- **oshi 版本 ↔ MC 版本**（哪些实例用哪个 `-meow` 件）见 [`../../40-adaptation/oshi-cpu-info.md`](../../40-adaptation/oshi-cpu-info.md) §5。

### 7.6 「清除缓存」覆盖范围

`clearSandboxCaches(cacheDir)`（`CacheCleaner`）只动 `cacheDir` 下**本工程写出来的**条目：

- **清**：`mc-cp/`、`mc-run/` 两棵**整树**（含各 `mc-cp/<key>-<id>`、`mc-run/<key>-<id>/{natives,logs-fallback}`）+ 顶层以 `mc-run-` 开头的**旧形态孤儿**（`mc-run-<id>` / `-logs`、前缀式 `mc-run-<key>-<id>` / `-logs`）+ `forge-installer/`、`neo-installer/`。
- **不清**：游戏根（`libraries` / `assets` / `versions` / 存档 / 日志）、`<filesDir>/meow-jres/`（JRE 数据）、`<filesDir>/meow-home/`（启动器 home = 账户 / 运行数据）、`<filesDir>/meow-settings/`（设置）。
- 逐个点名删除（绝不清空整个 `cacheDir`，故系统自己的条目如 `image_file_cache/` 不受影响）；全部 best-effort——被占用的跳过并如实上报，不抛异常。

### 7.7 如何自己观测

- 看沙箱缓存分区：`ls -1 <cache>/mc-cp`、`ls -1 <cache>/mc-run`。
- 看某次运行落到哪个 `<key>-<id>`：`grep -E 'stage .* mode=|classpath mode=|runDir=' <设备日志>`（对应日志串 `extras <key>-<id>: …` / `stage <key>-<id>: mode=… sources=…` / `version <id> isolation=on runDir=<cache>/mc-run/<key>-<id>`）。
- 看 `-XX:ErrorFile` 指向（首选 vs 兜底）：`grep -oE -- '-XX:ErrorFile=[^ ]+' <设备日志>`。
- 看日志兜底是否生效：启动日志**不应**出现 `logs dir unusable:` / `fallback logs dir unavailable:`（出现 = 实例内与沙箱两级都不可用 ⇒ 无 `-XX:ErrorFile`）；判据本身的规则见 [`决策与不变量.md`](决策与不变量.md) §26。
- 看游戏根（本工作区可直读）：`ls -1 stuffs/test-fabric/versions/26.3/`、`find stuffs/test-fabric/libraries -maxdepth 4 -type d | head`。

**边界**：`<cacheDir>`（设备应用缓存 `/data/storage/el2/base/haps/entry/cache`）**本机不可读** ⇒ 沙箱那棵树由**设备缓存快照**（`stuffs/research/file-structure/cache/`，清缓存前复制）与代码常量 / 日志路径合成；**游戏根那棵**（`stuffs/test-fabric/…`）是**本工作区可直接 `ls`** 的。

## §1 一页速查：拿到一个崩溃，按这个顺序做

| # | 动作 | 去哪 |
|---|---|---|
| 1 | **先确认这是"这一次运行"的物证**（看 mtime/时间戳，别把旧会话日志当本次） | §2 · §3.1 |
| 2 | 抓栈：`MEOW_BT=1`；要留一份可离线核对的转储就 `MEOW_BT_FILE=<实例>/.hmmcraft/logs/meowbt-dump.txt`。**只认转储最后一条 fault**（前面的多半良性） | §3.2 |
| 3 | 有 `hs_err_pid*.log` 就直接读——JVM 自报常常就是结论（例：`Cannot resize table: Node hash code has changed … corruption`） | §3.1 |
| 4 | 现象在渲染/GL 侧 ⇒ 抓 Zink **生成的** SPIR-V（`ZINK_DEBUG=spirv`）再解析 | §3.3 |
| 5 | **先找"零构建的决定性 A/B"**（env / 配置），确认机制后再考虑编译或换装 | §4.1 |
| 6 | 规避要随包 ⇒ **编译期默认开 + 运行时旋钮 + 零落盘** | §5 |
| 7 | 交付前：分域 multi-agent review + **逐字节核验入包内容** + 同步 digest | §6 |

## §2 平台与工具链事实（全是踩出来的）

| 坑 | 现象 | 解决 |
|---|---|---|
| 用错 `hdc` | `/data/service/hnp/bin/hdc` 直接 `Signal 15` / `Connect server failed` | **2026-09-28 起裸 `hdc` 可用**（`which hdc` → `/data/app/bin/hdc`）；`list targets` 空则 `hdc tconn 127.0.0.1:$(param get persist.hdc.port)`（端口 = 系统参数、会变勿写死）。旧的"只用 SDK 内那个"口径已作废，见 [`../00-current/工程与规范.md`](../00-current/工程与规范.md) §二.3 |

| 部署顺序/写法错 | 只给 `--module meowjre` ⇒ `Signal 15`；升版本时先装 HSP ⇒ `9568284 install version not compatible` | **2026-09-28 起 `devecocli` 看不到设备** ⇒ 不用 `devecocli run`，改 `hdc app install -r`：**同版本重装【先 HSP 后 HAP】/ `versionCode` 递增【先 HAP 后 HSP】**（见 [`../00-current/工程与规范.md`](../00-current/工程与规范.md) §二 3.1） |

| 用了错的 SDK | 同一份 `input_bridge.c`：`devecocli` 编过、IDE 编不过（`must use 'struct' tag to refer to type 'OH_PixelmapNative'`） | **IDE 与 `devecocli` 是两套 SDK**（DevEco 内置 `hmos-clt` vs `~/devecow/deveco_tools/sdk`）⇒ 头文件不同、改 native 后**两个入口都要编**；两套 SDK 的关系见 [`../00-current/工程与规范.md`](../00-current/工程与规范.md) §二.3 |
| `devecocli build` 报 `Not in a valid project directory` | 即使 session 目录已切仍报 | **显式给 `workdir`**（或先 `cd`） |

| 设备上跑自编 ELF | 可写路径 `EPERM` | 探针不能用"编译后本机跑"；改用容器/间接验证 |

## §3 取证与判读

### 3.1 物证种类与优先级
1. **`hs_err_pid*.log`**（JVM 自己写；现在的落点是 `<实例>/.hmmcraft/logs/`）— 信息最全，常有"自报结论"。
2. **`meowbt` 转储**（`MEOW_BT=1`）— 寄存器 + `/proc/self/maps` 快照 + 帧指针链 + 逐条 fault（带 epoch 时间戳）。
3. **平台捕获 `.logs/`（hilog）** — 是**环形快照**、会被海量输出挤掉；我们的启动器把 JVM 原生 stderr 以 **`[jre_stderr]`** 转发进来（**MC 的 `latest.log` 抓不到原生 stderr**）。
4. **实例 `logs/latest.log` / `crash-reports/`** — MC 自己的日志与崩溃报告。
5. ⚠️ **噪声，别当物证**：`hs_c*.log` / `hotspot_pid*.log` / `hotspot-meow.log`（`-XX:+LogCompilation` 的产物）、`replay_pid*.log`（`-XX:+ReplayCompiles`）。

### 3.2 ★一次运行里的三类**良性** fault（务必先排除，否则会被带偏）
| 现象 | 真面目 | 判据 |
|---|---|---|
| 同址、多线程、**pc 各不相同**（可几十条） | HotSpot **safepoint 轮询页** | 转储会标 `same-addr-diff-pc => safepoint-poll-like`；该页常是**固定地址**（本轮是 `0x5b8a2b8000`） |
| 低地址 `0x8/0xc/0x14` | **正常 Java NPE**（JVM 接住） | 地址 < 64 KB ⇒ 默认被过滤 |
| 退出瞬间 `VM Thread` SIGABRT | 收尾噪声 | 与"正常退出"时刻**秒级吻合** |

⇒ **只认最后一次运行的最后一条 fault**；`MEOW_BT_LOW=1`（关近空过滤）会灌入大量 NPE，是**死路**。

### 3.3 渲染链取证（GL/SPIR-V/驱动）
- Zink **生成**的 SPIR-V 落点 = 该 fork **硬编码**的 `/data/storage/el2/base/files/dump%02d.spv`（app 沙箱，**无 env 覆盖**）；开关是 `ZINK_DEBUG=spirv`。
  ❌ `MESA_SPIRV_DUMP_PATH` 是 vtn 侧"**吃进去的** SPIR-V"，对我们无效（本轮踩过）。
- 拿到后**别靠肉眼**：一个小解析器就能一眼看出阶段/能力/装饰/opcode 直方图（本轮靠它发现"崩前最后 4 个 dump 全是 `GLCompute`"）。
- 判定"谁在跑"：`logs/latest.log` 里的 GL 横幅（本轮：`zink Vulkan 1.2(Maleoon 916) Mesa 25.0.1`）⇒ 系统 GL 本身就是 Zink-over-Vulkan，**绕不开**。

### 3.4 符号化
- 本机 `nm` 可用；**未剥离**的 `libjvm`/bridge 可直接 `nm -C -S` 取函数与大小。
- **被 strip 的**（如 `.hsp` 内的库）只能看偏移 ⇒ 这也是 hs_err 里显示 `libjvm.so+0x…` 的原因。
- 判"某修复有没有真编进去"：比较**符号大小**（本轮 `meow_slack` 260 B→388 B 即证据）。

## §4 排查方法（可迁移）

### 4.1 便宜的决定性实验优先
推重活（容器编译 ~45 min / 换装）之前先问：**有没有零构建/零部署的办法**验证这个假设？
本轮真正定案的证据（驱动里的 NULL pc、`Cannot resize table`）**全是零构建拿到的**；而基于猜测跑的 4 次容器构建大多是浪费。
> 规则：先说清"假设是什么 / 这一步能证伪什么 / 有没有更便宜的替代"，再开重活。

### 4.2 单变量 + 自证信号
- 一次只改一件事；改两件就白跑（本轮曾"撤 slack + 开 sodium staging"同时改，结论直接作废）。
- 每个开关都要有**外部可验证的自证信号**（一行 banner / 标记文件 / 符号/字符串 / 现象），否则"改了但没生效"会被误读成"改了没用"。
- 验证"部署是否生效"是**独立课题**：本轮为此专门让产物可自证（但那行自证最初被写进了游戏目录 ⇒ 见 §5）。

### 4.3 拆分与交叉印证
- 一个崩溃可能是**多条独立链**（本轮 A 厂商着色器编译器 / B JVM 堆被越界写坏）⇒ 用"不同线程/不同地址族/不同 lib"把链拆开，各自做 A/B。
- 让**被怀疑对象自己说话**：JVM 的自报（`Cannot resize table`）比我们的推断可信；寄存器/地址模式（`0x5d00000000` = 压缩指针解码后的空 oop）能直接指认机制。

### 4.4 别被"优化过的规避"骗
规避验证通过后，**任何收窄/优化都要重做验证**：本轮把"对所有分配加 4 KB 富余"收窄成"只给 ≥1 KB"，结果**加载 16 秒就崩**（越界目标不限于大块）。
> 规则：规避的**生效边界**要写成判据，不要凭直觉收窄。

## §5 规避工程：把 hack 做成可交付件

| 原则 | 理由 / 实例 |
|---|---|
| **诊断件**：env 门控 + 默认零行为变化 | 抓栈器、日志开关等只在需要时开 |
| **规避件**：**编译期默认开** | 用户不该为了不崩去设 env；开关默认值就是产品决策 |
| **旋钮做成运行时 env** | 否则每次调参都要重编 JVM（45 min）；本轮 `MEOW_MALLOC_SLACK` / `_MIN` 都可运行时调 |
| **★零落盘**（铁律） | 物证统一落 `<实例>/.hmmcraft/logs/`；默认**不写任何文件**，要落盘须显式给路径（`MEOW_BT_FILE` / `-XX:ErrorFile`） |
| **指向不存在的目录 = 更糟** | HotSpot 的 `ErrorFile` 打不开会**静默回退到 cwd**（`vmError.cpp` 的 `default_pattern`）⇒ 又污染游戏目录；故建目录失败要**退沙箱**并告警 |
| ❌ **绝不把诊断型 VM 参数放进随包默认** | `-XX:LogFile` 是 diagnostic，未 `-XX:+UnlockDiagnosticVMOptions` 会**让 JVM 拒启**；此失败**没有 hs_err**、MC 日志也不更新，只能靠 `[jre_stderr]` 转发才看得到 |
| 保留**一键关闭/复验**通道 | `MEOW_MALLOC_SLACK=0` 让上游修好后能复验再撤 |
| 诚实记录**代价与残留风险** | 例：每条分配 +4 KB（未量 RSS）、越界超过富余仍会崩、这是"容忍上游 bug"而非修复 |
| **同时上报上游** | 规避不是终点；本轮已备好给 Flywheel 与驱动方的 issue 草稿 |

## §6 交付与协作

- **分域 multi-agent review**（本轮 3 个：JVM C 补丁 / ArkTS / native 抓栈器）⇒ 撕出 **1 BLOCKER + 4 MAJOR**，全是"我们新写的代码"的问题。
  ⇒ 规则：**别默认自己新写的代码是对的**；review 意见要落到具体行与失败模式，才可执行。
- **加固/重构时用真实样例验证**：本轮按 review 建议"加固"一行正则，反而把好构建拒了（`spec.gmk` 用 `:=`）。
- **入包内容要逐字节核验**：SPIR-V/HSP 这类"先打进去再运行"的产物，要解包比对（本轮发现 HSP 会 strip，进而修正了文档口径）。
- **digest/SBOM 变更必须同步**（含"为什么不同"的说明），否则后人核对会误判被篡改。
- **文档三层**：结论层（`00-current/`，唯一事实源）· 设计层（`20-design/`）· 历史归档（`90-archive/`）；改完跑三道检查：
  `notes-tools/check_links.py`、`notes_stalepaths.py`、`notes_statusdup.py`。
- **教训要写在会被读到的地方**：脚本注释（改代码的人会看）、本文（下一个人会查）、记忆（agent 会读）。

## §7 本战役坑清单（具体实例，按主题）

> 完整叙事见 [`../20-design/render/1.21.1-崩溃-两条链与随包规避.md`](../20-design/render/1.21.1-崩溃-两条链与随包规避.md)。

| 主题 | 坑 | 根因 | 解决 |
|---|---|---|---|
| 判读 | 把 safepoint 轮询页当"越界写到堆尾" | 该页地址**固定**且恰好紧贴堆末尾 | 认 `same-addr-diff-pc` 标注 + 只信最后一条 |
| 判读 | 把低地址 fault 当致命 | 那些是 JVM 接住的 NPE | 默认过滤；别开 `MEOW_BT_LOW` |
| 判读 | 用 hilog 环形快照推时间线 | 会被海量输出截断 | 以实例日志 + 转储时间戳为准 |
| 抓栈 | 只看 `FAULT#1` | 一次运行前几条多为良性 | 看**最后一条**；帧指针链在 Mesa 里不可靠，只信 pc/lr |
| 取证 | 用 `MESA_SPIRV_DUMP_PATH` 抓 Zink 输出 | 那是 vtn 侧输入口 | 用 `ZINK_DEBUG=spirv`；落点硬编码在沙箱 |
| 定位 | 靠肉眼读 SPIR-V | 二进制 | 写解析器（阶段/能力/直方图一眼看出） |
| 混淆 | 同时改两件事（撤 slack + 开 staging） | — | 单变量；结论作废重做 |
| 方法 | 为未证实假设跑 4 次容器构建 | 没先找零构建判据 | 先做便宜的决定性实验（§4.1） |
| 规避 | 收窄"已验证的富余"到 ≥1 KB | 越界目标不限于大块 | 全尺寸；写清判据 |
| 规避 | 让自证行写进游戏目录 | 自证便利 > 铁律 | 自证只走 stderr/hilog；落盘必须 opt-in |
| 规避 | 把 `-XX:LogFile` 加进随包默认 | 诊断参数需 unlock | 只留 `-XX:ErrorFile`；这类失败无 hs_err，靠 `[jre_stderr]` 定位 |
| 规避 | 让**不存在的目录**当 `ErrorFile` | HotSpot 静默回退 cwd | 失败退沙箱 + 告警 |
| 交付 | 代码 review 只看别人代码 | 新代码才是风险源 | 分域 review 自己的新件（抓到 BLOCKER：整数回绕致静默欠分配） |
| 交付 | "加固"正则没拿真实样例验 | `spec.gmk` 是 `:=` | 用真实/合成样例先验 |
| 交付 | 以为 `.hsp` 内容 = 仓库件 | 打包会 strip | 解包逐字节核验 + SBOM 写明 |
| 流程 | 单给 `--module meowjre` | 非可运行模块 | `--module entry meowjre`；部署前 force-stop |
| 流程 | agent 硬啃应用沙箱 | uid 2000 权限 | 取件交用户 |
| 上游 | 只做本机规避就收工 | 上游不修则长期背债 | 备好 issue：**驱动 bisheng 的 NULL/无效地址**（证据充分）；⚠️ **Flywheel 那条"光照越界"经字节码核验是错的 ⇒ 不要报** |
| **归因** | 拿**另一个类的同名常量**类比关键尺寸（vanilla `DataLayer` 的 16³ vs Flywheel 的 18³）| 归因错了一整轮，还写进了文档与 issue 草稿 ✗ | 关键尺寸一律查**字节码/`.class` 常量**（`javap`/常量池），别类比 |
| **假设** | 把"异步编译线程崩溃"当**竞态**就上 `ZINK_DEBUG=nobgc` | 换成同步后**仍崩** ⇒ 是"输入确定性"的 bug | 竞态假设必须做**换调度/换线程**的 A/B 才能立；否则先别写进结论 |
| **判读** | "没抓到 fault" ⇒ 以为没崩 / 没问题 | 同族崩溃也能落在**驱动内部线程**（该线程屏蔽 SIGSEGV ⇒ 全静默、连 DFX 都没记录）| "没有物证"≠"没有故障"：长跑 + **平台捕获**双保险；有静默死亡时优先怀疑屏蔽信号的第三方线程 |
| **取证** | 崩了才发现捕获没覆盖崩溃窗口 | hilog 是**环形快照**，重启会冲掉 | **崩后先导出捕获，再重启**（顺序反了就白跑一轮）|
| **方法** | 平台有没有开关先猜再说 | 60+ 查询的**负结论**能永久省掉后续尝试 | 先把负结论拿到手再谈"试旋钮" |
| **机制** | 从字节码里的**字符串**推断消费者读了哪个字段 | `GlCompat` 里确有 `GL_ARB_compute_shader` 字符串，但它的门控在**版本组**（`if (CAPABILITIES.OpenGL46) return true;`）⇒ 据此改错了一轮 ✗ | 判**取值路径**必须读**源码/反编译**（`ref/Flywheel` 就有源码 ✓）；字符串只是线索。改完用**行为判据**验证（本例：`GL_INVALID_VALUE` 5→0）|
| **判读** | 把 Flywheel 的 `fell back from …` 当"运行时崩溃兜底" | 它是 `BackendManagerImpl.chooseBackend()` 的**选择期**消息（配置想要的 backend 不支持 ⇒ 按优先级选下一个 supported）| 见到"惊悚"日志先查它**打印在哪段逻辑**；选择期消息 ≠ 故障；有它 + 无创建错误 = 理想 |
| **机制** | 把这个**上游/驱动提供的判定机制**当"真值来源"直接复用 | 上游 LWJGL 的版本组守卫查 `ext.contains("OpenGLxx")`，而 LWJGL **自己**只往 ext 里加**当前版本**那一个名字（`"OpenGL"+major+minor`，源码 `GL.java`）⇒ 守卫会让**低版本组全假**（低报 ✗），删掉守卫又让高版本组为真（高报 ✗）—— 两个极端都不对 | 复用任何机制前先**读源码/实测它在**本栈**到底给出什么**；两端都不对时去找**真值来源**（本例 = `GL_VERSION`），并用**自证行**把它打出来 |
| **判读** | 日志被截断先怀疑**平台/导出** | 实测是**我们自己**把含 NUL 的串当 C 串传给 `OH_LOG_Print` ⇒ 在 NUL 处**静默结束** ✗（平台上限是 4096 字节、且超限是**整条丢弃**，与 85 字节的截断都不符）| 截断先量**原始字节** + "全文搜尾部特征串"确认它是否**真没落盘**；再依次排查**自己的转发层** → 平台文档。另：C 串接口（`%s`）遇 NUL 会吃掉后面全部内容，转发原始输出前必须**清洗控制符** |

- **通用解的一手实操（2026-09-16）**：**"把能力藏掉"**是覆盖面最大的缓解手段（一次拦截 = 所有模组，
  不必逐模组打补丁）—— **但它到底怎么生效，必须实测**。本机实测的**完整链条**是：**Mesa 层拒绝创建 compute
  着色器**（`GL_INVALID_VALUE`）→ 模组的 compute 程序加载失败 → 它在**选择期**回退
  （`BackendManagerImpl.chooseBackend()` ⇒ `IndirectPrograms.allLoaded()` 为假 ⇒ 按优先级选下一个），
  **不是**"模组看见能力缺失后主动降级"；而**真正让门槛为假**的是把该能力从**消费者读的那份数据**
  （LWJGL 的能力标志）里摘掉 ✓。
  **拦截层必须选在消费者真正经过的那一层**：**GL 层**过滤 `glGetStringi`/`GL_NUM_EXTENSIONS`
  **到不了 LWJGL 的能力集** ✗（它既不吃我们改过的表、也不受其约束），改到 **Mesa 层**
  （`MESA_EXTENSION_OVERRIDE`）才有效果 ✓✓。⇒ 先问"消费者从哪拿这个信息"，再选层；
  然后问"生效点是**它主动避开**还是**它被动失败**"（后者取决于**它的错误处理** ⇒ 写入风险台账）。
- **★按轮次判"真实后端/行为"的判据**：别靠"我改了什么配置"推断 —— 找**被影响组件的自证日志**。
  本机例子：Flywheel 的 DEBUG 日志里 `Compiled **culling**/…` = INDIRECT、`Compiled **pipeline/instancing**/…`
  = INSTANCING ⇒ 一眼定后端 ✓（据此才把"配置改了没生效"和"崩溃规律"分开 ✓）。
- **★自证纪律（踩过）**：声称"我改了配置/环境"之后，必须**读回文件/环境本身**确认（例：读回 `.toml` 的那一行），
  不能凭"我执行了替换脚本"就下结论 —— 2026-09-16 我口述"已改回 instancing"而实际没改，导致一整轮结论作废 ✗。
- 相关：**测试机 = 用户资产**，改配置/环境前先备份、改后读回自证；被改动的文件可能被被测程序**回写**（Flywheel 会重写其 toml ✓）。

## §8 反面清单（明确不要做）

1. 不要为未证实的假设启动 45 分钟的构建。
2. 不要在随包默认里放任何**诊断**开关（`-XX:Log*`、LWJGL `Debug` 等）。
3. 不要让任何东西**默认**写进游戏目录（要写就给显式路径，且落在 `.hmmcraft/logs/`）。
4. 不要把"某次运行的现象"当成"已确立的机制"——至少要有单变量 A/B。
5. 不要只读第一条 fault 就下结论。
6. 不要把 hdc/shell 读不到的沙箱当成"没有文件"。
7. 不要把 review 只往别人代码上做。
8. 不要把"我改了什么"当成"被影响组件看到/做了什么"——去读它的**自证日志与字节码**（本机踩过：把"能力被藏掉"当成"模组看见后降级"✗，实际是"模组尝试→失败→捕获回退"，两者风险完全不同）。
9. 不要因为规避"看起来生效了"就停止追问**生效点**（主动避开 vs 被动失败 vs 恰好没触发）——三者的风险台账不一样。
10. 不要用补丁**制造失真的能力视图**：我们的 LWJGL overlay 曾删掉上游 **234 处**版本守卫 ⇒ 在 GL 4.2 设备上让 `OpenGL46` 为真 ⇒ 模组走错路径（Flywheel 因此走 compute、撞上驱动 bug）。**要么如实报告**（保留守卫），**要么用明确的运行时策略**（数据驱动、可关、有自证行、写进文档）。

## §9 平台**信号链与取证通道**（2026-09-17，Vulkan 战役实测定案）

> 这一节是**平台级事实**，与具体崩溃无关；凡在本机查原生崩溃都会用到。
> 案例与物证：`stuffs/research/vulkan/vk-m1-evidence/`（含第四轮 README）与 `stuffs/research/vulkan/vk-faultlog-archive/`。

### 9.1 信号派发顺序：**DFX 在链首**

hilog 原文形态：`signal_chain_handler call 0 rd sigchain action (sca=5afebbf1bc)` → `call 3 rd (musl)` → `call usr sigaction`。
⇒ **`libdfx` 的 sigchain 固定这个顺序**，普通 `sigaction` 装的 handler **一律落在 `usr` 层**（在 DFX **之后**）✗
⇒ **想"抢在 DFX 前面"是做不到的** ✗（不要浪费时间）。

**后果（三条实测）**：
1. **`hs_err` 永远不产** ✗ —— 即便 `-XX:ErrorFile` 配到了 `<实例>/.hmmcraft/logs/`，HotSpot 的 fatal handler 也**轮不到**。
   ⇒ **别再等 `hs_err`**。
2. **我们自己的 dumper（`meowbt`）也轮不到致死那一条** ✗ —— 判据：它明明报 `installed … chained-to SIGSEGV handler=… (valid=1)` ✓，
   但转储里**一条都不多** ✓ ⇒ 是"没被调用"，不是"没生效"。
3. **DFX 会放行"空页故障"** ✓ —— 证据：**GL 档天天跑**、HotSpot 的隐式空检查（`0x8/0xc`）天天触发，而进程活着 ✓
   ⇒ ⇒ 所以**若某轮死于 SIGSEGV，那不是"平台把良性故障当致命"，而多半是一个真·野指针读** ✓（地址不在空页里、HotSpot 认不出、无法转成 NPE）。

### 9.2 平台报告的 `Reason` **不一定是死因**（会 latch 良性 fault）

实测：同一轮 hilog 记的是 `si_code(1)`（MAPERR，真凶形），而 cppcrash 报告的 `Reason` 却是
`SEGV_ACCERR@0x0000005afce7d000`（= **safepoint 轮询页**，良性 ✓）⇒ **报告 latch 了"它决定上报的那一条"** ✗。
⇒ 判读规矩：
- `@0x5afce7d000`（`[---p]`，紧贴 `[anon:native_heap:brk]`，寄存器 `x8`=该地址）= **轮询页 ⇒ 良性** ✗ 当崩因会全错；
- **`Registers:` 段是精确的** ✓（`LastFatalMessage: Failed to unwind…` 只说明那串 `#00…#31` 帧不可信 ✗）⇒ **用 `pc`/`lr` 反查**才是正路；
- 死形要**另从 hilog 取**：`DFX_SignalHandler :: signo(N), si_code(M), pid, tid` + 结尾有没有 `rethrow … success` ✓。

### 9.3 取证通道（谁能读、能不能留）

| 对象 | 事实 |
|---|---|
| **我自己的 shell** | **能读** `/data/log/faultlog/faultlogger/` ✓（**写全路径**；父目录 `/data/log` 反而 `Permission denied` ✗）。**`hdc shell` 读不到** ✗ |
| faultlog 保留期 | **滚动保留 + 会清理** ✗ ⇒ **要引用就当场归档**到工作区；**禁止**用它做"有没有/多少"的**历史/范围**推断 ✗ |
| `.logs/`（用户导出） | 也有环形截断风险 ⇒ 结论落 notes，不以它是否留存为准 |

### 9.4 地址 → Java 方法：`stuffs/research/vulkan/resolve_pc.py`

消费 `-XX:+LogCompilation` 的 `hotspot_pid<pid>.log`（每条 nmethod 带 `address`+`size`）⇒
```
python3 stuffs/research/vulkan/resolve_pc.py <实例>/hotspot_pid<pid>.log 0x<pc> 0x<lr>
```
⚠️ 两个坑：① `lr` **可能是脏值**（实测落在 JVM 的 C 堆带内、与 `rthread` 同带）⇒ 别硬信 ✗；
② 该方法**只覆盖 nmethod**：**stub / 运行时代码**会报 "inside range: stub/non-method area" ✓（本身就是有用信息）。

### 9.5 `meowbt` 安装时机（**自保已加**）

它必须**在 HotSpot 装好 SIGSEGV handler 之后**才装，否则 `g_prev` 拿到 `SIG_DFL` ⇒ **把 JVM 顶掉** ⇒
良性故障反而变致命、且不产 `hs_err` ✗。现版本会在装前 `sigaction(SEGV,NULL,&cur)` 检查，
**旧动作是 `SIG_DFL`/`SIG_IGN` 就拒装 + hilog 告警**，且**不置 `g_installed`**（留给后续调用重试）✓；
Vulkan 档的安装点放在**第一次 Vulkan 调用**（保证在 JVM 之后）✓。

### 9.6 诊断件**不得改变崩溃语义**（本役踩过）

- 在 JVM 进程里**劫持 SIGSEGV** ✗（见记忆 `meowcraft_no_jvm_sigsegv_hijack`）；
- **高音量日志会扰动时序** ✗ —— 若怀疑目标含竞态，诊断日志要能**默认关**（本役为此给 shim 加了静默模式 ✓）。
- 同理：**别把诊断型 VM 参数放进随包默认** ✗；**参数名要先去 `ref/jdk26u` 源码核对** ✗
  （本役把 `ImplicitNullChecks` 误写成 `UseImplicitNullChecks` ⇒ JVM 直接拒启并 `abort()` ✓）。
